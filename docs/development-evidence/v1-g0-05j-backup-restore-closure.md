## A significant defect found by this package's own real deployment rehearsal

Standing up a genuinely fresh, disposable, P05-provisioned PostgreSQL and migrating it through 216 via the actual `vestrace migrate` CLI — precisely the rehearsal Category D work exists to perform — surfaced a defect in P05-I's migration 0216 that survived that package's own final review (which used direct SQL probes and `SET ROLE` tricks, never the real CLI against a database provisioned exactly as production would be):

1. **`p05_assertion_migration`'s predecessor-pair allowlist in `crates/vestrace-infrastructure/src/postgres/pool.rs` never included `(216, 215)`.** The production `vestrace migrate --only-version 216` command refused to even attempt the migration, independent of any privilege question — `migrate_only_version_after` rejects any `(version, required_prefix)` pair not in a fixed match arm, and 216 was never added to it. Migration 0216 was, in this literal sense, permanently undeployable via the real CLI. Fixed by adding the `(P05_DRAIN_PREFIX_VERSION, P05_SAFETY_READINESS_ASSERTION_MIGRATION_VERSION)` arm.
2. **Migration 0216's schema-creating DDL was structured on the wrong P05-era pattern.** P05-I's final review had already found and fixed migration 0216's inability to run as the restricted `vestrace` role, via an ownership hand-back bridge modeled on the older P04-era convention (migrations 0176-0208): temporarily transfer ownership of the objects a migration widens, then hand them back. That fix closed the specific failure the reviewer reproduced (`must be owner of table material_key_creation_intents`) but never granted `vestrace` the schema-wide `CREATE` privilege needed to create the two genuinely *new* objects (`installation_drain_requests`, and the two new drain functions) — a privilege every P05-era migration (0209 onward) deliberately avoids re-granting, even temporarily, because doing so reopens exactly the attack surface the P05 safety bootstrap's `REVOKE CREATE ON SCHEMA public FROM vestrace` exists to close. Standing up the real database and running `vestrace migrate --only-version 216` as `vestrace` reproduced `permission denied for schema public` — the schema-creation half of the problem the SQL-probe-based final review never exercised.

   The correct, already-established P05-era pattern (used by 0211's `vestrace_install_p05_base_capture_guards` and 0212's `vestrace_install_p05_restore_cutover_guards`) puts the real DDL inside a `SECURITY DEFINER` function owned by `vestrace_guarded_owner` — the owner of schema `public` itself, so its body always has implicit `CREATE` rights regardless of what has been revoked from `vestrace` — defined in `docker/postgres/init-runtime-role.sh` and invoked by name from the migration. No privilege ever passes through `vestrace` at all, and no ownership hand-back is needed. Migration 0216 and `init-runtime-role.sh` were rewritten to this pattern (`vestrace_install_p05_installation_drain_guards`), with a superuser-gated inline fallback for `#[sqlx::test]` (whose fresh databases are `template1` clones — confirmed by reading `sqlx-postgres`'s own test-fixture source, `CREATE DATABASE "db_name"` with no `TEMPLATE` clause — and never see `init-runtime-role.sh`'s provisioned state; `DRAIN_HISTORICAL_MIGRATOR` is the first bounded migrator built to reach past 208 in that harness, so this tension had never previously been exercised). Getting the fallback correct took three verified iterations, each a real, distinct privilege gap: the new table needed an explicit `ALTER TABLE ... OWNER TO vestrace_guarded_owner` (its raw `CREATE TABLE` in the fallback's plain, non-`SECURITY DEFINER` block otherwise leaves it owned by the connecting superuser, which the two *pre-existing* reserve functions — still owned by `vestrace_guarded_owner` via `CREATE OR REPLACE`'s ownership-preserving semantics — then have no privilege to read); and the two brand-new drain functions needed an explicit `ALTER FUNCTION ... OWNER TO vestrace_guarded_owner`, because this schema's raw-mutation-rejection triggers gate on `current_user = 'vestrace_guarded_owner'` specifically, not merely "some privileged owner."

Both defects were fixed and verified end-to-end, twice: once as the real restricted `vestrace` role via the actual `vestrace migrate --only-version 216` CLI command against the fresh disposable PostgreSQL this package stood up (ledger reached version 216 — 146 rows total; `installation_drain_requests` and all four drain/reserve functions owned by `vestrace_guarded_owner`; a live `vestrace_request_installation_drain` call as `vestrace` succeeded and the table was readable back), and once via every one of P05-I's own `#[sqlx::test]` suites re-run against the rewritten fallback path (`installation_drain_contract` 4/4, `installation_drain_request` 5/5, `intent_crash_boundaries` 20/20, `material_intent_lifecycle` 9/9, `credential_intent_lifecycle` 25/25 — all unchanged from P05-I's own final counts). `docs/development-evidence/v1-g0-05i-drain-mutation-permit.md` was updated to describe this corrected architecture in place of the superseded ownership-hand-back description.

This finding is exactly what the parent roadmap's Category D classification anticipated: work "achievable but needs the heavier disposable-PostgreSQL/Linux-runner recipe," because only a rehearsal that actually deploys as the real restricted role, through the real CLI, against a database provisioned exactly as `docker/postgres/init-runtime-role.sh` would provision it, can catch a defect that is invisible to both `#[sqlx::test]` (superuser, bypasses every check) and to direct `SET ROLE` SQL probes (which don't exercise the CLI's own predecessor-pair gate at all).

## The disposable infrastructure recipe used

1. **Image:** `docker build -t p05j-postgres:latest ./docker/postgres` (rebuilt fresh — the cached `p05d-postgres:latest` image predates P05-I's `init-runtime-role.sh` changes).
2. **Network and container:** `docker network create p05j_default`; `docker run -d --name p05j-postgres --network p05j_default -p 127.0.0.1:55434:5432` with `docker/postgres/init-runtime-role.sh` mounted at `/docker-entrypoint-initdb.d/10-runtime-role.sh` (the Dockerfile does not bake the init script — Compose/`docker run -v` must mount it, or role provisioning silently does not happen).
3. **Three-phase migration route**, exactly as the established memory recipe (`p05-supervisor-tests-need-a-linux-runner`) describes: `migrate --through-version 208` (138 rows) as `vestrace`; the bootstrap psql stage (`ALTER ROLE vestrace NOLOGIN`, `SELECT public.vestrace_install_p05_safety_schema()`, `ALTER ROLE vestrace LOGIN`) as `vestrace_bootstrap`; then `migrate --only-version` for 209 through **216** (not 215 — this package is the first to need the database at the same schema head as the always-on test cluster) one at a time as `vestrace`, reaching ledger head 216 (146 rows, all successful).
4. **Direct-SQL suites** (`installation_safety_authority`, `backup_archive_authority`, `restore_cutover_authority`) ran on Windows directly against the disposable database via `VESTRACE_P05_TEST_DATABASE_URL`. The real fix, found by an early mistake this package caught and corrected, was connecting as the restricted `vestrace` role, not the bootstrap superuser: connecting as `vestrace_bootstrap` bypasses every privilege check these tests exist to prove, so the forged-row `INSERT`s the tests attempt succeeded (or hit an unrelated unique-violation) instead of being refused. While debugging that mistake, this package also inserted minimal raw seed rows (`installation_safety_state`, a `managed_backup_sets` row with a base checkpoint, `managed_backup_restore_holds`/`managed_restore_attempts`) as `vestrace_bootstrap`, believing the tests' forged-row `INSERT`s needed a satisfied foreign key to reach their privilege assertion. On reflection this reasoning does not hold for the three authority suites specifically: PostgreSQL checks a role's table-level privilege before evaluating row-level constraints such as foreign keys, so `installation_safety_authority`/`backup_archive_authority`/`restore_cutover_authority` refuse a privilege-lacking role's `INSERT` regardless of whether the referenced parent row exists, and the seeding was very likely unnecessary busywork for those three once the role was corrected. This document does not claim to have re-verified that removing the seed rows still leaves those three suites green (the disposable database was already torn down when the imprecision was found) — record it here as an open, low-risk loose end rather than a re-confirmed fact. The seeding may have been genuinely load-bearing for the two Linux-runner recovery suites' own setup instead, which this document does not separately claim.
5. **Linux-runner suites** (`safety_supervisor_witness`, `safety_archive_recovery`, `safety_restore_recovery`) ran via `docker run --rm --network p05j_default` against the cached `p05c-rust185-cache:latest` image and the pre-existing `p05c-linux-cargo-home`/`p05c-linux-target-cache` volumes (already warm from prior P05 sessions; no Rust toolchain rebuild needed). `safety_supervisor_witness` needs no database at all (pure filesystem adapter, run for correct Linux fsync semantics only); the other two use `VESTRACE_P05_RECOVERY_BOOTSTRAP_DATABASE_URL`/`VESTRACE_P05_RECOVERY_SUPERVISOR_DATABASE_URL` pointing at `p05j-postgres` over the Docker network.
6. **Teardown:** `docker rm -f p05j-postgres && docker network rm p05j_default`, confirmed removed via `docker ps -a`/`docker network ls` before qualification closed.
