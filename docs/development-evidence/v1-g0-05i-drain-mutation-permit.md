# P05-I DrainMutationPermit/Quiescing: measured result

**Recorded:** 2026-09-17, following `docs/superpowers/plans/2026-09-17-vestrace-v1-g0-05i-drain-mutation-permit.md` (design: `docs/superpowers/specs/2026-09-17-vestrace-v1-g0-05i-drain-mutation-permit-design.md`). Executed via superpowers:subagent-driven-development: a fresh implementer subagent per task, an independent reviewer per task diff, directly in this repository's working tree (no git worktree — the whole P05 program depends on a preserved dirty working tree tracked by `scripts/verify-dirty-baseline.mjs`, confirmed with the operator before starting).

**Acceptance boundary:** P05-I only. Closes G0 criteria g0-12, g0-13, and the `DrainMutationPermit`/"no post-freeze write" conjunct of g0-10 (which stays `blocked` overall — its browser-oracle conjunct is unrelated and still open).

## What was built

`DrainMutationPermit`/`Quiescing` did not exist anywhere in the repository before this package (confirmed absent by grep, and already recorded as such in P04's own evidence doc). Built from nothing:

- **Migration 0216** (`migrations/0216_installation_drain_request.sql`): a new `installation_drain_requests` table (installation-wide, no RLS — matching the `installation_fingerprint_continuity` precedent), a partial unique index enforcing at most one active drain, a nullable `drained_by` snapshot column on both `material_key_creation_intents` and `credential_key_creation_intents`, two new guarded functions (`vestrace_request_installation_drain`, `vestrace_reconcile_installation_drain`), and one added precondition in each of the two existing `reserve` functions.
- **`crates/vestrace-domain/src/installation_drain.rs`**: `InstallationDrainRequestId`, `InstallationDrainRequest` (Draining/Frozen), and two exhaustive-by-construction classification functions (`is_material_pre_quiescing`, `is_credential_pre_quiescing`) — a state added to either source enum later fails to compile here rather than being silently misclassified.
- **`crates/vestrace-application/src/ports.rs`**: the `DrainMutationPermitRepository` trait (`request`, `current_state`, `reconcile`).
- **`crates/vestrace-infrastructure/src/postgres/installation_drain.rs`**: `PgDrainMutationPermitRepository`, the PostgreSQL implementation.
- **`crates/vestrace-infrastructure/src/postgres/pool.rs`**: generalized `bounded_migrator` into `bounded_migrator_excluding(upper, excluded)` and added `DRAIN_HISTORICAL_MIGRATOR` (bounded at 216, excluding the seven P05 assertion migrations 209-215) — `bounded_migrator`'s own behavior and `HISTORICAL_MIGRATOR`'s bound (208) are unchanged.
- **`crates/vestrace-infrastructure/tests/installation_drain_request.rs`**: a new PostgreSQL contract suite (4 tests as built; a fifth was added in final review, see below).
- **`crates/vestrace-infrastructure/tests/intent_crash_boundaries.rs`**: extended in place with 5 new crash-boundary tests, reusing the file's own existing `material_at`/`credential_at`/`resume_material`/`resume_credential`/`CountingVault` helpers rather than duplicating them.

No new per-intent state or transition was added anywhere; every material/credential intent transition this package touches already existed and is evidenced under g0-08/g0-09.

## The migration-numbering prerequisite

`bounded_migrator`'s hard `<= version` cutoff could not express "up through 216, except the fixed P05 assertion migrations 209-215" without also re-admitting them. Fixed by generalizing to an exclusion-list variant (`bounded_migrator_excluding`) that leaves the original function and `HISTORICAL_MIGRATOR` untouched. Without this, migration 0216 would have been invisible to ordinary `#[sqlx::test]` suites — the same problem P05-E fixed for migration 0209, recurring one migration later.

## Three defects found during execution, all fixed and re-verified

1. **A plan-mandated impossible test expectation (Task 2).** The plan's own Step 4 said a new guard test on `DRAIN_HISTORICAL_MIGRATOR` should pass immediately — impossible, since that `LazyLock` panics on first access when migration 216 doesn't yet exist (which it didn't, at Task 2's point in the sequence). Ruled: plan-authoring defect, not implementation defect; corrected the plan's expected-outcome text to match its own already-correct Step 5 framing (expected to fail until Task 3). No code change.
2. **A dropped comment in migration 0216 (Task 3).** The plan's own SQL for the widened `vestrace_reserve_credential_key_creation_intent` dropped one pre-existing comment line from the original `migrations/0173`, violating the stated "byte-for-byte identical beyond the guard block" requirement. Traced to a transcription slip when the plan was authored. Fixed with a one-line resumed-implementer fix round; independently re-verified byte-for-byte identical beyond the guard block.
3. **Missing ownership/grants in migration 0216, found by Task 7 (the most significant finding).** `installation_drain_requests` and the two new functions were created with no ownership transfer to `vestrace_guarded_owner`. Since the two widened `reserve` functions (owned by `vestrace_guarded_owner`, a `SECURITY DEFINER` role) now read `installation_drain_requests` inside their body, every `reserve()` call failed with `permission denied for table installation_drain_requests`, drain active or not — and `reserve_is_refused_while_draining` was a false pass (failing for the wrong reason). Task 7's implementer correctly diagnosed this as a defect in an earlier, already-closed task's file and declined to fix it itself, routing the decision back to the controller rather than silently patching around it. The controller investigated the established ownership-transfer convention directly (migrations 0176, 0187, 0191 — a reusable `vestrace_assign_p03_table_owner`/`vestrace_assign_p03_function_owner` helper pair, defined once in 0176 and reused by every later migration regardless of package name, with a superuser-only fallback for the SQLx-fresh-database path) and applied the fix to migration 0216 directly, since the required investigation was already complete. A dedicated review independently verified the fix against all three precedent migrations, confirmed the exception path (not a silent allowlist hit) is what actually runs in this environment, and confirmed all three of Task 3's original suites remained unaffected.

One assertion is worth naming explicitly: `draining_does_not_change_how_result_prepared_finalizes`'s final check asserts `Draining`, not `Frozen` — a `Parked` `ResultPrepared` intent never leaves the pre-Quiescing set (it is finalized only by its owning job's own bind call, never by mere resumption), so a correct `reconcile()` must keep reporting the drain as still pending. This held exactly as predicted and was independently re-verified by the task reviewer, who confirmed it was not silently weakened to match observed behavior.

### What the freeze evidence does and does not cover

The crash-boundary freeze evidence is a **representative** sample, not exhaustive coverage of every crash boundary. Five of `intent_crash_boundaries`'s 20 tests are drain-aware (`draining_does_not_change_how_a_reserved_material_intent_resumes`, `draining_does_not_change_how_a_content_prepared_material_intent_resumes`, `draining_does_not_change_how_result_prepared_finalizes`, `draining_does_not_change_how_a_reserved_credential_intent_resumes`, `a_bound_intent_present_before_a_drain_is_not_stamped_and_never_abandons` — `crates/vestrace-infrastructure/tests/intent_crash_boundaries.rs:991`, `:1027`, `:1056`, `:1092`, `:1120`). The credential side gets exactly one boundary (`after_reserved`) out of its seven, and three named material boundaries are not drain-aware at all: `after_vault_create_before_receipt`, `after_abort_before_witnessed_erase`, and `after_erase_receipt_before_terminal_append`. The evidence supports "a drain does not change how these representative boundaries resume"; it does not support "every crash boundary was tested under a drain."

### The refusal error type is asymmetric between `request()` and `reserve()`

The SQLSTATE-`55000`-to-`ApplicationError::Conflict("INSTALLATION_DRAIN_ALREADY_ACTIVE")` mapping exists **only** in `PgDrainMutationPermitRepository::request()` (`crates/vestrace-infrastructure/src/postgres/installation_drain.rs:50-52`). `PgMaterialIntentRepository::reserve()` — and its credential equivalent — has no such mapping, so a `reserve()` call refused while draining *or* while frozen surfaces as `ApplicationError::Storage(...)` carrying the raw database message, not as a typed `Conflict`. `reserve_is_refused_while_draining` and `reserve_is_refused_after_reconcile_reaches_frozen` therefore assert only `is_err()`, which is all that is actually proven. A typed "refused because the installation is draining" distinction on the reserve paths would require adding that mapping to `crates/vestrace-infrastructure/src/postgres/material_intent.rs` and the credential equivalent; no package needs it yet.

## Two Critical defects found in final review, fixed before push

The final whole-branch review found two Critical defects and one Important design-level gap that this package's own suites could not have caught. All three were fixed and re-verified before the package was pushed.

**(a) Migration 0216 was unappliable by the restricted `vestrace` role (Critical).** `material_key_creation_intents`, `credential_key_creation_intents`, and the two `vestrace_reserve_*_key_creation_intent` functions are owned by `vestrace_guarded_owner` (assigned in migration 0174). Migration 0216's `ALTER TABLE ... ADD COLUMN drained_by`, its `CREATE TABLE installation_drain_requests`, and its four `CREATE OR REPLACE FUNCTION` statements all required privileges the deployed runtime role does not have. **`#[sqlx::test]` structurally could not catch this:** it creates each database fresh and runs every migration as the PostgreSQL superuser, which bypasses every ownership and schema-privilege check, whereas the deployed migrator runs as the restricted `vestrace` role. A green suite and a broken deployment are fully compatible here.

The first fix attempt (during final review, before push) mirrored the P04-era pattern: a self-destructing ownership hand-back bridge (`vestrace_prepare_p05_installation_drain_upgrade`) that temporarily transferred ownership of the four *pre-existing* objects to `vestrace` so the migration's raw DDL could run, then handed them back at the migration's tail. This was independently verified against the live cluster and closed the specific failure the reviewer reproduced (`must be owner of table material_key_creation_intents`) — but it never granted `vestrace` the schema-level `CREATE` privilege needed to create the two genuinely *new* objects (`installation_drain_requests`, and the two new drain functions), because that privilege is deliberately revoked from `vestrace` by the P05 safety bootstrap and no P05-era migration (0209 onward) had ever needed to re-grant it.

**P05-J's real end-to-end deployment rehearsal (a fresh disposable PostgreSQL, provisioned exactly as production would be, migrated through 216 by the actual `vestrace` role via the real `vestrace migrate` CLI) found the deeper problem this bridge-based approach could not fix without reopening the P05 lockdown:** creating brand-new schema objects as `vestrace` needs schema-wide `CREATE`, which every migration since 0209 correctly avoids granting even temporarily. The established P05 pattern for this (already used by 0211's `vestrace_install_p05_base_capture_guards` and 0212's `vestrace_install_p05_restore_cutover_guards`) is different: the real DDL lives inside a `SECURITY DEFINER` function owned by `vestrace_guarded_owner` (the owner of schema `public` itself, so its body always has implicit `CREATE` rights regardless of what has been revoked from `vestrace`), defined once in `docker/postgres/init-runtime-role.sh` and invoked by name from within the migration file. No ownership hand-back, and no privilege ever passes through `vestrace` at all.

Migration 0216 and `docker/postgres/init-runtime-role.sh` were rewritten to this pattern: a new `vestrace_install_p05_installation_drain_guards()` installer (idempotent, matching `to_regclass`/`information_schema.columns` existence checks before each `CREATE`) replaces the ownership-hand-back bridge entirely, and the migration itself calls it, then asserts the resulting schema exists. Because `DRAIN_HISTORICAL_MIGRATOR` is the first bounded migrator built to reach migration 216 inside `#[sqlx::test]` — and `#[sqlx::test]` creates each database via a plain `CREATE DATABASE` (confirmed by reading `sqlx-postgres`'s own test-fixture source), which Postgres clones from `template1`, never from the provisioned `init-runtime-role.sh` state — the migration also carries a superuser-gated fallback that performs the identical DDL inline when the installer function is absent. Getting the fallback correct took three real, verified iterations: it needed the same `ALTER TABLE ... OWNER TO vestrace_guarded_owner` the authoritative installer gets implicitly (its raw `CREATE TABLE` runs in a plain, non-`SECURITY DEFINER` block, so without an explicit owner transfer the table ends up owned by the connecting superuser, not `vestrace_guarded_owner` — and the two pre-existing reserve functions, which keep their `vestrace_guarded_owner` ownership through `CREATE OR REPLACE`, then have no privilege to read it); and the two brand-new drain functions needed an explicit `ALTER FUNCTION ... OWNER TO vestrace_guarded_owner`, because this schema's raw-mutation-rejection triggers gate on `current_user = 'vestrace_guarded_owner'` specifically, not merely "some privileged owner" — a function left owned by a test superuser is correctly refused by those triggers. Verified end-to-end, twice: once as the real restricted `vestrace` role via the actual `vestrace migrate --only-version 216` CLI command against a fresh disposable PostgreSQL (ledger reached version 216, all new objects owned by `vestrace_guarded_owner`, a live `vestrace_request_installation_drain` call succeeded), and once via every one of P05-I's own `#[sqlx::test]` suites against the fallback path (`installation_drain_contract` 4/4, `installation_drain_request` 5/5, `intent_crash_boundaries` 20/20, `material_intent_lifecycle` 9/9, `credential_intent_lifecycle` 25/25 — all unchanged).

A smaller regression from the first fix attempt was also found and corrected in the same pass: the bootstrap block's first placement (mirroring an existing block's *location* along with its style) had landed before `init-runtime-role.sh`'s byte-pinned `# P05 safety supervisor role — do not move` marker, turning `tests/p05_provisioner_prefix.test.mjs` red (that pre-marker region is a byte-for-byte capture of P04-era work; no P05 addition may land there). The rewritten installer is defined as its own standalone `psql <<'SQL'` section after the marker; `p05_provisioner_prefix` is back to green. The migration's head guard also catches `WHEN undefined_function OR insufficient_privilege`, closing a latent fail-open trap: a deployment where the installer was provisioned into the wrong database would otherwise have surfaced a raw "function does not exist" rather than an actionable message.

**(b) A `Frozen` drain stopped refusing `reserve()` (Critical).** Both reserve guards tested `WHERE completed_at IS NULL`, so the moment `vestrace_reconcile_installation_drain` stamped `completed_at` on reaching Frozen, the guard stopped matching and `reserve()` began succeeding again — exactly backwards from "a freeze is permanent," which the design requires (design §7). This directly falsified the "no post-freeze write" conjunct of g0-12 that this package claims: the package was claiming post-freeze writes were refused while the schema permitted them. Fixed by dropping the `completed_at IS NULL` qualifier from both guards (both instances, once in `vestrace_install_p05_installation_drain_guards()` in `docker/postgres/init-runtime-role.sh` and once in migration 0216's `#[sqlx::test]` fallback, kept byte-identical between the two) — any drain request row, active or frozen, now refuses new reservations permanently, which is correct because this schema has no reactivation path (a new drain is a new row). Covered by the new `reserve_is_refused_after_reconcile_reaches_frozen` test.

**(c) `InstallationMutationPermit::Exclusive` was claimed but never acquired; a real TOCTOU race (Important, partly design-level).** `ports.rs`'s doc comment claimed `request` "acquires `InstallationMutationPermit::Exclusive` internally"; `PgDrainMutationPermitRepository::request()` only opened a scoped transaction. Under READ COMMITTED a concurrent `reserve()` could read `installation_drain_requests` as empty at the same instant a `request()` inserted and stamped, and both could commit — producing a live pre-Quiescing intent the drain never snapshotted. This was partly a gap in the approved design, not only in the implementation: design §19's premise that "every governed mutation already acquires Shared" does not hold for `reserve()` as it exists today. Fixed by taking the exclusion directly in SQL: `pg_advisory_xact_lock(hashtext('vestrace-installation-mutation-permit-v1'))` as the first statement of `vestrace_request_installation_drain` and `pg_advisory_xact_lock_shared` of the same key as the first statement of both reserve functions (present in both the authoritative installer and the `#[sqlx::test]` fallback, kept byte-identical between the two). Both locks are transaction-scoped, so they release on commit or rollback with no manual unlock and no risk of surviving a crash. The doc comment at `crates/vestrace-application/src/ports.rs:243-250` was corrected to describe what the code actually does.

The race was confirmed empirically rather than assumed, and the regression guard was then measured against its own failure mode. With the exclusive lock removed and the embedded migrator rebuilt, an eight-way concurrent `request()` race produced the raw `23505` unique-constraint violation on `installation_drain_requests_one_active` — surfacing as `ApplicationError::Storage(...)` instead of a typed `Conflict`. `tokio::join!` does produce genuine database-level overlap in this harness (two concurrent one-second `pg_sleep` calls complete in ~1.09s, not ~2s), but the original two-way form of `a_second_concurrent_drain_request_is_refused` never caught a missing lock at all (3 of 3 runs passed with it deleted), and even the eight-way form catches it only about three runs in five. Widening further does not help: the `#[sqlx::test]` pool allows five connections, so sixteen racers detect no better than eight. `a_second_concurrent_drain_request_is_refused` (`crates/vestrace-infrastructure/tests/installation_drain_request.rs:55-126`) therefore now pairs the eight-way race with a deterministic assertion, via `pg_get_functiondef`, that the exclusion is declared in all three places it must be — `pg_advisory_xact_lock(` in `vestrace_request_installation_drain` and `pg_advisory_xact_lock_shared(` in both reserve functions, each keyed to `hashtext('vestrace-installation-mutation-permit-v1')`. A one-sided lock excludes nothing, which is why all three are checked; deleting the material-side shared lock is a regression the race half alone would never detect. Verified by deleting each lock in turn: 3 of 3 runs fail for the exclusive lock, 3 of 3 for the material shared lock, and the suite passes 5/5 with all three present (deterministic across eight consecutive isolated runs).
