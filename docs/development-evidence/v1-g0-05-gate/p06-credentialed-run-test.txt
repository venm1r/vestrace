P06 Task 8 — credentialed branch (remote OpenAI-compatible, bearer) walkthrough
Captured: 2026-09-18, against the same local `docker compose` stack and the
same session's investigation as p06-no-auth-run-test.txt. Read that file
first; this one does not repeat verification already established there.

RESULT: THE CREDENTIALED BRANCH DOES NOT REACH A MODEL COMPLETION EITHER,
for the same four root causes already proven in the no-auth branch, plus one
additional gap specific to this branch. No new browser walkthrough was run
for the connection-creation/model-registration/qualification steps, because
Blockers One through Three (below) are not auth-mode-specific: they stop a
`kind: open_ai_chat_completions_v1, auth_mode: bearer` connection at the
exact same points, for the exact same reasons, as they stopped the
`kind: l_m_studio_local, auth_mode: none` one. Re-running an identical
walkthrough with different form values would add no new evidence; it is not
run here for that reason, not because it was skipped for convenience.

================================================================================
Blockers inherited unchanged from the no-auth branch
================================================================================

BLOCKER ONE (connector_id FK, no /v1/connectors route) — applies identically.
`apps/console/src/routes/ConnectionsPage.tsx`'s create-connection code path is
shared between both presets; only `kind`, `auth_mode`, `transport_policy` and
`credential_slot_id` differ per preset. The connector_id problem is upstream
of any of those fields.

BLOCKER TWO (provider_id FK, no /v1/providers replacement) — applies
identically. Model registration does not vary by which Connection's auth mode
it is bound to.

BLOCKER THREE (no qualification executor in any production binary) — applies
identically and is actually a strictly stronger blocker for this branch: the
credential branch's qualification target
(`QualificationTargetRequest::Credential { revision_id, slot_id,
activation_guard_id, expected_slot_version }`) requires an activated
credential to exist before a qualification job naming it can even be
requested meaningfully, on top of the same "nothing ever processes the job"
defect proven in the no-auth branch.

BLOCKER FOUR (POST /ag-ui/run refuses with 503) — applies identically and
unconditionally: `RunCoordinator::add_steps`'s refusal
(coordinator.rs:249-256) triggers on any `RunActorRef::AgentSnapshot` +
`NewRunStepInput::Confidential` combination, regardless of which Connection
or auth branch a workspace's chat default happens to point at. This blocker
alone is sufficient to prevent EITHER branch from ever producing a real
completion through this build's AG-UI endpoint, independent of Connections,
Models, or qualification entirely.

================================================================================
BLOCKER FIVE — credentialed branch only: no real secret material exists,
and nothing creates it
================================================================================

Investigated per the plan's own note that credential material has no HTTP
surface in this build (`docs/superpowers/plans/2026-09-18-vestrace-v1-p06-real-execution.md`,
Task 5's gap note 2).

  $ grep -rn "credential_intent\|CredentialIntent" crates/vestrace-http/src/api/
  crates/vestrace-http/src/api/connections.rs   (only as a caller-supplied,
    never-validated-against-a-real-row field on CredentialActivationRequest /
    CredentialRotationRequest / CredentialAbandonRequest)

  No route creates one. The only place real material-key bytes get produced is
  test fixture code:

  $ grep -rn "credential-fixture-ciphertext\|fn seed_credential\|material_key" \
      crates/vestrace-infrastructure/tests/common/mod.rs | head -5
  crates/vestrace-infrastructure/tests/common/mod.rs:  ... b"credential-fixture-ciphertext" ...

  This literal byte string is a placeholder used only to satisfy NOT NULL /
  encryption-shape constraints in test setup — it is not a real bearer token,
  cannot be sent to any real HTTP API, and using it against a genuine remote
  OpenAI-compatible endpoint would fail authentication immediately even if
  Blockers One through Four did not exist.

  Seeding it (the same way `tests/common/mod.rs` does, via direct SQL against
  the disposable local database) was considered as a way to at least exercise
  the `activate_credential` HTTP call's shape, but was not done: doing so would
  only prove the activation call's plumbing, which is not in doubt (it is
  exercised by this repo's own existing test suites), and would still not
  produce a real chat completion, because Blocker Four refuses the run step
  regardless of which credential is behind the Connection. It would not have
  added evidence toward this task's actual goal (a real completion), only
  toward a narrower claim nobody asked this task to prove.

  No remote OpenAI-compatible API key was available in this environment to
  test against a genuine third-party service. Even with one, Blockers One,
  Two, Three and Four would each need to be resolved first for a real
  completion to be reachable through either branch.

================================================================================
Conclusion for this branch
================================================================================

Not run further. The credentialed branch is blocked by everything the
no-auth branch is blocked by, plus the absence of any real credential
material or a way to create it. No completion was produced, none is claimed,
and no plaintext or fabricated secret was sent anywhere.
