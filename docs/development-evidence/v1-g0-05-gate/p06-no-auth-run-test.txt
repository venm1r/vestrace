--- Q2: does ConnectionTransportPolicy reject `host.docker.internal`? NO ---
--- ...and the reason it does not is itself a defect. ---

  The brief anticipated that the domain would DERIVE the transport policy from
  the runtime URL and refuse a non-loopback host under a loopback policy. It
  does derive it — but only in the domain constructor, which the HTTP create
  path never calls.

  `crates/vestrace-domain/src/connection/revision.rs:101-124`
    impl ConnectionTransportPolicy {
        fn for_runtime_url(url: &NormalizedBaseUrl) -> Result<Self, DomainError> {
            if url.as_str().strip_prefix("http://").and_then(runtime_authority_host)
                .is_some_and(|host| {
                    host.eq_ignore_ascii_case("localhost")
                        || host.eq_ignore_ascii_case("localhost.")
                        || host.parse::<std::net::IpAddr>().is_ok_and(|a| a.is_loopback())
                })
            { Ok(Self::LoopbackOnly) }
            else if url.as_str().starts_with("https://") { Ok(Self::RemoteHttps) }
            else { Err(DomainError::InvalidArgument("non-loopback runtime URL requires HTTPS".into())) }
        }
    }

  That function is called only from `ConnectionRevision::new` / `from_persisted`.
  The HTTP create path does NOT construct a `ConnectionRevision`; it passes the
  caller's stated policy straight into SQL:

  `crates/vestrace-infrastructure/src/postgres/connection_revision_repository.rs:322-337`
    let revision = sqlx::query_scalar(
        "SELECT vestrace_create_connection_revision_and_advance_head(...)")
        ...
        .bind(transport_policy(&self.command.transport_policy))   // <-- caller-stated, NOT derived
        ...

  Observed consequence — a non-loopback destination is accepted under a
  `loopback_only` policy:

  $ curl -X POST http://127.0.0.1:8080/v1/connections ... \
      -d '{... "runtime_base_url":"http://host.docker.internal:12345/v1",
              "transport_policy":{"kind":"loopback_only"}, "auth_mode":"none" ...}'
  HTTP 201
  {"audit_event_id":"01a0b1f9-a33c-7a62-aadc-0396da9b4e58", ...}

  So no workaround was needed for this task. But the domain's own guard test
  `deceptive_loopback_prefixes_are_not_local_runtime_urls`
  (revision.rs:452-472), which exists precisely to stop a deceptive hostname
  being called loopback, is bypassed at the HTTP boundary. A caller can label
  any reachable non-loopback destination `loopback_only`.

  Separately, the brief's suggested fallback — "add a `127.0.0.1 lmstudio.local`
  style loopback alias" — would NOT have worked against this code even if the
  derivation had been enforced: the check requires the host to be literally
  "localhost"/"localhost." or to parse as a loopback IP address. A hostname
  alias such as `lmstudio.local` satisfies neither.

================================================================================
6. WHAT WOULD ACTUALLY PROVE THIS, IF THE MISSING PIECES EXISTED
================================================================================

For the no-auth branch to be provable end-to-end through the browser, four
things must exist that do not exist today:

  (a) A way to create a Connector. Either an HTTP route (`POST /v1/connectors`)
      plus a selector in ConnectionsPage's form, or `insert_stable_connection`
      creating the connector row in the same transaction. Without one of these
      the Connections page's Create button can never succeed.

  (b) A way to register a Provider, or a governed model-creation route the
      console actually calls. `POST /v1/providers` is permanently retired and
      ModelsPage still posts to the legacy shape. ModelsPage also needs
      Connection and wire_model_id fields to express what
      `POST /v1/models/{id}/revisions` already accepts.

  (c) A qualification executor in the worker: a poller that leases
      `qualification_jobs` rows in `requested`, drives
      `QualificationJobService::run_next_probe` across the q1 ordinals using
      `PgQualificationProbeRunner`, and finalizes the job. Plus the console
      sending the connection's real no-auth binding revision id rather than a
      random UUID.

  (d) `GovernedRunStepInputReservation` composed into the server binary and
      handed to the AG-UI handler (or a `RunOrchestrator` impl that delegates
      confidential input to it), so `POST /ag-ui/run` creates a real run step
      with a model binding snapshot that the worker's already-wired
      `GovernedProviderStepExecutor` (worker.rs:157) can dispatch.

With those four in place, the proving evidence would be: a Playwright
transcript showing the connection reaching `qualified`, the model reaching a
non-blocked state, the default set, and an `/ag-ui/events/stream` capture
containing the model's actual completion text — none of which could be captured
here, and none of which is asserted.
