# Vestrace v0.1 — архитектурная спецификация

**Статус:** утверждено для планирования реализации  
**Дата:** 2026-07-31  
**Репозиторий:** `venm1r/vestrace`  
**Продукт:** независимый сервер долговременной памяти и когнитивных активов для AI-агентов

## 1. Краткое описание

Vestrace — локально разворачиваемый Rust-сервис, который принимает события от одного или нескольких AI-агентов, извлекает из них долговременные воспоминания, сохраняет происхождение и историю изменений, выполняет гибридный поиск и формирует компактные context packs под конкретную задачу.

Помимо памяти Vestrace хранит версионируемые определения агентов, навыков и workflow, журналирует внешнее исполнение, ведёт реестр доступных моделей и выбирает модель для каждого шага по требованиям качества, стоимости, задержки, приватности и надёжности.

Vestrace является самостоятельным продуктом и не зависит от StoryOS или другого оркестратора.

> Rust управляет памятью. PostgreSQL хранит память. Внешние модели анализируют и обогащают память.

## 2. Цели v0.1

Vestrace v0.1 должен обеспечивать полный цикл:

```text
событие
→ доказуемая память
→ гибридный поиск
→ context pack
→ улучшенное следующее выполнение
```

Обязательные возможности:

1. Запись сообщений, действий, результатов инструментов, документов, ошибок и execution events.
2. Извлечение candidate memories внешней моделью.
3. Активация, исправление, замещение, истечение и безопасное удаление воспоминаний.
4. Provenance до исходного события, модели, workflow и шага выполнения.
5. Полнотекстовый, векторный, структурированный и графовый поиск.
6. Сбор context pack под заданный токен-бюджет.
7. Хранение агентов, навыков, workflow и истории внешнего исполнения.
8. Реестр моделей и объяснимый выбор модели для задачи или шага workflow.
9. MCP API для агентов и HTTP API для интеграции и администрирования.
10. Локальный запуск через Docker Compose.

## 3. Явно не входит в v0.1

В первую версию не входят:

- собственное исполнение workflow;
- автоматическая декомпозиция произвольной задачи;
- Neo4j в runtime;
- нативный адаптер Anthropic;
- Python-компоненты;
- LightRAG;
- Redis, Kafka, RabbitMQ, Qdrant;
- web-интерфейс;
- OIDC и организации;
- автономное online learning без контроля;
- автоматическое изменение агентов, навыков и workflow на основе опыта;
- распределённый кластер Vestrace.

Архитектура не должна блокировать эти возможности в будущих версиях.

## 4. Технологический стек

- Rust Edition 2024.
- Tokio как async runtime.
- Axum и Tower для HTTP.
- Официальный Rust SDK MCP `rmcp`.
- Serde и Schemars для сериализации и схем.
- SQLx для PostgreSQL и миграций.
- `tracing` для структурированных логов.
- PostgreSQL как единственный источник истины.
- `pgvector` для embeddings.
- PostgreSQL Full Text Search и `pg_trgm` для текстового поиска.
- Docker Compose для локального развёртывания.
- React, TypeScript и Vite зарезервированы для будущего UI, но не входят в v0.1.

AI-инференс никогда не выполняется внутри процесса Vestrace. v0.1 поддерживает только OpenAI-compatible API, включая совместимые локальные серверы.

## 5. Архитектурный стиль

Vestrace реализуется как модульный монолит с одним Rust-проектом и несколькими режимами запуска.

```text
vestrace server   — HTTP API и MCP Streamable HTTP
vestrace worker   — фоновые задания
vestrace mcp      — локальный MCP stdio
vestrace migrate  — миграции
vestrace doctor   — диагностика целостности
vestrace rebuild  — пересборка производных данных
```

Логические слои:

```text
Interfaces
├── HTTP
├── MCP
└── CLI

Application
├── commands
├── queries
├── policies
└── orchestration services

Domain
├── memory
├── events
├── agents
├── skills
├── workflows
├── models
├── routing
├── retrieval
└── security

Infrastructure
├── PostgreSQL
├── AI providers
├── jobs
├── embeddings
└── graph projection ports
```

Domain не зависит от Axum, SQLx, MCP SDK или конкретного AI-провайдера. Infrastructure реализует порты application/domain.

## 6. PostgreSQL как источник истины

Авторитетные данные хранятся в PostgreSQL. Производные данные можно удалить и восстановить.

Авторитетные сущности:

- workspaces;
- principals, roles, capabilities и policies;
- agents и agent revisions;
- skills и skill revisions;
- workflows, workflow revisions, nodes и transitions;
- sessions;
- events и event links;
- memories и memory revisions;
- memory sources, conflicts и scopes;
- model/provider profiles и их revisions;
- model cost profiles, benchmarks и routing policies;
- routing decisions;
- workflow, step, model и tool execution records;
- quality evaluations и human feedback;
- jobs и transactional outbox.

Перестраиваемые данные:

- embeddings;
- search documents;
- summaries;
- context-pack cache;
- агрегированные метрики;
- будущая Neo4j-проекция.

## 7. Доменная модель памяти

### 7.1 Memory и MemoryRevision

`Memory` — стабильная идентичность воспоминания. Содержание не изменяется на месте: каждое исправление создаёт `MemoryRevision`.

Memory содержит:

- стабильный UUID;
- workspace;
- тип;
- статус;
- ссылку на текущую ревизию;
- importance;
- confidence;
- valid_from и valid_until;
- scopes;
- метки чувствительности;
- timestamps.

Ревизия содержит:

- последовательный номер;
- читаемый `content`;
- типизированный `structured` payload, сериализуемый в `jsonb`;
- причину изменения;
- автора;
- время создания.

### 7.2 Типы памяти

- `Fact`;
- `Preference`;
- `Constraint`;
- `Decision`;
- `Task`;
- `Procedure`;
- `Observation`;
- `Outcome`;
- `Summary`.

`Summary` является производной памятью и должна быть пересоздаваемой.

`MemoryKind` определяет допустимый вариант structured payload. Несовместимая пара type/payload отклоняется до записи.

### 7.3 Статусы

```text
Candidate
├── Active
└── Rejected

Active
├── Superseded
├── Expired
└── Deleted
```

Возврат `Superseded` или `Expired` в `Active` не допускается. Восстановление создаёт новую ревизию или новую память.

### 7.4 Гибридное представление

Каждая память сочетает:

- читаемый текст;
- типизированную структуру;
- тип памяти;
- источники;
- временную валидность;
- confidence;
- importance.

Для утверждений используется форма `subject / predicate / value`. Для решений сохраняются choice, rationale и alternatives. Для задач — состояние, assignee и due date. Для процедур — шаги и предусловия.

### 7.5 Scopes

Память может быть одновременно связана с несколькими областями через отдельную relation table:

- workspace;
- project;
- user;
- agent;
- team;
- workflow;
- execution;
- session;
- task;
- global.

`global` в v0.1 означает «доступно во всём текущем workspace». Межпространственная память и совместное использование данных между workspace не поддерживаются.

Одна nullable-owner колонка или свободный JSON для scopes не используются.

### 7.6 Политики записи

Workspace определяет одну из трёх write policies:

- `manual` — любая извлечённая память остаётся Candidate до явного подтверждения;
- `assisted` — система может автоматически активировать низкорисковые записи, остальные оставляет Candidate;
- `automatic` — память активируется при прохождении порогов confidence, source quality, conflict и sensitivity.

Пороговые значения являются версионируемой policy. Constraint, permission, credential-related и конфликтующие записи не активируются автоматически без отдельного разрешения.

### 7.7 Инварианты

1. У Memory существует минимум одна ревизия.
2. Текущая ревизия принадлежит той же Memory.
3. Номера ревизий последовательны и неизменяемы.
4. Изменение содержания всегда создаёт новую ревизию.
5. `valid_until` не раньше `valid_from`.
6. Confidence и importance находятся в диапазоне 0–1.
7. Активная память имеет минимум один источник.
8. Производная память имеет запись derivation.
9. Производные индексы не входят в агрегат Memory.
10. Workspace boundary не может быть расширена scope-значением.

## 8. Cognitive Assets

Агенты, навыки и workflow не являются обычными воспоминаниями. Они образуют отдельный слой версионируемых когнитивных активов.

### 8.1 AgentDefinition

Ревизия агента хранит:

- роль и назначение;
- системные инструкции;
- требования к модели;
- доступные навыки и инструменты;
- разрешения и ограничения;
- memory scopes;
- параметры context pack;
- budget policies.

Агент не может изменять собственные разрешения через agent-facing MCP API.

### 8.2 SkillDefinition

Навык содержит:

- назначение;
- инструкции;
- input и output JSON Schemas;
- разрешения;
- зависимости;
- условия применения;
- примеры;
- версию реализации.

Виды реализации:

- prompt skill;
- MCP tool skill;
- HTTP skill;
- composite skill;
- human skill.

Vestrace хранит спецификацию и историю навыка; исполняемый сервис может находиться отдельно.

### 8.3 WorkflowDefinition

Workflow хранится как типизированный ориентированный граф. Узлы:

- agent;
- skill;
- tool;
- decision;
- parallel;
- join;
- human approval;
- sub-workflow;
- end.

Переходы содержат условия, retry policy, timeout и optional compensation.

В v0.1 Vestrace хранит workflow и журналирует внешнее исполнение, но сам не является workflow runtime.

### 8.4 Execution history

Определение и фактический запуск разделены:

```text
WorkflowDefinition
→ WorkflowExecution
→ StepExecution
→ AgentInvocation / ToolInvocation / ModelExecution
→ ExecutionOutcome
```

Execution history используется для provenance, оценки моделей, анализа навыков и извлечения новых воспоминаний.

## 9. Реестр и маршрутизатор моделей

### 9.1 Model Registry

`ProviderProfile` описывает OpenAI-compatible endpoint, способ аутентификации, locality, health и статус. Секреты не хранятся в базе; сохраняются только ссылки на environment, mounted secrets, keyring или внешний secret store.

`ModelProfile` имеет стабильный UUID и версионируемые revisions. Revision хранит:

- provider и provider model name;
- capabilities;
- specializations;
- context limits;
- locality;
- lifecycle status;
- health metadata;
- дополнительные ограничения.

Capabilities и специализации разделены. Capability отвечает, может ли модель выполнить задачу; specialization — насколько хорошо она предположительно с ней справится.

Стоимость хранится отдельно в `ModelCostProfile` с `valid_from`/`valid_until`. Для remote API учитываются input/output token cost и request cost. Для локальных моделей v0.1 использует настраиваемый `local_compute_weight`, а не притворяется, что локальный запуск бесплатен.

RoutingDecision всегда ссылается на точные revisions model/provider profiles и действовавший cost profile.

### 9.2 Routing policy

Поддерживаемые стратегии v0.1:

- Fixed;
- BestQuality;
- LowestCost;
- LowestLatency;
- Balanced;
- LocalOnly;
- WithinBudget;
- QualityAboveThreshold;
- CustomWeighted.

Политика по умолчанию:

> Сначала обеспечить минимально требуемое качество, затем выбрать наиболее дешёвую допустимую модель с учётом задержки, надёжности, приватности и предпочтения локального выполнения.

### 9.3 Routing process

1. Классифицировать требования задачи.
2. Жёстко отфильтровать модели по capabilities, доступности, context size, privacy и budget.
3. Оценить quality, cost, latency, reliability, locality и историческую успешность.
4. Выбрать модель и fallback chain.
5. Сохранить объяснимый RoutingDecision, включая причины исключения кандидатов.
6. После выполнения связать прогноз с фактической оценкой.

В v0.1 workflow задаёт декомпозицию задачи. Router выбирает модель отдельно для каждого шага. Автоматическая декомпозиция откладывается.

### 9.4 Performance memory

Сырые измерения хранятся в typed execution/evaluation tables:

- task signature;
- input/output size;
- latency;
- token usage;
- estimated cost;
- retries;
- result status;
- deterministic checks;
- human feedback;
- downstream success.

v0.1 использует детерминированные проверки и человеческую оценку как авторитетные quality signals. LLM judge допускается как дополнительный неавторитетный сигнал, но не является обязательным для релиза.

Производные выводы о сильных и слабых сторонах моделей могут сохраняться как `ModelPerformanceMemory`, но не заменяют исходные измерения.

## 10. События и provenance

Vestrace использует гибридный подход: обычные таблицы актуального состояния плюс append-only журнал значимых событий. Полный event sourcing не используется.

### 10.1 Event

Событие содержит:

- workspace;
- namespaced event type;
- actor;
- subject;
- session/execution references;
- payload;
- `occurred_at`, `ingested_at`, `recorded_at`;
- `correlation_id`;
- `causation_id`;
- `idempotency_key`.

Событие после записи не редактируется. Исправление создаёт новое событие.

### 10.2 Actor

Поддерживаемые actor types:

- user;
- agent;
- model;
- workflow;
- system;
- tool;
- external service.

### 10.3 Provenance

`MemorySource` связывает конкретную MemoryRevision с:

- Event;
- Document;
- WorkflowExecution;
- StepExecution;
- ModelExecution;
- ToolResult;
- HumanFeedback;
- другой MemoryRevision;
- ExternalReference.

Роли источника:

- Primary;
- Supporting;
- Contradicting;
- Derived;
- Contextual.

`Derivation` фиксирует метод получения: extraction, summarization, inference, consolidation, conflict resolution, human-authored или import. Она хранит model execution, prompt version, input sources и output revision.

### 10.4 Model и routing provenance

Каждый model execution сохраняет точную версию model profile, provider profile, routing decision, prompt template, параметры, input references, response hash, usage, latency, cost и статус.

Каждый routing decision сохраняет требования, policy version, кандидатов, scores, причины исключения, selected model и fallbacks.

### 10.5 Режимы хранения содержимого

Workspace выбирает retention mode:

- `Full` — сохраняются полные сообщения, prompts, ответы и tool results;
- `Redacted` — содержимое очищается согласно policy до долговременного хранения;
- `MetadataOnly` — сохраняются хеши, типы, участники, временные метки, метрики и ссылки без полного контента.

Стандарт локального v0.1 — `Full`, но security classification и redaction применяются независимо от режима.

## 11. Retrieval и Context Pack

### 11.1 Принцип

Vestrace собирает не самый похожий текст, а минимальный набор актуальных, доказуемых и полезных знаний для конкретной задачи.

### 11.2 RetrievalRequest

Запрос включает:

- query;
- intent;
- workspace и actor;
- task context;
- scopes;
- filters;
- token budget;
- time perspective;
- retrieval policy;
- explanation level.

Основные intents:

- semantic recall;
- current state;
- decision recall;
- timeline;
- task resume;
- procedure lookup;
- user preferences;
- error recovery;
- model selection;
- workflow context;
- exploration.

### 11.3 Pipeline

```text
нормализация запроса
→ intent и требования
→ hard security/scope filters
→ генерация кандидатов
→ Reciprocal Rank Fusion
→ проверка актуальности
→ графовое расширение
→ reranking
→ дедупликация и разрешение конфликтов
→ token-aware context pack
→ объяснение и журнал retrieval
```

Каналы кандидатов:

- exact lookup;
- PostgreSQL FTS;
- `pg_trgm`;
- pgvector;
- structured fields;
- execution history.

RRF используется вместо прямого сложения несопоставимых score.

### 11.4 Время и конфликты

Поддерживаются режимы:

- current;
- as_of;
- timeline;
- all_history.

Current retrieval не возвращает superseded или expired память как актуальный факт. Неразрешённый конфликт возвращается явно и не трактуется как установленное знание.

### 11.5 Graph expansion

В v0.1 граф хранится в PostgreSQL adjacency tables. Разрешённое расширение — глубина 1–2, ограниченный набор edge types и затухание score.

Будущий Neo4j реализует тот же `GraphRepository` и является перестраиваемой проекцией, а не источником истины. Для этого используются стабильные UUID, typed edges, transactional outbox и rebuild projector.

### 11.6 Context Pack

Context pack может включать:

- current state;
- constraints;
- user preferences;
- relevant decisions и rationale;
- procedures и skills;
- open tasks;
- recent events;
- risks и conflicts;
- execution history;
- compact provenance.

Приоритет включения:

1. hard constraints;
2. подтверждённые актуальные факты;
3. критичные решения;
4. незавершённые задачи;
5. релевантные процедуры;
6. поддерживающие детали;
7. недавние события;
8. исторический контекст.

Контекст никогда не превышает заданный token budget. При сжатии используются уровни: полная ревизия, summary, атомарный факт, ссылка на объект.

### 11.7 Объяснимость

Для каждого результата сохраняются:

- каналы обнаружения;
- пройденные фильтры;
- компоненты score;
- причина включения;
- вытесненные дубликаты;
- provenance.

Недоступность embeddings или модельного reranker не блокирует retrieval: используется деградированный FTS/structured/deterministic режим с явным предупреждением.

### 11.8 Кэш и инвалидирование

Кэшируются только производные данные: query embeddings, candidate lists, summaries, graph expansions и context packs. Ключ содержит workspace, query hash, scopes, policy version, embedding space, time perspective и `memory_generation`.

Любое авторитетное изменение, способное повлиять на retrieval, увеличивает соответствующий generation counter. Устаревший context pack не может считаться актуальным после изменения памяти или policy.

## 12. MCP и HTTP API

Application layer общий для обоих интерфейсов. MCP — ограниченная agent-facing поверхность; HTTP — полный integration/admin API.

### 12.1 MCP transports

- stdio для локальных клиентов;
- Streamable HTTP для удалённых клиентов.

### 12.2 Основные MCP tools

- `vestrace_event_record`;
- `vestrace_memory_remember`;
- `vestrace_memory_search`;
- `vestrace_context_build`;
- `vestrace_memory_get`;
- `vestrace_memory_revise`;
- `vestrace_memory_forget`;
- `vestrace_memory_link`;
- `vestrace_timeline_get`;
- `vestrace_models_list`;
- `vestrace_model_route`;
- `vestrace_model_evaluation_record`;
- `vestrace_agent_get`;
- `vestrace_skill_get`;
- `vestrace_workflow_get`;
- `vestrace_workflow_context`;
- `vestrace_execution_start`;
- `vestrace_step_record`;
- `vestrace_execution_complete`;
- `vestrace_operation_get`;
- `vestrace_operation_cancel`.

Cognitive asset management, provider management и hard purge не доступны обычному агенту через MCP.

### 12.3 MCP resources

Read-only URI templates предоставляют memory, context, models, agents, skills, workflows, executions и operations.

### 12.4 Контрактные правила

1. Все внешние write commands принимают idempotency key.
2. Изменение версионируемого объекта принимает expected revision.
3. Один запрос выполняется в одном workspace.
4. Полное удаление доступно только admin HTTP API.
5. Производный вывод имеет provenance.
6. Routing всегда сохраняет объяснение.
7. Долгие действия возвращают operation ID.
8. Degraded success маркируется отдельно.

Предметные ошибки:

## 13. Безопасность и приватность

### 13.1 Модель доступа

Используются роли плюс capability policies. Субъекты:

- user;
- agent;
- service account;
- workflow;
- MCP client;
- system worker.

Модели и инструменты действуют по delegated authority инициатора. Нижележащий субъект не получает больше прав, чем родитель.

Capabilities включают memory, event, context, agent, skill, workflow, execution, model, provider, workspace, audit, export и purge operations.

Политика по умолчанию — deny.

### 13.2 Чувствительность

Уровни:

- Public;
- Internal;
- Confidential;
- Restricted;
- Secret.

Vestrace не является secret store. Секреты хранятся только как references и разрешаются через `SecretResolver`. Объект с classification `Secret` может содержать только ссылку и безопасные метаданные, но не значение секрета.

Право прочитать память и право передать её модели разделены. Перед model invocation выполняются classification, locality check, redaction и policy decision.

### 13.3 Authentication

v0.1 поддерживает:

- local trusted mode для localhost/stdio;
- bearer token mode для HTTP, с хранением только token hash.

OIDC откладывается.

### 13.4 PostgreSQL RLS

Application policies дополняются Row-Level Security. Каждая транзакция устанавливает workspace и principal context. RLS служит вторым уровнем защиты от запросов без scope filter.

### 13.5 Опасные действия

Human approval требуется для hard purge, массовых изменений, изменения разрешений, подключения внешнего provider, передачи Restricted-данных наружу и опасных tools.

### 13.6 Удаление

Операции:

- expire;
- supersede;
- soft delete;
- hard purge.

Hard purge удаляет содержимое, revisions, embeddings, summaries, caches, artifacts и graph projections. Разрешается оставить только минимальный audit факт без удалённого содержимого.

## 14. Фоновые задания и согласованность

v0.1 использует PostgreSQL queue с `FOR UPDATE SKIP LOCKED`, leases, retries, exponential backoff, jitter и dead-letter status.

Типы jobs:

- memory extraction/consolidation/expiry;
- embedding generation/rebuild;
- document import/chunking;
- model health/evaluation/aggregation;
- retrieval summary generation;
- graph projection/rebuild;
- export и purge.

Transactional outbox создаётся в одной транзакции с авторитетным изменением. Производные данные обновляются eventual-consistently.

Повторная обработка безопасна благодаря idempotency keys, content hashes и version keys.

Для внешнего model/tool call существует стабильный operation key. Если процесс завершился после внешнего ответа, но до фиксации результата, запись получает состояние `completion_unknown`; повторный вызов не выполняется автоматически до reconciliation или явной retry policy.

### 16.2 Критические сценарии

- optimistic concurrency: один concurrent revision succeeds, второй получает conflict;
- два worker не выполняют одну leased job одновременно;
- повторный idempotency key не создаёт дубликат;
- старое решение не возвращается как текущее после supersede;
- Restricted data не передаётся remote provider;
- чужой workspace недоступен, включая память с scope `global`;
- context pack не превышает budget;
- fallback работает при недоступности модели;
- удалённая память исчезает из vector search и cache;
- удаление производных данных и rebuild сохраняют логический результат retrieval;
- crash после внешнего ответа приводит к `completion_unknown`, а не к неконтролируемому повторному вызову.

## 17. Критерии готовности v0.1

### Memory

- событие записывается через MCP или HTTP;
- worker создаёт candidate memory;
- write policy активирует или оставляет кандидата;
- provenance и revisions сохраняются;
- correction создаёт новую revision;
- superseded knowledge не выдаётся как current;
- soft delete и hard purge соблюдают права.

### Retrieval

- FTS, vector и structured channels объединяются через RRF;
- workspace/agent scopes изолированы;
- конфликты и дубликаты обрабатываются явно;
- context pack укладывается в budget;
- объяснение доступно для каждого item;
- retrieval работает без embeddings в degraded mode.

### Models

- OpenAI-compatible provider регистрируется;
- model capabilities, cost и limits сохраняются версионированно;
- Balanced router сначала соблюдает quality threshold, затем оптимизирует cost;
- RoutingDecision объясним и сохраняется;
- фактические latency, usage, cost и quality фиксируются;
- fallback работает.

### Cognitive assets

- agent, skill и workflow версионируются;
- skill имеет input/output schemas;
- workflow хранится как graph;
- внешний оркестратор журналирует executions и steps;
- execution result может породить memory;
- агент не изменяет собственные permissions.

### Operations

- `docker compose up` запускает PostgreSQL, server и worker;
- MCP stdio работает локально;
- HTTP и MCP Streamable HTTP работают в server mode;
- jobs переживают restart;
- `vestrace doctor` обнаруживает нарушения;
- производные данные полностью пересобираются;
- логи не содержат секреты.

## 19. Архитектурные инварианты верхнего уровня

1. PostgreSQL — единственный источник истины v0.1.
2. Neo4j в будущем — только перестраиваемая проекция.
3. AI-инференс выполняется только внешними providers.
4. MCP и HTTP используют одинаковое application core.
5. Memory content изменяется только через revisions.
6. Активная память имеет provenance.
7. Производный вывод имеет derivation.
8. Все внешние write commands идемпотентны.
9. Все versioned updates используют optimistic concurrency.
10. Агент не повышает собственные права.
11. Чтение памяти и передача её модели — разные разрешения.
12. Hard constraints и актуальность важнее semantic similarity.
13. Router объясняет каждый выбор модели.
14. Авторитетные данные сохраняются транзакционно.
15. Производные данные можно удалить и пересоздать.
16. `global` scope никогда не пересекает границу workspace.

## 20. Итог

Vestrace v0.1 — это независимый Rust-based memory server и реестр когнитивных активов с доказуемой историей, гибридным retrieval, безопасным context building и объяснимой маршрутизацией моделей.

Первая версия не пытается стать полноценным автономным orchestration runtime. Она создаёт надёжный фундамент: хранит знания, опыт и определения работы, принимает execution logs от внешних оркестраторов и использует накопленные результаты для улучшения последующих задач.
