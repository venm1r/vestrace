# Vestrace v1.0 Full Product, AG-UI, and A2A Design

**Date:** 2026-08-25
**Status:** architecture profile and external OpenAI-compatible provider amendment approved; external-corpus/reconstruction amendment awaiting independent review and final operator approval
**Deployment profile:** local Docker Compose installation, one workspace, one operator
**Scope:** complete the existing eleven-item console, OpenAI-compatible model-provider configuration, AG-UI, and A2A as one release-qualified product

## 1. Purpose

Vestrace v1.0 is a usable local product, not a collection of screens over partially wired APIs. Every visible console action must reach a real application service, persist the authoritative result, execute required background work, and present the observed outcome or a truthful failure. Empty states are valid; enabled controls that simulate success, write inert configuration, or end at a catalogue row are not.

This document fixes the product and protocol architecture that implementation planning must follow. It does not claim that the described behavior is currently implemented, does not itself qualify v1.0, and does not authorize a release claim. Implementation begins only after this document is reviewed and a separate implementation plan receives adversarial review.

## 2. Authorities and pinned profiles

The design inherits the repository's architectural laws:

- canonical state is distinct from projections;
- Vestrace has one execution boundary, the canonical `Run` engine;
- protocol adapters and remote systems cannot become a second source of execution authority;
- capability plus policy determines authority;
- ambiguous external outcomes remain explicit instead of being guessed into success or failure;
- observations and imported content are evidence before they may become cognition;
- v1.0 requires persisted qualification evidence, not feature-count assertions.

The console's presentation and responsive layout remain governed by [`2026-08-25-console-interface-redesign-design.md`](2026-08-25-console-interface-redesign-design.md). That document owns visual composition. Its non-goals constrain the already bounded visual-only slice; they do not prohibit later reviewed v1 backend work. This document owns end-to-end behavior, protocol semantics, persistence, and release acceptance whenever the scopes differ.

The protocol profiles are deliberately exact:

- AG-UI uses `@ag-ui/core` `0.0.58` and `@ag-ui/client` `0.0.58`. The lockfile must use exact versions, not ranges. A committed protocol lock record must also contain each resolved npm integrity value, the upstream source commit reported by package provenance, and a SHA-256 digest of the extracted runtime schemas used by the conformance tests. An upgrade is a reviewed protocol change, not an incidental dependency refresh.
- A2A uses specification release `v1.0.1`, release commit `3303592`, and wire header version `1.0`. Vestrace advertises one fully qualified JSON-RPC 2.0 over HTTP/SSE interface. The adapter uses the official Rust SDK crates `a2a-lf` `0.3.0`, `a2a-client-lf` `0.2.1`, and `a2a-server-lf` `0.4.1`; exact registry checksums and the corresponding upstream source commits belong in the protocol lock record. SDK types remain behind the adapter, and Vestrace contract/TCK evidence remains authoritative if an SDK helper is incomplete.
- OpenAI-compatible qualification uses the committed `schemas/openai-compatible/openai-chat-completions-v1-q1.json` manifest. Its exact bytes, fixture digests, and SHA-256 digest are pinned release inputs in the same protocol lock; a changed probe, oracle, bound, order, or fixture is a reviewed profile version rather than an in-place reinterpretation.

“Full AG-UI” means the entire pinned AG-UI request, event, state, tool, multimedia, and interrupt profile described below. “Full A2A” means both server and client roles implement the complete advertised v1.0 core profile. It does not mean claiming optional bindings or capabilities that Vestrace has not qualified.

## 3. Product boundary and non-goals

The supported v1.0 installation consists of:

- one PostgreSQL database;
- one migrator, HTTP server, and worker deployment under Docker Compose; the worker owns the trigger-scheduler loop rather than requiring a fourth application service;
- one host safety supervisor outside the product containers, with independently persisted witness, append-only journal, signing-key record, material/comparison-key vault, immutable installation-fingerprint authority, archive controller, and activation-lease authority; these are distributed-systems-grade failure domains even though v1 is operated on one machine;
- one same-origin web console served on loopback;
- one pre-provisioned local workspace and operator principal;
- LM Studio reachable through its OpenAI-compatible endpoint, with operator-facing `http://localhost:12345/v1` as the supported default;
- any number of operator-created remote OpenAI-compatible API Connections that pass the v1 transport and capability qualification profile;
- optional outbound A2A connections explicitly created by the operator.

All published container ports bind to loopback by default. A non-loopback bind is a conscious configuration change that fails readiness unless authentication, trusted origins, and public base URLs are explicitly configured.

`localhost` has two explicit meanings in this deployment. The browser/operator sees `http://localhost:12345/v1`; server and worker containers resolve that one `LMStudioLocal` Connection through the Compose host bridge as `http://host.docker.internal:12345/v1`, with `host-gateway` mapping where the engine requires it. The logical URL and resolved runtime URL are both stored in configuration evidence, and no general URL is silently rewritten. Installation readiness performs a real `/models` request from both application containers and fails with instructions if LM Studio is not listening on an address reachable through the host bridge. The host bridge remains a `RemoteProvider` destination for data-policy purposes even though it reaches the same physical machine.

The following are not v1.0 goals:

- multi-workspace administration or cross-workspace sharing UI;
- multi-operator RBAC, invitations, teams, or cloud control-plane provisioning;
- hosted SaaS deployment;
- A2A gRPC, HTTP+JSON/REST, push notifications, or an extended Agent Card;
- AG-UI `RAW` events, opaque encrypted reasoning, or disclosure of hidden chain-of-thought;
- vendor-specific model API dialects that require deployment-specific paths, query credentials, arbitrary header templates, or an implicit Responses-API fallback; such a dialect requires a separately named and qualified adapter profile;
- automatic trust elevation from protocol responses, model output, or imported artifacts;
- model training or fine-tuning.

Unsupported A2A capabilities are absent from the Agent Card and use their pinned wire errors. Push-configuration methods return `PushNotificationNotSupportedError`; `GetExtendedAgentCard` returns `UnsupportedOperationError`; REST and gRPC are not advertised or mounted. This is a complete, truthful protocol profile, not a placeholder for a promised feature.

## 4. Definition of end-to-end functionality

A console feature is complete only when all of these are true:

1. Its form or action validates input and invokes a typed HTTP contract.
2. Authorization is checked through the same default-deny route authority as every other governed request.
3. The command and its audit record commit atomically, with an idempotency or optimistic-concurrency contract where repetition or races are possible.
4. Required work is durably queued and executed by the worker; a catalogue insert alone is not completion.
5. The resulting canonical state survives server, worker, and browser restarts.
6. List and detail APIs expose pagination, stable ordering, and visible error/empty/loading states.
7. The UI reads the persisted outcome and does not infer success from a click, an expected action, or a locally updated draft.
8. Focused tests prove the behavior fails before the implementation and passes afterward; runtime qualification covers the composed path.

An unavailable dependency produces an explicit failed, paused, or unknown outcome with actionable diagnostics. It never produces a canned “connected”, “saved”, “completed”, or “healthy” response.

## 5. One execution engine with protocol adapters

AG-UI and A2A are anti-corruption adapters around the existing Vestrace execution model. They do not define parallel Run, Step, Event, Artifact, policy, or audit stores.

```text
Browser / AG-UI client              Remote A2A client
          |                                  |
          v                                  v
  AG-UI HTTP/SSE adapter              A2A server adapter
          |                                  |
          +----------- Interaction services-+
                              |
                              v
                Canonical Run / Step / Event engine
                              |
                 policy + outbox + work queue
                              |
              +---------------+----------------+
              v                                v
    model/tool adapter boundary          A2A client adapter
        |                 |                      |
        v                 v                      v
   LM Studio       remote OpenAI API      Remote A2A agent
```

The execution plane is supervised by a logically distributed safety/control plane whose authorities do not collapse into PostgreSQL:

```text
Compose product plane                     Host safety/control plane
---------------------                     -------------------------
server / worker / migrator  <--- permits/receipts --->  supervisor
          |                                               |
          v                         +---------------------+--------------------+
      PostgreSQL                    v                     v                    v
          |                    monotonic witness   signed safety journal   key vault
          v                                               |                    |
   WAL archive producer  <--- guarded heads/holds --------+----------> archive store
```

These are independent persistence and fencing authorities, not necessarily separately networked microservices in v1. They use distributed-systems semantics—monotonic witness state, generation fencing, leases, CAS, append-only receipts, idempotent reconciliation, and fail-closed continuity—while remaining installable and operable on one workstation.

Logical ownership is split as follows:

| Component | Responsibility | Forbidden responsibility |
| --- | --- | --- |
| Protocol-neutral interaction services | Threads, messages, human requests, continuation rules, binding commands | AG-UI or A2A wire DTOs |
| AG-UI adapter | Pinned schema validation, HTTP/SSE transport, event projection, replay | Canonical execution state or policy decisions |
| A2A adapter | Agent Card, JSON-RPC/SSE binding, A2A client transport, task projection | Treating a remote Task as local authority |
| Model binding resolver | Resolve the snapshotted model and Connection revisions into one qualified leaf adapter and exact egress evidence | Choosing a provider by model name, process-wide environment, or mutable UI state |
| Run engine | Run/Step lifecycle, checkpoints, cancellation, terminal state | Protocol-specific identifiers as primary keys |
| Worker | Model/tool/remote-agent execution and durable receipts | Unrecorded external effects |
| PostgreSQL infrastructure | RLS-scoped repositories, outbox, idempotency, ordered event storage | Reconstructing missing authority from a projection |
| Host safety supervisor | Generation permits, restore/cutover orchestration, reconciliation, archive/hold control, witnessed receipts | Ordinary product commands or hidden success inference |
| Witness/journal/key/archive authorities | Monotonic lineage, append-only safety evidence, create-only or erasure-bound key custody, authenticated backup objects | Product-state mutation or trust in restored PostgreSQL alone |
| Console | Operator workflows and protocol client behavior | Fabricated state or direct database authority |

The implementation plan may choose final crate boundaries, but protocol DTOs must remain confined to adapter crates or adapter modules. Domain, application, and persistence APIs use Vestrace types.

## 6. Canonical product model

### 6.1 Published agents and executable snapshots

An `Agent` is a stable operator-managed identity with a mutable draft. Publishing creates an immutable `AgentRevision`. A revision includes the actual system instruction, selected model binding, sampling and context limits, allowed registered tools, artifact/media policy, capabilities, and protocol metadata. Editing a published agent creates a new draft and later a new revision; it never rewrites a revision used by an existing Run.

Every executable Run stores an immutable runtime snapshot referencing the exact `AgentRevision`, complete `ModelBindingSnapshot` configuration/qualification/auth-binding-XOR tuple, workflow revision when applicable, effective capability grant, and protocol binding that started it. It copies no credential material. The worker executes that snapshot. Changing Models, Connections, credential rotation, Agents, Workflows, or Settings affects future Runs only unless a setting is explicitly documented as live and the event applying it is recorded; credential revocation and live authorization/policy denial remain immediate barriers to a later dispatch.

Canonical Run/Step events are append-only structural facts. They may contain opaque content identities/references, erasure-bound commitment values, padded size classes, safe media classes, result classifications, and lifecycle metadata, but never an unkeyed content digest, exact plaintext byte count, prompt/model text, state/context JSON, tool arguments/results, artifact bytes, protocol payload bytes, or any other retention-governed content. Runtime/completion content is stored in referenced message/state/context/artifact/protocol typed maps; tombstoning that material leaves the Run event truthful and non-sensitive after the commitment key is erased.

The snapshotted capability grant is provenance and an upper bound, not a lease that defeats later revocation. Immediately before every model, tool, remote-agent, artifact-transfer, credential-use, or other external dispatch, the shared authorization authority re-evaluates the live principal, capability/grant expiry and revocation, immutable snapshot ceiling, exact target, sensitivity, and current policy. A newly granted capability cannot broaden an already accepted Run beyond its snapshot, while a revoked, expired, or newly denied capability stops the pending effect. The denial and safe reason are audited, but no `Authorized` decision or dispatch-started evidence is appended and the effect is not invoked.

A Run is created atomically with at least one executable Step. The public create path cannot create an empty Run that waits forever. A failure to compile the requested agent or workflow creates no Run and returns a validation error.

Each canonical `Step` owns immutable ordinal `StepAttempt` children. Ordinal zero is its original attempt; any successor names its immutable predecessor and never rewrites it. Database authority permits at most one nonterminal active attempt per Step and at most one acknowledged successor for a recovered-`Unknown` predecessor effect. Attempt outcome remains derived only from its external-effect lifecycle and receipt/reconciliation evidence: a safe retry is a distinct next attempt only when `retry-only-when-safe` has a definite safe basis, while an ambiguous provider `Unknown` can have only the separately authorized duplicate-risk successor described in section 6.4. That successor leaves the original `Unknown` effect/outcome intact, carries its own intent/effect/MRE identity, and may not be scheduled or created from `Dispatching`.

### 6.2 Interaction model

The protocol-neutral interaction layer owns:

- `InteractionThread`: workspace-scoped conversation identity and monotonically ordered message sequence;
- `InteractionMessage`: immutable role/order/provenance envelope, created time, retention-governed typed-parts payload reference and erasure-bound commitment, and optional artifact references;
- `HumanRequest`: durable request for approval, confirmation, authentication, or structured input;
- `HumanResponse`: immutable response correlated to a request, with schema-validation result and actor;
- `ProtocolBinding`: mapping among installation-keyed external protocol identifiers, a thread, a local Run, and an erasure-bound request-comparison fingerprint;
- `ProtocolProjectionEvent`: a durable ordinal structural envelope with a retention-governed payload reference/erasure-bound commitment, safe event kind, and replay metadata;
- `ProtocolDeliveryCursor`: durable historical evidence of the last acknowledged or replayed projection ordinal for a scoped consumer;
- `ProtocolDeliveryLease`: the bounded active delivery/replay range whose unexpired owner temporarily protects a retained prefix.

External `threadId`, `runId`, `taskId`, `contextId`, `messageId`, and JSON-RPC request IDs are untrusted strings. They are length-bounded, normalized only where the upstream contract permits, transformed with the immutable per-installation `InstallationFingerprintKey`, scoped by workspace/principal/protocol/endpoint, and never used as local database authority. This stable fingerprint is only a uniqueness index over identifiers; it never hashes a prompt, message body, Context value, tool result, webhook body, or other retention-governed content.

### 6.3 Remote agent invocation

Outbound A2A is represented by a durable `RemoteAgentInvocation` owned by one canonical Run Step. Its lifecycle distinguishes:

```text
Prepared -> Dispatching -> Submitted/Working
                         -> InputRequired/AuthRequired
                         -> Succeeded/Failed/Rejected/Cancelled
                         -> Unknown -> Reconciling -> observed outcome
```

The record contains the connection revision, public remote Agent Card digest, local message ID, remote context/task IDs when observed, erasure-bound request-comparison fingerprint identity, attempt ordinal, dispatch timestamps, receipts, and reconciliation evidence. The remote Task is evidence about the Step; it is never the local Run itself.

### 6.4 OpenAI-compatible Connections, models, and provider attempts

`NoAuthBindingRevision` is the single immutable no-auth binding revision: it is one-to-one with a `ConnectionRevision` whose closed auth mode is `None`, and is created atomically with that revision. It names only workspace, ConnectionId, ConnectionRevisionId, and proof of auth mode `None`; it contains no CredentialSlotId, CredentialRevision, CredentialActivationGuard, credential lease/material, or secret, and is neither routing, authentication, nor qualification authority. An auth-required ConnectionRevision cannot own one. Every no-auth acceptance or probe names this exact binding and revalidates it under the ConnectionExecutionGuard; it never fabricates a credential identity.

Every `QualificationJob` owns exactly one immutable `QualificationTargetBinding`, the typed target for its ModelsList, chat, and Embeddings probes. It is a strict XOR: the credential branch names the exact CredentialRevision and its slot/guard lineage in its permitted Candidate/Active state under the existing contract; the no-auth branch names the exact `NoAuthBindingRevision` and has no CredentialSlotId, CredentialRevision, CredentialActivationGuard, credential lease, material, or secret. The binding is not routing, authentication, or qualification authority. ConnectionExecutionGuard is always first; only the credential branch then takes its exact CredentialActivationGuard, while the no-auth branch stops at ConnectionExecutionGuard and revalidates the current immutable binding/configuration/qualification and absence of credential reference. q1 ordinal 90, its Embeddings ModelRequestEvidence, and dispatch cite this same binding; ConnectionQualificationRevision and ModelQualificationRevision provenance cite the same branch rather than reinterpreting it.

Every stable `Connection` identity atomically creates exactly one permanent `ConnectionExecutionGuard` keyed by `(workspace, ConnectionId)` before any ConnectionRevision, NoAuthBindingRevision, CredentialSlot reservation, qualification, model snapshot, or provider work. It is never deleted or reused, stores no secret, and is serialization only—not routing, default, authentication, credential, or qualification authority. Every Connection configuration/current-revision or auth-mode/no-auth-binding change, qualification publication/effective-pointer CAS, model or EmbeddingJob snapshot acceptance, transition planning/activation/barrier supersession/classification, CredentialActivationGuard creation/slot binding/rotation/abandon/revoke, and final dispatch first takes it. The canonical order is `ConnectionExecutionGuard -> optional CredentialActivationGuard(s) in canonical slot order -> exact EmbeddingSpaceKey transition/corpus guards -> predecessor job/effect -> barrier lineage -> batch/recipe mappings -> existing lower-level material rows`. A credential-backed operation next takes its exact `CredentialActivationGuard(workspace, ConnectionId, CredentialSlotId)`; a no-auth operation has no CredentialSlotId or credential reference, takes no sentinel/fabricated credential guard, and instead revalidates the immutable exact `NoAuthBindingRevision`, current ConnectionRevision/qualification/configuration, and absence of a credential reference while holding `ConnectionExecutionGuard`.

`Connection` is the stable operator-owned identity for either `LMStudioLocal`, `OpenAiChatCompletionsV1`, or `A2ARemote`. Creating or editing executable configuration creates an immutable `ConnectionRevision`; enabled/disabled/archive state and its current revision remain on the stable aggregate under compare-and-swap. An OpenAI-compatible Connection revision contains configuration only: normalized logical base URL, adapter profile, closed authentication mode, stable credential-slot reference when authentication is required, transport policy, and request/response/time bounds. It never contains mutable health, capability, or admission claims. Live concurrency, request-rate, queue-wait, and provider-throttle behavior belongs to the separately versioned stable-Connection admission authority in section 6.4.2.

`OpenAiChatCompletionsV1` owns exactly `GET /models` and `POST /chat/completions`; `POST /embeddings` is enabled as a separately qualified capability. A configured base URL may contain a fixed path prefix such as `/v1`, but it cannot contain user information, a query, or a fragment, and the adapter owns endpoint joining. The only v1 auth variants are `None`, `Bearer`, `ApiKey` (the exact `api-key` header), and `XApiKey` (the exact `x-api-key` header), compared case-insensitively but emitted canonically by the adapter. `None` forbids a credential reference; every other variant requires one. No caller supplies a header name. `Host`, `Cookie`, hop-by-hop, proxy, forwarding, and query credentials are forbidden. The generic profile neither calls the Responses API nor silently translates a vendor-specific deployment or API-version convention.

`Model` is a stable operator-facing identity. Each immutable `ModelRevision` contains configuration only: one exact `ConnectionRevision`, exact upstream wire model ID, kind (`chat` or `embedding`), and optional operator-supplied context/pricing metadata with provenance. It does not contain mutable probe results. Pricing, context window, rate limits, and usage are `provider_observed`, `operator_supplied`, or `unknown`; absence is never represented as zero.

Probing is a durable command, not a mutation of either configuration revision. A `QualificationJob` targets exact Connection, Model when applicable, immutable `QualificationTargetBinding`, and probe-profile revisions. It records append-only `Requested -> Running -> Succeeded | FailedDefinite | InconclusiveUnknown | Cancelled` transitions plus the external-effect IDs for every probe. All four outcomes are terminal job states; `InconclusiveUnknown` is terminal only for scheduler/lifecycle purposes and never claims a definite provider outcome. The success transaction revalidates every required terminal oracle, creates one immutable `ConnectionQualificationRevision` or `ModelQualificationRevision`, applies either the ordinary effective-pointer finalizer or the embedding-space-transition rule below, and appends `Succeeded`.

Holding the permanent `ConnectionExecutionGuard` and, only for a credential-bound tuple, its exact `CredentialActivationGuard`, the generic finalizer may compare-and-swap an effective qualification pointer only when the targeted configuration is still current and either the qualification names the exact current `Active` CredentialRevision at the slot's expected version or both the configuration and qualification name the exact current `NoAuthBindingRevision` for auth mode `None`. A Candidate-bound result is stored non-effective until the first-activation or staged-rotation transaction in section 11.4 revalidates and publishes it; those are the only paths that may make Candidate evidence effective. A successful embedding requalification with a live old-space corpus instead follows the explicitly guarded transition rule below and remains non-effective until its whole corpus handoff activates. A late result for a changed configuration, retired/revoked credential, changed slot version, or Candidate outside that activation transaction remains immutable non-effective evidence and cannot overwrite a current pointer. Requalification creates a new qualification revision, never a new configuration revision. Each qualification records `qualified_at`, `valid_until`, profile version, exact evidence IDs and digests, observed endpoint/model identity, and its capability matrix.

A `ConnectionQualificationRevision` identifies one exact ConnectionRevision, immutable `QualificationTargetBinding` branch, auth mode, adapter/profile version, transport/TLS observation, and canonical sorted-model discovery digest. A `ModelQualificationRevision` identifies one exact ModelRevision, ConnectionRevision, and the same immutable QualificationTargetBinding branch plus probe profile; it cites the Connection qualification used by the job as provenance. A later refreshed Connection qualification is compatible with that Model qualification only when the configuration, credential, adapter/profile, normalized scheme/host/port/base-path authority, and discovered wire-model membership still match; a normal WebPKI certificate renewal or permitted public peer change is new evidence, not a different endpoint identity. It need not reuse the earlier Connection qualification ID. Qualification IDs are content-linked provenance, not mutable health flags; effective/current pointers are CAS-controlled projections and can be rebuilt from immutable records.

For an embedding Model with a live current-space corpus, a successful refreshed `ModelQualificationRevision` is stored non-effective and, in the same guarded qualification-finalizer transaction, creates one durable `EmbeddingSpaceTransition`. The plan fixes the exact old effective qualification, old `EmbeddingSpaceKey`, old corpus revision and projection-ordinal/member-count watermark, exact captured old live projection recipe set, exact new qualification/new `EmbeddingSpaceKey`, and independently exact source and target auth-binding branches: each is the structural strict XOR of an exact CredentialRevision with its slot/guard lineage or an exact NoAuthBindingRevision, with its ConnectionRevision, qualification, adapter/profile provenance. Source and target branches may differ; neither may contain a sentinel or fabricated credential. This is plan provenance, not a routing, qualification, or authentication authority. The plan also fixes transition version and restricted derivation scope. Its closed lifecycle is `Planned -> Rebuilding -> ReadyToActivate -> Activated | Stale | Failed`; immutable transition observations explain every retry, stale reason, blocker, and terminal result. The plan is the only authority from which a transition snapshot may be instantiated: it owns no snapshot row. Every initial transition-batch `EmbeddingJob`, and every acknowledged same-batch successor, instead owns its own fresh immutable ordinary `ModelBindingSnapshot` row one-to-one with that job; composite foreign keys constrain it to the exact transition ID/version, `TransitionBatchId`, ordered recipe set, source/target auth-binding XORs with configuration/qualification/adapter provenance, target space, and plan. That sole snapshot type is transition-scoped and usable only by the plan's fixed rebuild jobs; it is neither a q1 target, a default, nor general routing authority. Ordinary retrieval and work continue only on the old effective, current, unexpired space while the transition builds; old and new vectors never mix. If the old corpus has no Live projections, the same guard may fast-path a zero-member Ready generation and CAS the effective qualification and retrieval-active space together.

At planning under the old-space/corpus guard, an opaque immutable `EmbeddingTransitionProjectionRecipeId` is created for each captured old live `EmbeddingProjectionEntry`; it is an identity, never a content hash, fingerprint, or digest. Each recipe fixes its transition/version; exact old `EmbeddingSpaceKey`; exact old projection identity including source `EmbeddingJobId`, input ordinal, and space-local projection ordinal; exact ordered source-dependency rows with dependency ordinals and `ContentMaterialId`s; exact target ModelRevision, ModelQualificationRevision, EmbeddingSpaceKey, and request-shape revision; and immutable target assignment of the sole logical `TransitionBatchId` cause and target input ordinal; it never fixes a physical `EmbeddingJobId`. Every named source dependency must remain `Live`. Repeated old projections with identical dependency sets are distinct recipes, shared sources create every affected recipe, and multi-source dependency order is preserved. A `TransitionBatch` persists its ordered recipe list and exact wire `input` order before any `Dispatching`; regrouping or reordering after plan creation is forbidden. Its `TransitionBatchId` is the sole immutable logical batch cause. Every initial job, same-version retry, and carried retry is instead a fresh physical `EmbeddingJob` attempt with no physical-ID reuse; composite foreign keys bind that attempt to the exact transition/version, immutable `TransitionBatchId`, ordered recipe list, and target tuple. A retry may consume only its fixed logical batch cause and ordered recipe list through its governed successor edge.

For a nonempty transition, durable rebuild `EmbeddingJobs` consume only their immutable `TransitionBatch` recipe lists and populate only the exact new space. A target transition `EmbeddingProjectionEntry` names exactly one recipe. Foreign keys and uniqueness require exactly one satisfier for each recipe across its whole physical-attempt lineage: either the actual `Succeeded` physical attempt job/input/projection/derived-MaterialId foreign-key tuple, or one explicit exact `SatisfiedExisting` recipe-to-prior-Live-projection lineage row; each target transition entry names exactly one recipe. Failed, Cancelled, and InconclusiveUnknown attempts are immutable history but cannot satisfy a recipe, and no physical job ID may be reused as a satisfier. Its response index must equal the planned target input ordinal. The builder/rebuilder captures the old corpus revision, projection watermark, and recipe set; it CAS-publishes a new-space `Ready` generation only after the exact bijection holds: every captured still-required old live recipe has exactly one `Live` target projection in the exact target space, and no target transition projection is duplicate, omitted, unplanned, or in a different batch/order. The target corpus revision, projection/member count, and Ready generation must match that same recipe set. One guarded activation transaction takes `ConnectionExecutionGuard -> every exact involved CredentialActivationGuard/slot in canonical slot order -> exact source/target space guards`, then requires the old qualification/current pointer, old corpus revision and recipe set, the exact source/target auth-binding XOR/configuration/qualification lawfulness, and new-space bijection/completeness/Ready generation all still match before it CASes the effective qualification and retrieval-active space together. It acquires zero CredentialActivationGuards when both branches are no-auth, one when exactly one unique credential slot is involved, and every distinct involved guard exactly once in canonical slot order otherwise; for each credential-backed source/target branch it revalidates exact lineage, slot/version, required Candidate/Active lifecycle state, and absence of CredentialMaterialErasurePrepared, Destroyed, or revocation that forbids activation; it relies only on persisted terminal rebuild results/bijection/readiness, never a provider-effect lease. A no-auth branch remains its exact NoAuthBindingRevision with no credential lease, guard, material, or header. No transition-wide credential lease exists. Addition or erasure, a source dependency change, expiry, or another corpus mutation makes the version `Stale`, records the exact recipe mismatch, and deterministically creates/catches up through a later version; it never partially switches. A later version may mark a prior target projection `SatisfiedExisting` only through exact recipe-to-recipe/target-entry lineage and rechecked `Live` source and target predicates; additions receive new recipes, removed recipes cease to be target requirements, dependent vectors follow the existing erasure rules, and no content-equality/hash oracle exists. If the old qualification expires before activation, new retrieval acceptance fails visibly as `qualification-transition-not-ready`; it neither uses expired evidence nor falls back or mixes spaces. Proactive refresh, scheduling, Models visibility, and readiness report that state as a failed transition rather than a routine successful refresh. Restart resumes only the same durable plan, recipes, batches, jobs, and guarded CAS.

The preceding handoff is the ordinary refresh rule for an already Active/no-auth tuple. For a candidate-bound embedding qualification created during staged rotation, its successful finalizer takes `ConnectionExecutionGuard` first and then the exact permanent `CredentialActivationGuard`, and creates a `rotation_staged` `EmbeddingSpaceTransition` instead of publishing that qualification over a live old space. It fixes the old effective Active qualification/space/corpus watermark, exact candidate qualification/target space, and the restricted snapshot-derivation tuple under that guard. Each transition-batch job owns its own plan-derived transition-scoped ordinary `ModelBindingSnapshot` and may use only that bound/finalized, fully qualified Candidate for its exact rebuild effect through the ordinary live authorization, model-data-policy, credential-lease, admission, owner/deadline, and `Dispatching` path; Candidate remains unavailable to defaults, ordinary routing, or any other job. First activation with no old space, and an empty old corpus, may use the same guarded fast path. The transition has no new routing type and never mixes spaces.

`ModelBindingSnapshot` is the sole model-routing authority. Any durable model-effect cause atomically resolves and pins the exact `ConnectionRevision`, current unexpired `ConnectionQualificationRevision`, `ModelRevision`, current unexpired `ModelQualificationRevision`, and exact CredentialRevision or `NoAuthBindingRevision` selected by its immutable binding under the permanent `ConnectionExecutionGuard` followed only when credential-backed by the exact `CredentialActivationGuard` in canonical slot order, then slot-version, current-qualification, live authorization/policy, and binding checks. A no-auth tuple has no CredentialSlotId or fabricated guard and instead revalidates its exact immutable `NoAuthBindingRevision`, current ConnectionRevision/qualification/configuration, and absence of every credential reference while holding `ConnectionExecutionGuard`. All tuple members share workspace, adapter profile, endpoint authority, exact auth-binding branch, and wire model identity. A Run owns its snapshot through `RunSnapshot`; an ordinary non-Run production embedding operation owns it through its durable `EmbeddingJob`; the sole exception is a transition-scoped, job-owned snapshot instantiated only from the guarded handoff plan's fixed derivation scope and usable only by that exact rebuild job. Thus either commits a valid current tuple before rotation, or waits and pins the new valid tuple; neither can pin a retired credential merely read earlier. No second snapshot type, probe target, or other routing authority exists.

#### 6.4.2 Durable Connection admission and provider throttling

`ConnectionAdmissionPolicy` is the stable live safety authority for one `ConnectionId`; each edit creates an immutable `ConnectionAdmissionPolicyRevision` and compare-and-swaps its active pointer with Audit in the same transaction. Policy edits take the same per-Connection admission-state row lock as dispatch, and a dispatch reads the active revision only after taking that lock, so a limit change is ordered before or after one admission rather than racing it. It is deliberately separate from `ConnectionRevision`, so parallel configuration revisions and credential rotations share one admission key and cannot multiply capacity. Every Run call, EmbeddingJob call, and Connection/Model probe records and obeys the active admission-policy revision selected immediately before dispatch. The v1 fields are exact:

- `max_in_flight`: integer 1..64, default 4;
- `requests_per_60_seconds`: integer 1..60000, default 60;
- `queue_wait_timeout_seconds`: integer 1..300, default 30;
- `provider_throttle_cap_seconds`: integer 1..900, default 900.

The generic v1 profile has no tokens-per-minute authority because provider usage may be absent. Token/context bounds remain Model/Run constraints and missing usage remains `unknown`.

PostgreSQL owns admission. One stable per-Connection `ConnectionAdmissionState` row serializes decisions under row lock. After acquiring that lock, the transaction samples the database clock once and counts immutable `ConnectionDispatchAdmission` records for the stable Connection whose `admitted_at` lies in the half-open rolling interval `(sampled_at - 60 seconds, sampled_at]`; a new dispatch is allowed only when that count is strictly below `requests_per_60_seconds`. The same transaction appends the external-effect-keyed admission record with that sampled time and exact policy revision, acquires its durable concurrency lease, and appends `Dispatching` with owner/deadline atomically before adapter invocation. For authenticated effects this is the one credential/lease/admission/`Dispatching` transaction defined above, not a later second transaction. Thus two concurrent transactions, restart, and a UTC clock-minute boundary cannot over-admit the rolling limit.

Without capacity, no admission record, concurrency lease, `Dispatching` transition, or provider bytes exist. The first refusal stores `admission_wait_started_at` and a non-extendable `queue_deadline` computed from that attempt's active policy; later attempts use the latest live capacity/throttle policy but never move that deadline later. The work remains visibly `waiting_for_provider_capacity` until capacity arrives or the stored deadline produces a definite pre-dispatch failure. For an EmbeddingJob, that failure is the guarded safe-refusal evidence plus `FailedDefinite`/lease release from section 6.4, with any provisional output intents reconciled only to `Abandoned`. Probes, Runs, and EmbeddingJobs compete through the same authority.

A concurrency lease is released by a definite provider receipt or by the one-winner lost-dispatch adoption that appends `Unknown`; a crash leaves it held until the shared deadline/owner recovery contract permits that decision. `Unknown` is never retried. A valid HTTP 429 `Retry-After` delta-seconds or HTTP-date is bounded by `provider_throttle_cap_seconds` and advances a durable Connection-level `not_before`; an absent, invalid, past, or overflowing value does not invent a delay. The 429 receipt is terminal for that effect, releases concurrency, and never auto-retries it. New dispatches wait behind `not_before` under the same visible queue timeout.

Admission state survives server and worker restart. Lowering a policy limit never cancels in-flight work but blocks new dispatches until current occupancy and the rolling count satisfy the new bound; raising a limit affects only the next admission decision. Dispatch-admission records are evidence and are never decremented or shifted when a policy changes. Each effect retains the exact policy revision that admitted it. PostgreSQL/fault tests cover concurrent calls at both 60-second boundaries, probes competing with Runs, restart, policy change with occupied leases, exact inclusion/exclusion at 60 seconds, queue timeout, 429 with every `Retry-After` form, lost dispatch, one-winner release, and refusal to release or retry an `Unknown` twice.

### 6.5 Canonical content retention

`WorkspaceRetentionPolicy` is a stable aggregate with immutable revisions and an expected-version compare-and-swap active pointer. The only operator-set content fields in v1 are `mode = KeepForever | DeleteAfterDays` and `completed_content_days`, which must be null for `KeepForever` and an integer 0..3650 for `DeleteAfterDays`; zero means immediately after every protection predicate becomes false, not before terminal/close. A fresh installation defaults to `KeepForever`; selecting `DeleteAfterDays` initializes an editable draft to 30 days and requires confirmation that already eligible bytes may be irreversibly removed from Vestrace-managed live storage and managed backups through the key-erasure contract below. The worker sweep interval is a pinned release constant of fifteen minutes and the transaction batch size is 250 content records, so neither is an inert UI setting.

`ContentMaterial` is the stable workspace-scoped identity and concurrency guard for retention-governed bytes. `InteractionMessagePayload`, `InteractionStateRevision`, `InteractionContextRevision`, `ArtifactRevisionContent`, `ProtocolProjectionPayload`, `TriggerDeliveryPayload`, and ModelRequestEvidence input maps are structural typed maps whose parts explicitly reference `ContentMaterialId`; they never embed the referenced text, canonical JSON, tool arguments, binary bytes, unkeyed content digest, or exact plaintext length. Live product ciphertext exists only in the corresponding `ContentMaterialBytes` row; plaintext and exact MIME/length/integrity metadata exist only inside its AEAD-protected payload and a bounded zeroizing hydration buffer. Immutable envelopes, typed maps, identities, ordinals, erasure-bound commitments, padded size classes, safe media classes, provenance, provider observations, Run/Step events, policy decisions, external-effect evidence, and Audit remain after deletion.

Every new governed `ContentMaterial`, including every `EmbeddingVectorMaterial`, uses the generic v1 `MaterialKeyCreationIntent` protocol rather than an impossible cross-store SQL transaction. Reservation fixes the exact MaterialId, MaterialKeyId, nonce, typed cause, fixed owner, and output ordinal where applicable. Its closed durable sequence is `Reserved -> ProvisionalCreated -> ProvisionalReceipted -> ContentPrepared | ResultPrepared -> Bound -> Live`; the ordinary-content branch alone may instead record `ContentAbandonPrepared -> Abandoned`, while `ResultPrepared` must bind/finalize and can never take the abandonment branch. The vault's create-if-absent provisional key and its receipt are durable but never runtime-unwrap-capable; the supervisor may perform only an intent-bound one-use encryption operation over bounded zeroizing buffers. A `PreparedMaterialAttachment` is a narrow internal structural record, not an ordinary `ContentMaterial` reference: it is unique to that exact intent, fixed owner/cause/ordinal, and the same committed `ContentPrepared` or `ResultPrepared` marker, and is neither queryable, hydratable, executable, shareable, nor accepted/visible product content. Ordinary content commits ciphertext plus this attachment, never a typed message/revision/payload/result reference. Provider-derived embedding output uses its non-live `ResultFinalizing` projection attachment as this specialized form. The reconciler binds a provisional key idempotently only to its exact committed prepared marker, stores a bound receipt, and one database finalizer atomically promotes the attachment to the typed ordinary reference or projection and makes the material `Live`; only then may its owner become accepted, visible, executable, dispatchable, or otherwise consumable. Thus the installation material-key vault, outside PostgreSQL, safety journal, and every backup, remains the only key-envelope authority; PostgreSQL and managed backups contain only ciphertext/fingerprint plus opaque key identity, and no raw key is exported.

Every live content material, credential revision, and idempotency-comparison scope has its own random data-encryption or comparison key and stable `MaterialKeyId`/`IdempotencyComparisonKeyId`. `Live` additionally requires a matching `Bound` creation-intent receipt, required bytes, a promoted typed reference/projection where applicable, no ErasurePrepared, and no tombstone/Destroyed; lifecycle, retention, authorization, and purpose checks remain additional necessary conditions. Bound material uses the same preparation -> witnessed fence -> vault erase -> receipt -> database-finalization machinery; an idempotency scope carries no ciphertext but retains its now-non-recomputable comparison fingerprint as evidence. The supervisor exposes narrow purpose-bound unwrap/compare and irreversible erase operations, never key export. Erasure is one externally idempotent but internally two-phase state machine: under the scope/material/credential guard, phase one revalidates every blocker and commits immutable ErasurePrepared evidence (and Candidate `Cancelled` when applicable), which immediately and permanently makes hydrate, compare, unwrap, automatic reuse, new references, activation, leases, and dispatch refuse that identity. Only for that committed preparation may the supervisor append a witnessed key-erasure fence, irreversibly erase the exact vault key, and return its receipt; phase two requires the preparation plus receipt, removes ciphertext where present, and appends tombstone/`Destroyed`. Neither preparation nor key erasure can be cancelled. Before any `ContentPrepared`, `ResultPrepared`, or `Bound` marker, the intent guard may authorize only the narrow vault `erase_unbound_provisional_key`, which requires the committed Reserved/provisional intent plus database proof of no prepared/bound/live material, ordinary reference, or result, returns a witnessed receipt, and permits `Abandoned`. After `ContentPrepared` but before `Bound`, the distinct guarded `ContentAbandonPrepared` transition must first append its abort evidence, atomically remove the never-published ciphertext and `PreparedMaterialAttachment`, and prove no accepted owner, `Live` material, ordinary reference, or provider result; only that abort record permits the same unbound erase/receipt/`Abandoned` finalization. A plain `ContentPrepared` marker can never jump to `Abandoned` or lose its key, and a `ResultPrepared` marker can never be abandoned. This is distinct from, and can never erase, a bound Live key; a database rollback alone never erases an already-created external-vault key. A live safety reconciler completes every reservation/vault/receipt/prepared/abort/bind/activate/abandon or erasure boundary before affected APIs or installation readiness can proceed. Consequently every Vestrace-managed backup copy becomes cryptographically unrecoverable at the same boundary even if opaque ciphertext/fingerprint remains until backup expiry; operator-created plaintext or independently decrypted exports are explicitly outside the managed-storage deletion claim and are warned/audited at export time.

For each content material, HKDF derives a distinct `MaterialCommitmentKey` from its random DEK. Structural evidence stores only `HMAC-SHA-256(MaterialCommitmentKey, domain || ContentMaterialId || canonical_plaintext)` and `SizeClass = max(4096, next_power_of_two(AEAD_payload_bytes))`, with empty input defined as SizeClass 4096; ciphertext is padded to that class, classes below 4 KiB are invalid, and the exact digest, byte length, and MIME details required for live verification are inside the AEAD payload. The commitment key is never exported or backed up separately and disappears with the DEK, so a retained database/backup/tombstone cannot recompute the commitment or confirm equality of a low-entropy guess after erasure; the explicitly disclosed SizeClass remains only a bounded padded-length class, never an exact-length or equality claim. Unkeyed deterministic digests and exact sizes of retention-governed bytes are forbidden in structural maps, provider/Run/protocol evidence, Audit, logs, and tombstones.

V1 has exactly two other fingerprint authorities. One random immutable `InstallationFingerprintKey` and opaque `FingerprintKeyId` are created with the `InstallationId`; they fingerprint only untrusted external identifiers for uniqueness. A domain-separated `FingerprintKeyContinuityProof = HMAC-SHA-256(key, "vestrace-installation-fingerprint-v1" || InstallationId || FingerprintKeyId)` is pinned with the key identity in PostgreSQL, every managed-backup manifest, and the independent witness, while the create-only, non-overwritable key record remains only in the host vault. Readiness and restore recompute the proof through the supervisor and compare it without exporting the key. V1 has no rotation, overwrite, import, or silent replacement operation: absence, wrong identity/version, or proof mismatch fails readiness and normal restore closed; structural salvage alone creates a new InstallationId and key. Separately, each content-bearing idempotency scope receives a random `IdempotencyComparisonKeyId` whose key remains in the vault and whose domain-separated HMAC compares the retained canonical body. The idempotency-scope/binding/delivery guard is taken before referenced material guards and before comparison. When the first required body material enters ErasurePrepared, the same transaction makes comparison unavailable and commits the comparison key's own ErasurePrepared evidence; the existing witnessed erasure/reconciler machinery finishes it. Every later retry resolves the stable identifier first and returns the one documented expired outcome before hashing or comparing caller bytes. The opaque fingerprint may remain as non-recomputable evidence, but cannot become a post-retention equality oracle. Raw canonical request hashes are never persisted or exposed.

AG-UI acceptance atomically persists the complete bounded input `state` as one immutable canonical-JSON `InteractionStateRevision` and the ordered `context` items as one immutable `InteractionContextRevision`, both linked to the ProtocolBinding, InteractionThread, canonical Run, classification, and exact source material references. For every upstream Context item, both caller-controlled `description` and `value` are separate retention-governed material parts; the structural map contains only order, a server-issued opaque `ContextItemId`, material references, per-material erasure-bound commitments, coarse SizeClasses, and classifications. No caller-controlled label, description, value, unkeyed digest, exact size, or plaintext-equality oracle may appear in a Run snapshot, checkpoint, queue, event, log, audit, or tombstone projection; the declared coarse SizeClass is the sole bounded length disclosure. Later authoritative state snapshots/deltas create new immutable state revisions; a delta records its base revision and validated RFC 6902 patch material before deriving the next revision. `RunSnapshot`, checkpoints, and worker queues contain only these revision IDs, opaque item IDs, commitments, SizeClasses, and classifications. A worker must hydrate live material through the guarded content repository immediately before use and cannot fall back to protocol envelopes, logs, or an inline copy. A nonterminal or paused Run/binding protects every required state/context revision. After terminal/close and policy eligibility, deletion leaves only tombstoned structural metadata whose commitments are no longer recomputable; no resume or new execution may use missing material.

V1 performs no automatic plaintext-derived deduplication of new message/state/context/artifact/protocol bytes. Every new ingestion receives a fresh MaterialId/key/commitment; sharing exists only when an authorized governed command explicitly links another compatible typed revision to an already known `Live` MaterialId, and every reference is an explicit composite-FK row. A shared material can be tombstoned only when every referencing revision independently passes retention eligibility and no live blocker exists. A protected reference therefore protects the shared bytes for all references and appears as `shared_live_reference` in Preview/job evidence. To keep a scalar replay low-water truthful, material referenced by a `ProtocolProjectionPayload` is ordinal-private: a database constraint permits that identity to be referenced by exactly one `(ProtocolBindingId, ordinal)` projection and by no other content class. Once tombstoned, resubmitting identical bytes creates a fresh identity/key/commitment/provenance; it never resurrects or rebinds the old identity.

`EmbeddingSpaceKey` is structural metadata, never content or a digest: exact embedding `ModelRevision`, exact `ModelQualificationRevision`, adapter/profile/request-shape revision from the immutable evidence, fixed `encoding_format: float`, and that qualification's observed output dimension. Different Model qualification, adapter/profile/request-shape revision, returned model, or dimension is a different space and never mixes vectors. A production response must match its exact space model and observed dimension or fail definitely. Each space has one guarded `EmbeddingSpaceCorpusState` with monotonic `corpus_revision`, `next_projection_ordinal`, and current live-member count. `EmbeddingVectorMaterial` is an encrypted derived `ContentMaterial`, never a plaintext-vector table or digest. Each structural `EmbeddingProjectionEntry` is unique for `(EmbeddingJobId, input_ordinal)`, names that ordinal's exact ordered source `ContentMaterial` dependency set, one EmbeddingSpaceKey/embedding `ModelRevision`/`ModelBindingSnapshot` provenance tuple, inherited classification, response index/dimension/model, and exactly one derived vector `MaterialId`; it also has its never-reused space-local `projection_ordinal`. Until its result finalizer, that row is the non-live `ResultFinalizing` provider-result `PreparedMaterialAttachment`; every source dependency is already `Live`, while its own derived-vector attachment is not an ordinary reference or usable material. Database constraints require response index to equal `input_ordinal`, response model/dimension to match the space/binding, and unique `(EmbeddingSpaceKey, projection_ordinal)`. Its classification and retention are at least the strictest source's, it has its own intent-reserved random `MaterialKeyId` and erasure-bound commitment, and it inherits every source eligibility predicate. PostgreSQL, provider evidence, Audit, logs, and managed backups contain no plaintext vector or stable vector digest.

`EmbeddingTransitionProjectionRecipe` is structural provenance, not content and never a digest. A recipe row is unique on `(EmbeddingSpaceTransitionId, transition_version, old_projection_entry_id)` and carries its opaque ID; old-space/job/input/projection-ordinal identity; ordered dependency rows; target ModelRevision/ModelQualificationRevision/EmbeddingSpaceKey/request-shape; and immutable `TransitionBatchId`/target-input-ordinal assignment with no physical target job ID. A transition target `EmbeddingProjectionEntry` has exactly one recipe foreign key, while exactly one lineage-wide recipe satisfier is either the successful physical job/input/projection/derived-MaterialId tuple or exact `SatisfiedExisting` prior-Live-projection row after promotion; deferred constraints reject any missing, duplicate, unplanned, regrouped, reordered, wrong-space, wrong-model, or response-index-mismatched result. A recipe has no content-equality field. `SatisfiedExisting` is an immutable prior-recipe/target-entry lineage fact, never a vector alias: it is valid only while the exact current target and every ordered source dependency are `Live` and the target is in the exact required space. Transition completeness derives from this FKs-only bijection, not from source-set equality or a digest.
`EmbeddingIndexGeneration` is metadata-only durable state scoped to one exact EmbeddingSpaceKey: an opaque generation ID/epoch, captured `corpus_revision`, built-through projection ordinal, member count, `Building | Ready | Stale | Revoked` state, current pointer/CAS version, and safe lifecycle timestamps/reasons; it never contains a vector, digest, or source content. `EmbeddingIndexGenerationGuard` is the persisted space epoch fence. A vector query takes its exact space's current generation guard in shared mode for bounded use, requires the query's accepted immutable ModelBindingSnapshot-derived space to equal the generation space, revalidates that the persisted generation is `Ready`/current with captured corpus revision equal to the current space corpus revision and every selected vector/source material `Live`, then may use that exact in-memory generation. A builder captures one space corpus revision under the guard, builds only that space from Live encrypted vector materials, then reacquires the exclusive guard and compare-and-swap publishes `Ready`/current only if corpus revision, built-through ordinal/member count, and every source/vector state still match; otherwise it discards/zeroizes its candidate and retries later. Delivery/rebuild activation advances that exact space corpus revision, makes current Ready generations `Stale`/not-current, and emits a durable rebuild event; source/vector erasure advances the affected corpus and uses `Revoked`/not-current semantics. Only after either committed event do workers zeroize/drop stale memory. A stale or partitioned worker cannot use a retained copy because every query reacquires and revalidates the persisted epoch/corpus revision. Restart has no memory index and queries fail closed until a builder completes that guarded live-material build. A later rebuild cannot derive a vector from an `Expired` source, and identical later content receives fresh source/vector identities, keys, and commitments.

Server and worker roles have no direct `INSERT`, `UPDATE`, or `DELETE` on content-material or idempotency-comparison identities, bytes/fingerprints, creation intents/receipts, prepared attachments, erasure/abandon preparations, tombstones, scope-body references, or material-reference rows. A narrow non-login-owned creation operation with fixed `search_path` and no dynamic SQL drives the reserved `MaterialKeyCreationIntent` protocol: it accepts only the fixed identity/owner/cause/nonce, invokes the vault provisional create/receipt, derives the per-material commitment and scope comparison fingerprint, pads/encrypts through the intent-bound operation, and commits `ContentPrepared` ciphertext plus its one internal `PreparedMaterialAttachment`, never a typed ordinary reference. The owner remains non-accepted/non-visible/non-executable until the exact bound-receipt finalizer atomically promotes that attachment to its typed reference and material `Live`. A separate explicit-share operation locks the known material guard and may add a compatible reference only while the identity is `Live`; it never searches by plaintext, digest, commitment, fingerprint, or SizeClass. Ordinal-private protocol creation binds the fresh identity to that exact binding/ordinal only in its promotion finalizer. Governed `TriggerDeliveryPayload` creation likewise completes its intent bind/live finalizer and comparison scope before it becomes dispatch-eligible. These operations reject an erasure-prepared, tombstoned, aborted, or unbound-prepared identity. Deferred invariants enforce bytes-before-tombstone, immutable preparation-before-erasure, ciphertext absence after tombstone or guarded pre-live abort, creation-intent/attachment/receipt causality, one exact prepared marker per attachment, promotion-only ordinary references, and reference refusal once preparation exists. Raw SQL cannot forge, publish, or repoint an attachment, ordinary reference, prepared marker, bound receipt, or owner acceptance.

Every transaction that creates a byte-requiring executable dependency, message/state/context/artifact/projection/webhook-body/model-request/vector-projection reference, retention hold, upload/export/download lease, or protocol delivery lease locks its idempotency-scope/binding/delivery/ModelRequestEvidence guard first, then required `MaterialKeyCreationIntent` and EmbeddingSpaceCorpusState/`EmbeddingIndexGenerationGuard` rows in canonical `(workspace, EmbeddingSpaceKey)` order, then all affected `ContentMaterial` guards in canonical `(workspace, ContentMaterialId)` order. It rechecks every existing/source/referenced material and comparison scope `Live` before commit; a newly created target may instead be the exact non-live `ContentPrepared`/`ResultPrepared` attachment under its reserved intent and is never treated as `Live` early. Sweep, model-request reconstruction/dispatch, vector-index build/query, projection/delivery creation, comparison, and replay/delivery-lease creation use that same cross-aggregate order. PostgreSQL enforcement triggers on every scope/body/blocker/reference table take the same locks and reject an erasure-prepared or tombstoned identity even for raw SQL; application commands sort multi-material IDs to prevent deadlocks. The sweep takes those locks and re-queries all reference/blocker tables, eliminating absence-check phantoms. Its phase-one transition accepts the exact running sweep job/policy/material identities and expected lease owner, revalidates policy, lease, cutoff, references, blockers, and `Live`, then atomically derives `Expired` for every ModelRequestEvidence graph requiring this body, finds every FK-dependent `EmbeddingProjectionEntry`/derived `EmbeddingVectorMaterial`, prepares them, advances each affected EmbeddingSpaceCorpusState, and marks its affected persisted `EmbeddingIndexGeneration` rows `Revoked`/not-current before appending `MaterialErasurePrepared`; it also disables/prepares every comparison scope that requires the body and marks the item `erasure_finalizing` without advancing reclaimed counters. The committed preparation emits durable invalidation/rebuild events; only their post-commit consumers zeroize/drop in-memory generations. After witnessed vault erasure, phase two re-locks the same guards, requires every preparation/receipt, removes only ciphertext, and appends one `ContentTombstone` containing material identity, now-unverifiable erasure-bound commitment, coarse SizeClass/safe media class, padded storage bytes reclaimed, policy revision, sweep job, eligibility anchor, and deletion time. It then advances material/padded-storage counters and checkpoint. A crash at either boundary leaves hydration, vector indexing/query, reconstruction, and comparison refused until the persisted guard/status permits use, and is completed idempotently by the live reconciler. Raw creation/mutation/deletion and resurrection by runtime roles fail independently of application code; no preparation or tombstone stores deleted content, exact length, plaintext vector, stable vector digest, or unkeyed digest.

For `DeleteAfterDays`, each referencing message/state/context/artifact/projection/webhook-delivery/model-request revision's `eligible_at` is the latest of its creation time and every producing or consuming Run, Step, InteractionThread, ProtocolBinding, TriggerDelivery, and provider effect terminal/closed time, plus the configured days. A shared material is eligible only when database time has reached every reference's instant and all of these are true under the shared guards: every related Run/Step/binding/thread/delivery/effect is terminal or explicitly closed; no HumanRequest, upload verification, tool/A2A/model effect, webhook dispatch, export/download, request-inspection, or protocol delivery lease is pending; no active/interrupted binding needs the payload; no published Agent/Workflow/Trigger, workspace default, Evaluation/dataset, operator-retained Artifact revision, or other executable relation requires its bytes; and no explicit operator retention hold exists. Structural historical/provenance/ModelRequestEvidence references do not block after those predicates because they survive through the tombstone and truthfully derive `Expired`. Operator-uploaded Artifact revisions receive a hold by default; generated interaction artifacts and terminal webhook bodies follow workspace policy unless the operator places a hold. Hold placement/release uses the material guard, expected-version CAS, and Audit.

Active or interrupted AG-UI/A2A bindings are never purged. A durable historical `ProtocolDeliveryCursor` is evidence, not a permanent deletion blocker. Only an unexpired `ProtocolDeliveryLease` for an active response/replay temporarily protects its binding and covered ordinal range; the lease records binding, scoped consumer, owner, from/to high-water, `issued_at`, and deadline, and lapsed ownership follows the shared deadline rule.

For a completed binding past retention cutoff, the sweep locks the binding retention guard and then its `ContentMaterial` guards in canonical order. Starting immediately after the existing replay low-water mark, it computes the largest contiguous ordinal prefix for which every projection material/reference is eligible and no unexpired delivery lease covers an ordinal. If an earlier ordinal is protected, no later ordinal from that binding is tombstoned even when independently old enough. Tombstoning that complete prefix, advancing the scalar low-water mark to its final ordinal, and appending expiry evidence for historical cursors at or below it commit atomically. This preserves one gap-free retained suffix.

Replay/delivery lease creation takes the same binding/material guards, first rejects a requested cursor at or below low-water with the protocol's machine-readable expiry outcome, and only then establishes the lease. It therefore orders reconnect before sweep or observes the advanced low-water after sweep. Canonical APIs expose tombstoned metadata rather than fabricated content. An `Unknown` external effect remains structural evidence and is not itself content, but any nonterminal parent/binding or unexpired delivery lease continues to protect the referenced payload.

Saving a policy revision writes Audit and a durable configuration event consumed by the worker. Selecting a shorter destructive period schedules a `RetentionSweepJob`; while `DeleteAfterDays` is active, the worker also creates one on the fifteen-minute cadence. Under `KeepForever`, Preview reports protected-by-policy and `Run now` is disabled with that exact reason rather than creating a no-op success. A job snapshots the exact policy revision and cutoff and records append-only `Requested -> Running -> Succeeded | Failed | CancelledPolicyChanged` transitions, owner, lease deadline, `(eligible_at, content_id)` checkpoint, examined/deleted/protected material counts, reclaimed padded-storage bytes, safe failure, and timestamps; it never persists aggregate exact plaintext lengths. The worker revalidates the active policy and every dependency before each bounded deletion transaction; its tombstones, counters, and next checkpoint commit together. A policy change is a barrier between batches: an old-revision job stops before deleting more content. A lost worker is re-leased only after the shared deadline rule; unique tombstones make each deletion idempotent, and restart resumes from the durable checkpoint without double counting or skipping. Retrying a terminal Failed job creates a linked new job against the current policy/cutoff and never rewrites the failed evidence.

Settings shows the effective revision, mode/days, advisory Preview material count and padded-storage SizeClass totals by content class—including webhook delivery bodies—protected counts by exact reason, next scheduled sweep, current/last job state and checkpoint, reclaimed padded-storage bytes, comparison-key reconciliation, failure/retry action, and Audit link. It does not expose or retain exact plaintext lengths for deleted Context/message/webhook content. Preview never authorizes deletion and may become stale; the worker's locked revalidation is authoritative. Browser and PostgreSQL fault evidence must prove save/confirmation, real worker consumption, protected refusal, eligible deletion, cursor/webhook expiry, policy-change cancellation, mid-batch crash/restart, idempotent resume, visible failure, body-independent expired outcomes, tombstoned canonical APIs, immutable structural evidence, and Audit correlation.

## 7. AG-UI v1.0 product profile

### 7.1 Transport and endpoint

Each published agent exposes one authenticated endpoint:

```text
POST /v1/ag-ui/agents/{agent_id}
Content-Type: application/json
Accept: text/event-stream
Body: RunAgentInput from @ag-ui/core 0.0.58
Response: ordered AG-UI events over SSE
```

The console uses the pinned official `HttpAgent` through a thin Vestrace wrapper that adds authentication, request idempotency, bounded reconnect, and local Run correlation. The server validates the full pinned `RunAgentInput`; it does not accept a smaller private message DTO while silently ignoring standard fields.

The pre-v1 split endpoints `/ag-ui/run`, `/ag-ui/events/stream`, and `/ag-ui/endpoints` are not part of the v1 contract. The console and OpenAPI change atomically to the single POST/SSE endpoint, after which the old routes are removed rather than retained as inert compatibility surfaces.

### 7.2 Input mapping

The adapter supports and validates all pinned input families:

- `threadId`, `runId`, and `parentRunId` become scoped external identifiers in `ProtocolBinding`;
- `messages` are imported as immutable interaction messages after role, ordering, size, and part validation;
- `state` is working-state input, not permission or server configuration; its complete bounded canonical JSON becomes the exact `InteractionStateRevision` referenced by the runtime snapshot;
- `context` becomes ordered `InteractionContextRevision` evidence referenced by the runtime snapshot; each caller-controlled `description` and `value` is governed material, while only server-issued opaque item IDs and structural metadata may remain inline;
- `tools` are client offers and never authority grants;
- multimedia message parts are ingested through the Artifact service before model use;
- `forwardedProps` are allowlisted per published agent; unknown or authority-bearing keys are rejected;
- `resume` is validated against every open interrupt on the same thread.

The erasure-bound canonical request-comparison fingerprint covers every validated semantic `RunAgentInput` field, including ordered messages, complete state/context, tool schemas, allowlisted forwarded props, and resume entries; it excludes authentication, transport cursor, and retry headers. First acceptance allocates an `IdempotencyComparisonKeyId` and atomically binds its fingerprint plus the exact message/state/context revision IDs to the ProtocolBinding and Run. A retry first resolves `(workspace, agent, threadId, runId)` through installation-keyed external-identifier indexes and takes the binding/material guards. While every required body remains live, an equal comparison fingerprint resolves only to the original binding and replays its event stream, while a different body conflicts. Once its completed prefix or any required request/comparison material enters ErasurePrepared or is tombstoned, every body supplied under that existing identity returns the section 7.6 `cursor_expired` outcome before comparison and never re-ingests bytes or creates replacement work. Ordinary turns create a new canonical Run and executable Step atomically. A conforming resume uses a new AG-UI `runId` but continues the same paused canonical Run; it does not create a duplicate local Run or repeat already authorized effects.

### 7.3 Tools, authority, and human interruption

A client-declared tool is callable only when it is also:

1. registered by exact name and schema in Vestrace;
2. allowed by the immutable `AgentRevision`;
3. present in the caller's effective capability set;
4. allowed by policy for the current input, target, and sensitivity;
5. executable by a configured local or client-side implementation.

Tool-call arguments are proposals. An approval-requiring call emits the standard tool-call sequence and a `RUN_FINISHED` event with `outcome.type = "interrupt"`. Before that terminal protocol event, the server emits the state and message snapshots required to resume. The canonical Run remains paused on durable `HumanRequest` records.

The next standard `RunAgentInput.resume[]` must cover every open interrupt, match the thread, pass expiry and JSON Schema validation, and be idempotent by an erasure-bound response-comparison fingerprint tied to the governed response material. Approval, denial, cancellation, and edited arguments are recorded exactly through governed material references. Allowed decisions append authorization evidence; denials are audited but never represented as authorization. On resume, the adapter emits tool results against the original tool-call ID without replaying the original proposal.

Client-side tool results and uploaded files are observations. They cannot by themselves prove that an external effect succeeded or grant capability.

Backend and frontend tools have distinct completion paths. A backend tool executes through a durable local Step/effect boundary and emits its result in the same AG-UI stream. A frontend-defined tool ends `TOOL_CALL_END` by persisting an open `ClientToolRequest` and pausing the canonical Run. The current AG-UI protocol run then terminates normally as a completed protocol turn; this terminal event does not mark the bound canonical Run successful.

The Vestrace client wrapper executes a registered frontend handler and starts the standard follow-up turn on the same thread with a new `runId`, the prior `runId` as `parentRunId`, and exactly one new `ToolMessage` carrying the original `toolCallId`. An unwrapped official client can perform the same standard message sequence. The adapter correlates the open request, verifies tool name/call ID, message ordering, declared result schema when present, live decrypted size, error field, expiry, and caller, then resumes the same canonical Run. `(client_tool_request_id, tool_message_id, erasure_bound_result_comparison_fingerprint)` is idempotent while result material is live; reuse with different retained content conflicts without persisting a raw result hash, and expired material produces the same `RUN_ERROR` before comparison for every supplied body. Unknown, already resolved, or expired calls do not advance execution. A client exception is returned as a ToolMessage with `error`, while a missing result reaches the immutable revision's timeout and fails the Step without inventing an effect outcome. Approval-bearing frontend tools use the interrupt/resume path instead of this automatic result path.

### 7.4 Multimedia and artifacts

Every content-part form accepted by the pinned schema is parsed. Text is stored only through bounded `InteractionMessagePayload -> ContentMaterial` references. Binary, image, audio, and file-like parts are streamed into fresh-identity Artifact material with MIME sniffing, declared-versus-observed type checks, live size limits, AEAD/integrity verification, padding, and quarantine state; no unkeyed content address enters structural storage. Remote URLs are never fetched by the model worker directly; the Artifact service performs an SSRF-safe import or rejects the part.

The selected model binding declares the modalities it actually supports. A valid AG-UI part unsupported by that model produces an actionable pre-execution protocol error or an explicit configured transformation; it is not silently dropped. The console can upload, preview, download, and show provenance for supported parts.

### 7.5 Event projection

Projection uses durable Run/Step/Message/Artifact events and a per-binding ordinal, never timestamps alone.

| Vestrace observation | AG-UI projection |
| --- | --- |
| Binding accepted and canonical Run available | exactly one `RUN_STARTED` |
| Assistant message begins/streams/ends | `TEXT_MESSAGE_START`, `TEXT_MESSAGE_CONTENT`, `TEXT_MESSAGE_END` |
| Step begins/completes | `STEP_STARTED`, `STEP_FINISHED` |
| Tool proposal arguments and result | `TOOL_CALL_START`, `TOOL_CALL_ARGS`, `TOOL_CALL_END`, `TOOL_CALL_RESULT` |
| Complete working state or RFC 6902 change | `STATE_SNAPSHOT` or validated `STATE_DELTA` |
| Authoritative visible message history | `MESSAGES_SNAPSHOT` |
| Safe progress/activity view | `ACTIVITY_SNAPSHOT` or `ACTIVITY_DELTA` |
| Artifact revision becomes visible | allowlisted `CUSTOM` event `vestrace.artifact.v1` |
| Local Run binding established | allowlisted `CUSTOM` event `vestrace.run-binding.v1` |
| Frontend tool request is durable and the canonical Run awaits its ToolMessage | `RUN_FINISHED` success for that AG-UI protocol turn; `vestrace.run-binding.v1` remains paused |
| Human input is required | snapshots followed by `RUN_FINISHED` with interrupt outcome |
| Run completes successfully | exactly one `RUN_FINISHED` with success outcome |
| Run cannot continue | exactly one sanitized `RUN_ERROR` |

Reasoning events may carry only an explicitly generated, policy-approved reasoning summary. Hidden chain-of-thought, `RAW`, and `REASONING_ENCRYPTED_VALUE` are never emitted. `CUSTOM` names and schemas are centrally allowlisted; arbitrary domain payloads, secrets, capability envelopes, policy internals, and unredacted errors cannot cross the adapter.

### 7.6 Ordering, replay, and disconnects

Each exposed event has a durable `(binding_id, ordinal)` identity encoded into the SSE `id`. PostgreSQL enforces one gap-free projection sequence and one stored event per ordinal. The initial POST streams from ordinal zero. A retry with the same request identity and `Last-Event-ID` starts strictly after that stored ordinal; a cursor from another binding is rejected. Before sending bytes, an initial/replay response takes the binding/material guards, validates low-water, captures its high-water, and creates the bounded `ProtocolDeliveryLease`; live tailing renews that lease, while disconnect lets its deadline lapse rather than deleting content immediately.

Network delivery is at-least-once, not magically exactly-once. An uncertain disconnect may cause the last event to be delivered again, so the wrapper deduplicates by `(binding_id, ordinal)` before applying it. The wrapper reconnects transport inside one logical `runAgent()` event sequence, preserving the already observed `RUN_STARTED`; a valid retained cursor loses no later stored event, and replay switches to live tailing at a recorded high-water mark. While required material is retained, a plain official client without the cursor extension can repeat the original semantic POST and receive the complete valid stream from ordinal zero; request idempotency prevents a second canonical Run. Active and interrupted bindings are never purged.

For a completed binding, a supplied `Last-Event-ID` at or below replay low-water, or any bounded syntactically admissible no-cursor POST reusing an existing AG-UI identity whose required request material or ordinal-zero prefix is prepared/tombstoned, fails before body comparison, any SSE headers, or event bytes. Equal and unequal candidate bodies receive the exact same HTTP `409 Conflict`, `Content-Type: application/json; charset=utf-8`, and this closed body with no additional fields:

```json
{
  "error": {
    "code": "vestrace.cursor_expired",
    "message": "The retained AG-UI event prefix is no longer available.",
    "retryable": false,
    "recovery": "read_canonical_run"
  }
}
```

This transport failure emits no `RUN_STARTED`, `RUN_ERROR`, or other AG-UI event because it does not change the already-terminal canonical Run. The pinned official `HttpAgent` rejects that `runAgent()` once with status `409` and the parsed JSON payload. The Vestrace wrapper matches only this exact status/code pair, raises typed `AgUiReplayExpiredError`, stops bounded reconnect instead of looping, and reads authorized canonical Run/message/artifact plus tombstoned state/context metadata. Every other non-2xx response remains a distinct failure. Neither path creates a Run, binding, effect, delivery lease, or replacement stream.

Backpressure has bounded memory and a documented slow-consumer policy. Dropping a browser connection does not cancel the Run. Server or worker restart does not lose an accepted input or stored terminal event. A protocol run stores exactly one start and one terminal event, although replay may redeliver the same terminal identity. An EOF without observing a terminal event is a failed/truncated delivery, never success.

## 8. A2A v1.0 product profile

### 8.1 Advertised interface

Vestrace publishes an Agent Card at `GET /.well-known/agent-card.json`. The single-workspace profile selects exactly one published `AgentRevision` as the advertised A2A agent. The card is generated from that revision and contains stable public metadata, skills, input/output modes, authentication requirements, and one `AgentInterface`. Its absolute URL is the validated configured A2A public base URL plus `/a2a/v1` (`http://127.0.0.1:8080/a2a/v1` in the default local profile), its binding is `JSONRPC`, and its protocol version is `1.0`. Non-streaming and streaming JSON-RPC requests use `POST /a2a/v1` and `A2A-Version: 1.0`. Requests and non-streaming responses use `application/json`; streaming responses use `text/event-stream`.

The card declares:

- `streaming: true`;
- push notifications: false;
- extended Agent Card: false;
- no gRPC binding;
- no HTTP+JSON/REST binding;
- only skills backed by executable published revisions.

Draft, invalid, and non-selected agents are never discoverable through this card. The selected revision cannot be unpublished while advertised; the operator must atomically select another published revision or disable the A2A server profile. Selection or revision change invalidates the card cache and produces a new digest without rewriting the card and agent snapshot pinned to existing Tasks and Runs.

Agent Card signatures follow the pinned A2A procedure, not JCS alone. The server first applies the protocol's optional-field-presence and default-value omission rules, removes `signatures`, canonicalizes the remaining ProtoJSON with RFC 8785, and signs it with the installation's ES256 protocol key. The protected JOSE header contains `alg`, `typ`, `kid`, and an absolute same-origin `jku` for the cacheable JWKS document. Outbound verification repeats the same omission/removal/canonicalization rules and resolves the key only from the protected `jku` inside the Connection's trust scope or from an explicitly pinned trusted key. Normal remote HTTPS requires Web PKI hostname validation and may additionally require a card signature, while loopback HTTP requires an explicit address allowlist and pinned card/key digest. Unsigned or unverifiable cards fail unless the operator explicitly selects and audits a bounded local-development exception.

### 8.2 Required server operations

The single JSON-RPC endpoint implements all six core operations:

| Operation | Required behavior |
| --- | --- |
| `SendMessage` | Validate and idempotently create or continue a protocol task and canonical Run; return a `Task` or a qualifying direct `Message` |
| `SendStreamingMessage` | For a direct response, emit exactly one `Message` and close immediately; for a Task, emit the initial `Task`, then ordered status/artifact events, and close at terminal state |
| `GetTask` | Return the caller-visible current task with bounded requested history |
| `ListTasks` | Filter and paginate caller-visible tasks with stable opaque page tokens |
| `CancelTask` | Effect-idempotently request cancellation, preserve version races, return the updated Task on the first valid call, and return the normative terminal-state error on a later wire call |
| `SubscribeToTask` | Emit the initial nonterminal task snapshot, tail ordered updates, and close at terminal state |

JSON-RPC IDs are echoed but are not idempotency authority. An initial send is keyed by installation-keyed fingerprints of `(workspace, stable_a2a_profile_id, caller, messageId)`; its separate erasure-bound semantic comparison fingerprint covers context ID when supplied, Message Parts, configuration, and metadata but excludes the choice between streaming and non-streaming delivery. The first acceptance stores the then-selected immutable `AgentRevision` and public Agent Card digest inside the binding, so a later profile selection cannot make a retry create a second Run. A task continuation is keyed by installation-keyed `(workspace, caller, bound_task_id, messageId)` and requires any supplied context ID to match the bound context. After bounded JSON-RPC/envelope validation sufficient to extract the message key, a retry resolves that key and locks the binding before semantic body normalization or comparison. While all comparison/request/response material is live, the same comparison fingerprint resolves only to the original binding and replays its original outcome, while a different fingerprint returns `InvalidParamsError` with safe `vestrace.message_id_reuse` error data.

If retention has prepared or tombstoned any comparison material, original direct Message, or content required to form that same `SendMessage` outcome, every retry under the existing message key returns `InvalidParamsError` with `vestrace.content_expired` before hashing or comparing the supplied Message. It creates no Run, binding, Message, or effect and never fabricates empty Parts; matching and nonmatching candidate bodies are indistinguishable after expiry. `GetTask` may still return protocol-valid current structural Task truth with tombstoned optional history/artifact Parts omitted; if a protocol-valid requested Task/history cannot be formed without deleted required content, it returns the same `vestrace.content_expired` error. `ListTasks` remains metadata-only. Cancellation is internally effect-idempotent by caller-visible task ID: the first valid call returns the updated Task, while a later wire call on the now-terminal Task returns `TaskNotCancelableError` (or `TaskNotFoundError` after authorized purge) without repeating an effect. Errors use the pinned normative A2A error shapes and never expose SQL, secrets, stack traces, policy internals, or another principal's resource existence.

### 8.2.1 Streaming delivery and reconnect

A2A task/status/artifact projections have durable `(task_binding_id, ordinal)` identities and stable SSE `id` values. Their persisted sequence is unique; network delivery is at-least-once. Vestrace clients deduplicate Task snapshots by task/version and artifact updates by artifact identity/revision; raw duplicate envelopes remain observable evidence but cannot duplicate a local state transition or `ArtifactRevision`.

An idempotent retry of `SendStreamingMessage` resolves the original installation-keyed message identity and, while retained, compares the erasure-bound semantic fingerprint to return the same binding. A direct-Message binding emits exactly the same single `Message` and closes, and a Task binding without a cursor emits the complete stored response from its original initial Task followed by its ordered status/artifact events and a live tail when still nonterminal; a plain official client can repeat the identical request without creating another Run. `Last-Event-ID` is a Vestrace transport extension for this idempotent Task-stream retry, not a requirement imposed on other A2A implementations. With a valid retained cursor, the server still emits the original initial Task first with its stable event identity, then replays stored status/artifact events strictly after the cursor and tails live events. Each response establishes the same binding/material-guarded `ProtocolDeliveryLease` before bytes. The Vestrace wrapper deduplicates that initial Task and subsequent repeated envelopes before applying state. A cursor from another binding is rejected.

Active and interrupted tasks retain their stream history. For a completed binding, a cursor at or below the replay low-water mark produces a pre-stream `InvalidParamsError` with `vestrace.cursor_expired`. A no-cursor retry, direct-Message retry, or otherwise valid later cursor whose required initial/prefix payload is tombstoned produces a pre-stream `InvalidParamsError` with `vestrace.content_expired`. Neither error creates or resumes work; `GetTask` then supplies only the protocol-valid retained current truth described above.

`SubscribeToTask` is a separate current-state subscription and is accepted only for a nonterminal Task. Every fresh subscription first emits the current Task snapshot at a captured high-water ordinal and then only events committed after that high-water mark; `Last-Event-ID`, if presented by a transport, never replaces or rewinds this required current-Task baseline. Subscribing to a terminal Task returns `UnsupportedOperationError` before a stream begins. If `SendStreamingMessage` disconnects after the task ID is observed, the client calls `GetTask`, accepts a terminal result, or calls `SubscribeToTask` for the returned nonterminal Task. If no task ID was observed, it repeats the original message ID and Message payload so the server resolves the existing binding and performs the guarded retained comparison. These paths provide recoverable at-least-once delivery; they do not claim exactly-once network delivery.

### 8.3 Inbound task-to-Run semantics

An inbound A2A Task is a protocol projection bound to one `InteractionThread` and exactly one canonical Run; it is not a renamed Run table row. An A2A context may contain multiple sequential Tasks/Runs, but no Task ambiguously owns several Runs. A direct A2A Message has no Task resource yet still has exactly one durable binding to the canonical Run that produced it.

- A first message without a task always creates one executable Run atomically. A published agent may return a direct `Message` only after that Run completes synchronously; the protocol omits a Task resource in that case, while the local Run and binding remain durable and auditable.
- A repeated message with the same ID and retained equal semantic body resolves only to the original binding and returns or replays its original outcome; after governed deletion every body under that ID returns the exact `vestrace.content_expired` or `vestrace.cursor_expired` outcome defined above before comparison and without creating work.
- A follow-up on `input-required` or `auth-required` validates the response and resumes the same paused canonical Run.
- A new conversational turn after a completed task uses the same context but a new A2A Task and new canonical Run.
- A message aimed at a terminal task receives the normative error; terminal history is not silently reopened.
- Cancellation requests the canonical Run cancellation state machine. It does not claim that an already dispatched external effect was cancelled unless a durable receipt proves it.

The task projection maps observed local state as follows:

| Canonical observation | A2A Task state |
| --- | --- |
| Accepted/Preparing | submitted |
| Executing or reconciling a nonterminal ambiguity | working |
| Durable structured input request | input-required |
| Durable authentication request | auth-required |
| Run succeeded and artifacts finalized | completed |
| Run failed with a known failure | failed |
| Cancellation reached a proved local terminal state | canceled |
| Policy or agent rejects the request before execution | rejected |

Vestrace never projects its internal `Unknown` external-effect state as a proved remote terminal outcome. While automatic reconciliation remains active, the Task stays nonterminal with a safe reconciliation status. An operator may stop reconciliation and cancel/fail the local Run because a remote outcome cannot be established; the A2A Task may then report that local terminal decision with an explicit “remote outcome unresolved” status message, while `RemoteAgentInvocation` remains `Unknown` with an unresolved disposition. The operator action cannot manufacture remote success, failure, rejection, or cancellation evidence.

For streamed task lifecycles, the first item is the current `Task`, later items are `TaskStatusUpdateEvent` or `TaskArtifactUpdateEvent`, and the stream closes only at a protocol-defined terminal state. Task history, Parts, artifact revisions, metadata, and extensions are validated against the pinned schemas and preserve ordering.

### 8.4 Outbound A2A client

An enabled A2A Connection stores a normalized base URL, a secret reference, trust and network policy, timeouts, and the validated Agent Card plus digest. “Test connection” performs real SSRF-safe discovery, authentication negotiation, version/capability validation, and a bounded request; it never equates TCP reachability with protocol compatibility.

When a Run Step invokes a remote agent:

1. policy authorizes the exact remote connection, agent skill, data sensitivity, and artifact transfer;
2. the transaction persists `RemoteAgentInvocation::Prepared` and an outbox item;
3. the dispatcher records `Dispatching` before the network effect;
4. the adapter uses stable context/message IDs and the pinned Agent Card snapshot;
5. received task/message/events are schema-validated and recorded as evidence before advancing the Step;
6. task state and artifacts are projected into the local Run without granting remote authority;
7. cancellation and additional-input paths use the same durable invocation and expected version;
8. a terminal remote result completes the Step only after artifact verification and local policy checks.

A timeout or lost response after dispatch becomes `Unknown`, not an automatic retry. Reconciliation uses the observed task ID when available, then `GetTask`/`SubscribeToTask`; when the task ID was never received it uses the stable context/message IDs and `ListTasks` evidence where the peer supports it. The dispatcher never blindly creates a second external task. If the peer cannot provide decisive evidence, the invocation remains visibly unresolved for operator action.

Discovery and dispatch enforce scheme, host, port, DNS, resolved-address, redirect, response-size, media-type, and timeout policy on every hop. Private, loopback, and link-local targets require an explicit connection allowlist; DNS rebinding and credential forwarding across redirects are refused. Credentials are short-lived leases from the secret store and are never persisted in cards, events, artifacts, or logs.

### 8.5 Optional operation behavior

Push notification methods return `PushNotificationNotSupportedError`; `GetExtendedAgentCard` returns `UnsupportedOperationError`. The Agent Card does not advertise either capability. REST and gRPC routes do not exist and no alternate interface is advertised. Adding any of these later requires a new profile, threat model, contract suite, and qualification evidence.

## 9. Complete console information architecture

The primary menu remains exactly eleven items. Each item owns the following real workflow.

### 9.1 Home

Home is the truthful launch and status surface. It shows server/database/worker/LM Studio readiness, real workspace counts, recent Runs, unresolved human requests, failed jobs, and protocol health from dedicated read models. Quick actions start a Run from a published Agent or Workflow, open the corresponding record, or take the operator to the exact configuration error. Health reads do not mutate finding history.

### 9.2 Runs

Runs provides cursor pagination, server-side search/filter/sort, exact deep links, and complete detail for Run, Steps, events, checkpoints, protocol bindings, model snapshot, provider effects, artifacts, approvals, errors, and retention eligibility. Each model or Embeddings effect shows its ModelRequestEvidence identity, current `Complete | Incomplete | Expired` reconstruction status, immutable append-only reconstruction-check history, exact bound revision graph, and safe reason/erasure evidence. While current `Complete`, an authorized `Inspect model-visible request` action takes the same evidence/material guards plus a bounded read lease and reconstructs the exact semantic request into a transient view with a sensitivity warning and no credential/auth material; it never persists an export or digest. Retention preparation racing inspection therefore has one order. Current `Incomplete` is visibly a non-retention defect: inspection and dispatch are disabled, the defect reason/navigation is shown, and it cannot be represented as an erasure state; restoring a pinned implementation may recover only current status, never erase its historical check. `Expired` disables inspection and dispatch, shows the exact authorized `ErasurePrepared` evidence and final tombstone when present, and cannot hydrate. Create requires a published Agent or Workflow and creates executable Steps atomically. Pause, resume, cancel, answer-interrupt, retry-only-when-safe, reconcile, `Acknowledge duplicate risk and start new Step attempt`, close an otherwise inactive InteractionThread, and place/release a content-retention hold invoke real versioned commands with Audit and display conflicts/protected reasons. The duplicate-risk command appears only for a recovered `Unknown` provider effect, names that effect, requires its warning/confirmation, and shows the immutable predecessor plus linked new attempt rather than pretending the predecessor was retried. Legacy empty Runs remain visible as historical incomplete records but cannot be created or presented as active work.

### 9.3 Artifacts

Artifacts stores and retrieves fresh-identity guarded material with immutable revisions, erasure-bound commitment, padded SizeClass/safe media class, provenance, sensitivity, quarantine/verification state, Run/Step/message links, and retention state. While material is live and authorized, the UI may hydrate its AEAD-protected exact MIME/length/integrity metadata for preview/download; after erasure it shows only the safe structural classes and tombstone. The UI supports upload, safe preview, revision history, provenance navigation, authenticated streaming download, and compare-and-swap place/release retention hold. Missing, quarantined, protected, or tombstoned content remains visible with its exact lifecycle state and explanation; metadata never pretends content exists or preserves a dictionary oracle.

### 9.4 Agents

Agents supports draft create/edit/validate, model and tool selection, real system instructions, media policy, capability configuration, version diff, publish/unpublish/archive, duplicate, run, and protocol preview. Publishing creates an immutable executable revision and generated Agent Card view. A test/run action creates a normal canonical Run, uses the saved revision, and opens its live workspace.

### 9.5 Workflows

Workflows supports draft graph editing with typed nodes/edges, validation, immutable revisions, publish/unpublish, and execution. Publishing compiles the graph into an executable plan pinned to referenced Agent/Connection/Model revisions. Running a Workflow creates a canonical Run with real Steps and dependency semantics. Validation, cycles, missing bindings, step failures, pause/resume, and produced artifacts are visible; a saved JSON definition without execution is not complete. The pre-v1 client-writable `/workflow-executions` start/complete/step commands are removed. Any retained workflow-execution resource is a read-only projection derived from canonical Run events, always identifies its owning Run, and cannot accept a caller-asserted status, outcome, or step history.

### 9.6 Triggers

Triggers supports create/edit/delete, enable/disable, manual, schedule, signed webhook, and internal outbox-event sources, target revision selection, input mapping, idempotency policy, next-fire time where applicable, delivery history, and last outcome. The existing “Outbox Topic Subscription” choice is implemented as the internal outbox-event source: it matches an allowlisted event type and bounded resource filter only after the source transaction commits, then durably dispatches through the same trigger application service as every other source. `(stable_trigger_id, source_event_id)` is unique, and the first accepted dispatch atomically pins the then-selected immutable Trigger and target revisions; editing the Trigger before a lost-ack redelivery cannot create another Run or reinterpret the event. An intentional operator replay uses a new explicit replay identity, requires confirmation, and records its relationship to the original delivery in Audit. Recursive/self-generated event families are rejected at validation, and a configured maximum causal depth stops indirect trigger loops. A scheduler, webhook ingress, and outbox consumer all create Runs through the same canonical command used by the console. Test-fire performs the real path with a clearly labelled synthetic source event that cannot masquerade as production evidence. Duplicate webhook or outbox deliveries do not duplicate Runs.

#### 9.6.1 Trigger authority

The installation provisions one non-login `trigger-dispatcher` service principal with no ambient execution capability. Each immutable `TriggerRevision` identifies the exact target revision, input-mapping schema, source configuration, and a revocable `TriggerExecutionGrant` issued by the operator. Publishing compiles the target into a `RequiredAuthorityManifest` covering `run.create` plus the maximum downstream model, tool, A2A Connection, credential, artifact-transfer, sensitivity, budget, and resource scopes that the immutable Agent/Workflow plan may exercise. The operator grants the service principal only an equal or narrower workspace-scoped envelope, with an explicit expiry; a Trigger cannot be enabled while required authority is missing. Publishing or materially editing a Trigger or target creates a new revision and delegation binding instead of transitively broadening an existing grant.

Source authentication proves only that a schedule occurrence, webhook sender, or internal event is eligible to become a delivery observation. It never authorizes the target Run. Immediately before a delivery can create a Run, the trigger dispatcher re-evaluates the live service principal, non-revoked/non-expired delegation, immutable TriggerRevision and `RequiredAuthorityManifest` ceiling, exact target and mapped input, and current policy through the shared authorization authority. The accepted Run records the service principal and delegation ID and snapshots that complete bounded downstream envelope as provenance and its maximum authority ceiling. Every later effect authorizes the same service principal under the same still-live delegation, intersected with that Run snapshot and current policy; starting the target never implies unnamed transitive authority. Revocation, expiry, or narrowing between trigger publication, source ingress, durable queueing, Run creation, and a later model/tool/A2A/artifact dispatch yields a visible denial with Audit evidence, executes no pending effect, and appends no `Authorized` decision. A denial before Run creation leaves a `denied` delivery and no Run; a denial after creation transitions the affected Step/Run through its truthful failure or human-remediation state. The audit correlation preserves both the external/source actor and the operator-issued delegation; neither is impersonated as the other.

#### 9.6.2 Schedule source contract

The v1 schedule grammar is exactly five fields: minute `0..59`, hour `0..23`, day-of-month `1..31`, month `1..12`, and day-of-week `0..6` with Sunday `0`. Decimal values, `*`, comma lists, inclusive ranges, and `/` steps over a wildcard or range are supported; seconds, names, `L`, `W`, `#`, macros, and environment substitutions are rejected. When day-of-month and day-of-week are both restricted, either field matching selects the local date; an impossible calendar date does not fire. Every immutable schedule revision stores an IANA timezone, the tzdb version used for evaluation, and an exact effective interval; a tzdb or schedule change requires a new TriggerRevision and never retroactively changes an old interval. Evaluation uses a PostgreSQL-backed lease and durable high-water mark. An occurrence uses the revision effective at its scheduled instant, its identity is the stable Trigger ID plus the canonical scheduled UTC instant, and its first accepted delivery pins that revision. Recovery evaluates missed intervals revision by revision, so an edit during downtime neither reinterprets nor silently drops an earlier occurrence.

V1 uses one occurrence per matching local wall-clock tuple. A nonexistent tuple in a daylight-saving gap is recorded as `skipped_dst_gap`; when a tuple occurs twice during a fold, only the earlier UTC instant is eligible and the later is recorded as `skipped_dst_fold`. `misfirePolicy` is either `skip` or `fire_once` and defaults to `fire_once`: after downtime, `skip` writes one history summary containing the exact missed UTC range and occurrence count without creating a Run, while `fire_once` collapses the same range into one delivery identified by the latest missed scheduled instant. The scheduler advances its high-water mark only in the transaction that stores that decision, scans calculations in bounded pages, and records a blocking overflow diagnostic instead of silently advancing past an unexamined interval. V1 `overlapPolicy` is `forbid`: if the prior Run from that stable Trigger is still nonterminal, the occurrence is recorded as `skipped_overlap`; it is never queued as an invisible second Run. Restart, lease theft, or a lost acknowledgement reuses the same occurrence identity and cannot duplicate the Run.

#### 9.6.3 Signed webhook source contract

The endpoint is `POST /v1/webhooks/{public_trigger_id}`, where `public_trigger_id` is a canonical opaque random base64url identifier unrelated to a database key; query parameters and alternate path spellings are rejected. V1 accepts a bounded `application/json` raw body and requires these headers: `Vestrace-Webhook-Id` (a caller-stable bounded delivery ID), `Vestrace-Webhook-Timestamp` (decimal Unix seconds), `Vestrace-Webhook-Key-Id`, and `Vestrace-Webhook-Signature`. The signature value is `v1=` plus unpadded base64url HMAC-SHA-256 over `UTF8("POST\n/v1/webhooks/" + public_trigger_id + "\n" + timestamp + "\n" + delivery_id + "\n") || raw_body_bytes`. This binds the method and canonical Trigger endpoint as well as the timestamp, delivery, and exact body. Verification uses constant-time comparison on the raw bytes before JSON parsing; reserialization is never part of the signature oracle. Processing order is closed: route/media/body/header bounds, then signing-key/timestamp/signature authentication, then installation-keyed delivery lookup and guard, then the existing-delivery expiry check, and only afterward JSON/schema parsing or live comparison. Thus an authenticated expired retry cannot be distinguished by malformed JSON or a guessed body. A first receipt outside the fixed five-minute clock window is rejected.

Each stable webhook Trigger owns generated key material that cannot be selected by or shared with another Trigger. The current key version is a write-only secret reference. Rotation creates a new key ID and permits the previous version only for a recorded ten-minute verification grace period; retiring or revoking a key is immediate and audited. Installation-keyed fingerprints of `(stable_trigger_id, namespaced_webhook_delivery_id)` form the unique replay key. The first receipt stores its raw body as governed material and a domain-separated erasure-bound comparison fingerprint. A retry resolves and locks the delivery before body comparison: while the body/comparison key remains live, equal bytes return the same durable receipt without another Run and different bytes conflict; after either enters erasure preparation, every authenticated body for that existing delivery ID returns `410` with `vestrace.delivery_expired` before comparison and cannot create a Run. During rotation a retained retry may use either key still inside its verification window. After the old webhook-signing key expires, an old signature returns `401`, while the same retained delivery re-signed with the current key returns its original receipt and still cannot duplicate the Run. A deliberate replay is possible only through the confirmed operator replay command described above.

An unknown public ID returns `404`; missing, stale, unknown-key, or invalid authentication returns the same non-revealing `401`; invalid media type or transport bounds returns `400` before authentication; an authenticated retry of an expired existing delivery returns body-independent `410 vestrace.delivery_expired` before JSON parsing, schema validation, comparison-key unwrap, or body comparison; invalid JSON/input schema returns `400` only for an unseen or retained-live delivery that reaches parsing; a first valid request for a disabled Trigger returns `409`; first durable acceptance and an identical authenticated retained duplicate return `202` with the same opaque delivery receipt and status URL even if the Trigger was subsequently edited or disabled; inability to commit the delivery returns `503`, never a success. `202` means that the source event was durably accepted, not that its Run succeeded. The status resource exposes `accepted`, `denied`, `dispatched`, the owning Run when created, or the precise safe failure, subject to the same workspace/capability checks as other delivery history.

#### 9.6.4 Enable and disable semantics

Enable and disable are versioned compare-and-swap transitions that create explicit enable epochs. Disable is a hard barrier for new Run creation: in the same transaction it closes the current epoch, marks every accepted-but-undispatched delivery `cancelled_disabled`, and advances a schedule high-water mark to the disable instant with a visible `skipped_disabled` summary for any unevaluated interval. A dispatcher racing that transaction either commits the Run first or observes the closed epoch and creates no Run; it cannot do both. Runs already created before disable continue under their snapshotted delegation unless the operator separately cancels the Run or revokes the grant.

While disabled, manual/test fire returns `409`, first valid webhook delivery records `rejected_disabled` and returns `409`, schedule occurrences are summarized as `skipped_disabled`, and each otherwise-matching outbox event records a terminal deduplicated `skipped_disabled` receipt instead of becoming eligible for dispatch. Re-enable opens a new epoch at its commit instant and starts schedule evaluation at that instant; `fire_once` never catches up across a disabled interval. An outbox event is eligible only when its source commit and durable acceptance both belong to the same still-open enable epoch. A receipt rejected, skipped, or cancelled in an older epoch remains terminal after re-enable, so replay requires a new source/replay identity rather than silently reviving work. These rules survive server/worker restart and apply before trigger delegation authorization; disable does not masquerade as an authority revocation.

Every route provides semantic loading, empty, stale, partial, and error states. Mutation forms expose validation errors, retain drafts, prevent accidental double submission, and resolve optimistic-concurrency conflicts without overwriting another revision.

No enabled button may be a local-only state change. A feature unavailable under the selected configuration is either hidden because it is not advertised or disabled with the precise prerequisite and a navigation path to fix it. “Coming soon”, hard-coded demo data, random metrics, fabricated progress, and unconditional success toasts are forbidden in release code.

The layout, responsive breakpoints, keyboard behavior, reduced motion, focus treatment, and contrast follow the console redesign specification. Browser qualification covers every menu route, primary mutation, deep link, error recovery, and narrow viewport.

## 11. Security and consistency invariants

### 11.1 Authentication and route authorization

The supported local console is same-origin. The operator unlocks it with a bootstrapped or rotated local credential; the server issues an `HttpOnly`, `Secure` when TLS is configured, `SameSite=Strict` session cookie with CSRF protection. External AG-UI and A2A clients use scoped bearer access tokens. Secrets and bearer tokens are never stored in browser local storage.

All governed routes appear in one exhaustive route-to-capability manifest. Unknown governed routes fail closed. `/v1/access-tokens`, protocol endpoints, downloads, streams, webhooks, and newly added routes are covered before they can be mounted. Public health and Agent Card routes are explicit exceptions with bounded, non-sensitive responses.

Route admission does not authorize a later effect forever. Every queued worker action and every model, tool, A2A, credential, or artifact dispatch passes the same shared live authorization boundary immediately before the effect. That boundary intersects the immutable Run snapshot ceiling with current non-revoked, non-expired authority and current policy. A denial records the attempted action and reason but never appends `Authorized`; no adapter may reimplement or cache a broader decision.

### 11.2 Workspace isolation and database roles

The local profile provisions exactly one workspace and one operator, but every repository transaction still sets workspace and principal context. Runtime PostgreSQL remains `NOSUPERUSER` and `NOBYPASSRLS`; protected tables use enabled and forced RLS. Clean Compose applies grants for the server, worker-owned scheduler loop, AG-UI, A2A, artifact, and audit paths automatically. A manually repaired development database is not qualification evidence.

### 11.3 Atomicity, idempotency, and concurrency

`EmbeddingSpaceTransition` is not an intent lifecycle: `Stale` and `Failed` are both lawful immutable pre-activation terminal outcomes, while `Abandoned` remains reserved for the distinct lawful restore, intent, and material state machines. Candidate abandonment may set only a current nonterminal Candidate-bound version to `Failed(reason=candidate_abandoned)`.

- A governed mutation, outbox work, idempotency record, and audit entry commit in one transaction.
- Stable external identifiers use only the immutable installation fingerprint key. Content-bearing idempotency uses a separate erasure-bound comparison key: a different retained body conflicts, while any retry after required material expiry receives the scope's single expired outcome before body comparison.
- Mutable aggregates require expected versions and compare-and-swap transitions.
- Ordered protocol delivery uses persisted ordinal keys, not timestamp cursors.
- Terminal Run, AG-UI run, and A2A Task outcomes are emitted once.
- Cancellation races record the observed winner and never rewrite a terminal outcome.
- Disconnect is not cancellation.
- Unknown external outcomes enter reconciliation and are never retried as though no dispatch occurred.

### 11.4 Input, output, and secret handling

Every JSON, SSE, upload, remote card, Part, artifact, model response, and error has depth/count/byte/time bounds. Schema validation precedes persistence into canonical structures. Sensitive content is redacted or withheld from projections according to policy. Logs use opaque correlations, not prompts, credentials, raw model output, tool arguments, or artifact content. The mounted bootstrap secret store contains only installation/bootstrap references needed to reach separately protected services; decrypt-capable content and credential DEK envelopes live only in the host material-key vault defined below. Product configuration stores opaque credential-slot, credential-revision, and key identities, never secret values.

`CredentialSlot` is the stable workspace/purpose/name reference exposed to Connections and the UI. Every Connection already has its permanent `ConnectionExecutionGuard`; reserving a provider-purpose slot for it takes that guard first and creates a permanent `CredentialActivationGuard` keyed by `(workspace, ConnectionId, CredentialSlotId)` before Candidate material or qualification exists. The guard is the row-lock authority before activation, while owned, and after cancellation/destruction; it is never deleted, reused for another Connection, or inferred from a mutable current pointer. The slot becomes runtime-owned by that same stable Connection only when activated; it may then serve every model of that Connection but cannot be rebound to another Connection or authority. It has compare-and-swap current-revision and tombstone fields but no ciphertext. Each `CredentialRevision` is immutable metadata whose ciphertext, once lawfully finalized, names the per-revision `MaterialKeyId` and a recorded associated-data profile; its random DEK is resolvable only through the installation material-key vault. New `credential-v2` material is AEAD-bound to the workspace, slot ID, credential-revision ID, material-key ID, purpose, normalized destination-authority digest, and auth mode. A migrated `legacy-v1` revision preserves its original workspace/secret-ID/purpose binding and is not eligible for a new remote OpenAI-compatible Connection until a governed rotation creates and validates `credential-v2` material. Append-only lifecycle events derive `Candidate`, `Active`, `Retired`, `Revoked`, and `Destroyed`; history never changes state in place. `SecretRefId` becomes the stable slot ID, while every resolution and external-effect record names the exact credential revision.

Creation and rotation serialize `(workspace, purpose, name)` and allocate the revision identity before encryption, so concurrent writers cannot encrypt under one identity and return another. A separate durable `CredentialKeyCreationIntent`—never a `ContentMaterial` substitute—reserves the exact Candidate association, CredentialRevision, slot, `MaterialKeyId`, nonce, typed cause, and expected slot version. Its closed sequence is `Reserved -> ProvisionalCreated -> ProvisionalReceipted -> CredentialPrepared -> Bound -> Candidate`; the distinct pre-live abort branch is `Reserved | ProvisionalCreated | ProvisionalReceipted | CredentialPrepared -> CredentialAbandonPrepared -> Abandoned`. The provisional vault create-if-absent and durable receipt are unavailable to normal decrypt. `CredentialPrepared` stores Candidate ciphertext only as non-selectable/non-activatable prepared data. The reconciler binds only that exact committed marker and records its bound receipt; one database finalizer then atomically exposes the revision as `Candidate`, appends its lifecycle/Audit evidence, and leaves the association `Pending`. No Candidate is visible, resolvable, or qualifiable before that bound finalizer. A guarded pre-live abort takes `ConnectionExecutionGuard`, then the exact permanent `CredentialActivationGuard`, exact association expected version, intent, and then prepared-material rows in that order; it requires the association still `Preparing`, no Bound/Candidate/ErasurePrepared, and atomically appends a `CredentialAssociationCancelled` event tied to that intent/cause/expected versions, marks the association non-publishable, and appends `CredentialAbandonPrepared`. When ciphertext/attachment exists it removes only that nonpublished state in the same transaction; otherwise the abort fact records the exact pre-prepared boundary. Only the witnessed unbound key erase then finalizes that same intent `Abandoned`. A prepared row never jumps directly to `Abandoned`, SQL rollback alone never erases a key already created in the external vault, and the pre-live branch never creates Candidate or ErasurePrepared. A bound/finalized Candidate uses the ordinary Candidate-abandon/destruction `ErasurePrepared` path below; the two paths are not conflated. Creating it from the Connection wizard atomically creates the permanent guard and an append-only pending-association state machine `Preparing -> Pending -> Activated | Cancelled`, bound to the exact Connection/configuration/slot/Candidate versions, with the draft/configuration command and Audit: `Preparing -> Cancelled` is only the exact intent-bound pre-live abort above, while `Pending -> Cancelled` is only the live-Candidate abandonment path. The association is closed by an event, never cleared or deleted. A database-enforced live-occupancy constraint permits at most one nonterminal preparing/Candidate or RestoreCandidate for each permanent `(workspace, ConnectionId, CredentialSlotId)` guard; it releases a pre-live association only after its `Cancelled` event and exact intent terminal/receipt reconciliation both exist. Concurrent or sequential creation of a second otherwise returns a typed conflict. Creation neither binds the stable slot for runtime use nor leaves an apparently Active orphan on partial failure.

For a Connection's first credential, successful Connection-qualification finalization takes the permanent guard and canonical lock order, revalidates the exact still-`Pending` bound/finalized Candidate association and complete `q1` evidence and, in one transaction, publishes the `ConnectionQualificationRevision`, binds the reserved slot permanently to the stable Connection, compare-and-swaps its current revision from absent to the Candidate, appends `Active`, sets the Connection's effective qualification pointer, closes the association as `Activated`, and writes Audit. If any predicate or write fails, the transaction rolls back: the revision remains non-current `Candidate`, the association remains `Pending`, no qualification is effective, and no Run can resolve it. A `Preparing` or `CredentialPrepared` association cannot enter this finalizer or become qualification evidence.

`Abandon Candidate and destroy material` is one narrowly granted, externally idempotent state-machine command for either a failed first Candidate or an unactivated staged-rotation Candidate, not a client-side sequence. For a `Preparing` association at any Reserved/provisional/receipted/prepared pre-live boundary, it invokes only the exact guard-ordered `CredentialAssociationCancelled` plus `CredentialAbandonPrepared`/unbound-key receipt path above; the expected association/intent versions and fixed cause make replay return that same abort, it exposes no Candidate, and it creates no ErasurePrepared fact. A crash before the abort leaves the association/intent resumably `Preparing`; a crash after abort but before witnessed erase leaves the non-publishable `Cancelled` association and exact abort marker; a crash after the receipt leaves only terminal `Abandoned` reconciliation. For a bound/finalized non-current Candidate, its preparation transaction takes `ConnectionExecutionGuard` first, then the exact permanent `CredentialActivationGuard`, and the exact association/job/revision/material rows next; revalidates expected versions, persisted authorization, exact-name confirmation, non-current Candidate state, and absence of any Active event, usable lease, or `Authorized`/`Dispatching` effect; and accepts terminal jobs plus pre-dispatch `Requested`/between-probe jobs that it can cancel. An in-flight provider effect remains a typed blocker until definite/`Unknown` terminal evidence exists. The Candidate-abandon finalizer cannot win while a genuinely nonterminal effect, lease, or intent remains; its sole permanent-guarded atomic preparation is the transition specified below. A dependent nonterminal `rotation_staged` or RestoreCandidate transition, `AwaitingPredecessorTerminal` barrier, or `AwaitingAcknowledgement` carry is an explicit Candidate-abandon/destruction dependency under `ConnectionExecutionGuard` then the exact permanent `CredentialActivationGuard`; a genuinely nonterminal effect, lease, or intent remains a blocker until its existing terminal reconciliation. Once those underlying effects are terminal, the one winning bound-Candidate abandonment preparation atomically closes `Pending -> Cancelled`, cancels eligible pre-dispatch work, appends `CredentialMaterialErasurePrepared`, marks only each current nonterminal Candidate-bound `EmbeddingSpaceTransition` in `Planned | Rebuilding | ReadyToActivate` as `Failed(reason=candidate_abandoned)`, leaves every historical terminal `Stale`/`Failed` version immutable, terminalizes only every current open carry/barrier mapping and its current dedicated barrier batch as `NoLongerRequired(candidate abandoned)` while retaining predecessor/possible-charge evidence and leaving `Superseded` barrier history immutable, and forbidding retry, marks every Candidate target generation `Revoked`/not-current, and creates the existing guarded cleanup/retention work for Candidate-only target projections/materials before or with `CredentialMaterialErasurePrepared` as the erasure law requires. If no current nonterminal Candidate-bound transition remains, the same transaction creates no transition state/version and instead appends immutable `candidate_work_closed` evidence that forbids Resume/Rebuild/new barrier/carry, closes only any current open mapping/generation cleanup, and leaves terminal history unchanged. At most one current nonterminal transition version exists per Candidate/model lineage, and the same `ConnectionExecutionGuard` order serializes Candidate abandonment against stale-version successor planning. Old Active qualification/space remains current for a staged rotation; RestoreCandidate keeps its existing source-resume/abandon law. If activation wins first this abandonment refuses unchanged. Terminal Unknown metadata needs no credential only after every dependent carry/barrier has been terminalized. After that Candidate preparation commits and releases all database locks, the supervisor erases the exact bound key outside every database transaction; its finalizer/reconciler reacquires `ConnectionExecutionGuard -> exact CredentialActivationGuard`/slot -> exact preparation/revision/material rows, verifies the witnessed receipt, then appends `Destroyed`, removes only that ciphertext, and writes immutable destruction receipt/Audit. No database lock is held during the vault call. A crash at any reserve/vault/receipt/`CredentialPrepared`/bind/finalize/abort or live-erasure boundary remains visibly `credential_preparing`, `credential_abandon_finalizing`, or `erasure_finalizing` and is completed by the live reconciler. If preparation commits first, late evidence remains non-effective; if activation commits first, preparation observes `Activated`/`Active` and refuses without changing material. The guard, association history, revision metadata, qualification/effect evidence, one-way material/preparation/Destroyed invariant, and any prior Active revision remain durable. An idempotent replay returns the exact preparation, association abort, or final receipt without starting a second erasure.

Rotation is staged against the exact current Connection revision and auth mode. Before normal activation it must produce a compatible candidate-bound Connection qualification and candidate-bound Model qualifications for every currently executable `ModelRevision` required by a workspace default or any published Agent, Workflow, or Trigger revision. For every affected embedding Model with a live old space, that candidate qualification finalizer must also create and complete the exact `rotation_staged` EmbeddingSpaceTransition described above; an incomplete, stale, expired, or failed transition is a rotation blocker, not an effective qualification. Transactions that create/change one of those executable dependencies, Run or EmbeddingJob snapshot acceptance, first activation, Candidate abandon, rotation, and revocation all take `ConnectionExecutionGuard` first and then, only where credential-backed, the exact permanent `CredentialActivationGuard` in canonical slot order; no-auth work takes no sentinel guard. The activation transaction then takes each affected space guard in canonical order, re-queries the complete closed dependency set and every transition's old pointer/corpus revision/projection-recipe set, current source/target auth-binding-XOR/configuration lawfulness, exact candidate target-space completeness/Ready generation, and only then atomically compare-and-swaps the Connection/slot versions, publishes/sets all candidate-bound effective qualifications, advances the slot to the Candidate, appends `Active` for it and `Retired` for the prior revision, and CASes every retrieval-active target space together before Audit. No partial Model, qualification, space, or slot switch can commit. First activation or an empty corpus may complete the same guarded fast path. Thus a concurrent default switch, publication, Run/EmbeddingJob acceptance, activation/abandon, rotation, corpus mutation, or revoke has one database order: the effect owner either commits a valid Active snapshot first or observes the new Active/revoked state. A failed or incomplete staged set refuses activation and the UI names every blocking Model/capability/transition; it never silently invalidates future bindings. Future ordinary Runs and EmbeddingJobs resolve and pin the new revision only after that whole activation; candidate transition rebuild jobs remain the sole pre-activation exception. A retired revision may serve only a nonterminal Run or EmbeddingJob that pinned it before retirement; `Revoked` refuses every later resolution, including old owners' next dispatch. Emergency revoke remains immediate after it obtains that transaction lock, may intentionally leave retrieval unavailable, and never fabricates a transition or mixed-space handoff.

`RestoreMaintenanceEpoch` is a closed exception to normal rotation activation, not a second rotation authority. It may create through the same `CredentialKeyCreationIntent` protocol and fully qualify at most one bound/finalized target-generation `RestoreCandidate` for a permanent slot guard; a later epoch must reuse/requalify that Candidate or cancel and finish its pre-live abort or live destruction before creating another. For every affected embedding Model/live old space, maintenance creates the same exact candidate transition/rebuild plan, pins its old projection-recipe set and target space, and may instantiate and use each job-owned snapshot derived from that fixed candidate plan only through the existing CrossGenerationMaintenanceBarrier, target InstallationMutationPermit, live authorization/data-policy/admission/owner/deadline, and witnessed maintenance dispatch authority. No ordinary Candidate routing is enabled. The database refuses any pre-cutover `Active` event, slot-current change, or `Retired` event for that candidate/prior revision. Complete candidate-bound evidence plus every required exact-space transition `ReadyToActivate`/target Ready generation yields only `CutoverReady`; the inherited source revision remains semantically unchanged unless the operator separately performs an explicit cross-generation `Revoked`/material-erasure reduction. Before the point-of-no-return, restore abandonment therefore cancels and destroys only a still-non-current bound Candidate through the existing guarded preparation, while a preparing one uses only the guarded intent abort; source resume either retains the genuinely unchanged inherited Active revision or applies its witnessed Revoked/Destroyed reduction.

Activation uses one immutable `TargetActivationPlan`, not post-cutover discovery or normal TTL-sensitive revalidation. Before `TargetActivating`, under the exclusive target permit and every affected permanent guard and exact-space guard, the supervisor validates the complete dependency set and requires every selected qualification to be unexpired at one database timestamp. The plan binds restore attempt/generation, `Hfinal`, proposed activation epoch, exact zero-or-one CutoverReady Candidate and exact prior state/receipt per slot, qualification/dependency revisions, intended guarded lifecycle writes, and every required embedding transition's exact old/new qualification/space, projection-recipe set, completed target corpus/Ready generation, and atomic retrieval-space handoff entry. If the prior is `Active`, its entry intends ordinary `Retired`; if the exact prior already has a witnessed cross-generation `Revoked` or `Destroyed` reduction, the entry preserves it and never fabricates `Retired`. No other prior state is accepted. The plan is flushed and archived through `Ltargetfinal` before the witness CAS. TTL, corpus, transition, or dependency changes can refuse plan construction, but after the CAS elapsed time cannot invalidate the already authorized plan; expired evidence still cannot authorize a later ordinary Run. The executor verifies plan identity/digest and performs only its idempotent Candidate activation/qualification-effective/retrieval-space-handoff entries. It cannot rebuild, broaden, replace, requalify, or create a transition after the point-of-no-return, so a crash can only resume target initialization and source abandonment is no longer available.

A credential lease names workspace, purpose, exact credential revision, authorization decision, external-effect ID, normalized destination-authority digest, auth mode, `issued_at`, and `expires_at`; append-only state distinguishes Issued, `ConsumedForDispatch`, Expired, and Refused. The single pre-dispatch transaction in section 6.4 repeats lifecycle, slot-version, absence of `CredentialMaterialErasurePrepared`, candidate-governed-job/current/pinned-Run, purpose, effect, authority, auth-mode, and expiry checks under the credential guard, refuses every stale/rotated-away/revoked/erasure-prepared/destroyed/wrong binding, decrypts into the bounded zeroizing container, and appends `ConsumedForDispatch` together with admission and `Dispatching`. The vault independently refuses unwrap after preparation. A consumed lease cannot be reused or block later destruction; the still-`Dispatching` effect does. Plaintext may be attached only by the qualified adapter to its exact authority and is zeroized after that one invocation.

Restricted runtime roles have no direct `INSERT`, `UPDATE`, or `DELETE` privilege on activation guards, pending-association state, `credential_key_creation_intents`/receipts/prepared attachments, `credential_revision_material`, erasure/abort preparations, or credential lifecycle-event rows; lifecycle append and material mutation occur only through the named guarded operations. One narrowly granted creation operation owned by a non-login role, with fixed `search_path` and no dynamic SQL, locks the serialized slot reservation and exact preallocated CredentialRevision, validates the permanent guard plus still-`Preparing` association and the fixed workspace/purpose/authority/auth/AAD/Candidate/slot-version intent, rejects any prior erasure/abort preparation, `Destroyed` event, or material row, and inserts `CredentialPrepared` ciphertext plus its internal prepared attachment exactly once without exposing the revision. Only the exact bound-receipt finalizer may append the Candidate lifecycle event and make the revision visible. Reusing the same secret after preparation/destruction requires a new CredentialRevision identity. Deferred database invariants enforce `Reserved -> ProvisionalCreated -> ProvisionalReceipted -> CredentialPrepared -> Bound -> Candidate`, the guard-ordered intent-bound `CredentialAssociationCancelled` plus `CredentialAbandonPrepared -> Abandoned` pre-live branch, and one-way `material -> erasure prepared -> Destroyed` for a live Candidate; they require a still-Preparing exact association for prepare/bind, a non-publishable Cancelled association plus witnessed terminal intent receipt before occupancy release, ciphertext presence until its respective finalizer and absence after pre-live abort or `Destroyed`, and refusal of every resolution/reference from prepared, aborted, or erasure-prepared identities. Raw or governed insertion cannot forge a prepared attachment, cancellation event, Candidate event, bound receipt, or visible credential from a prepared/destroyed identity.

Material destruction for `Retired` or `Revoked` revisions uses a separate narrowly granted two-phase operation under the same non-login authority; Candidate material uses only the combined abandon preparation above. Its phase-one database transaction takes `ConnectionExecutionGuard` first, then the exact `CredentialActivationGuard`/slot, then exact credential-revision/material/blocker rows, matching configuration, rotation, revoke, and final dispatch order. Under those locks it validates workspace, exact revision and expected version, persisted authorization, confirmed destroy-command identity, and every blocker, appends `CredentialMaterialErasurePrepared`, commits, and releases every database lock before any vault network call. `Active` is never destructible. A current slot pointer blocks unless that exact revision is already `Revoked`; a current Revoked/prepared/Destroyed metadata tombstone may remain selected only while the Connection is visibly `needs requalification` and cannot resolve a credential.

The Retired/Revoked preparation refuses while any nonterminal pending/preparing association, `CredentialKeyCreationIntent`, QualificationJob, or EmbeddingJob still targets the revision; any usable unexpired credential lease exists; any external-effect intent that can still resolve the revision is nonterminal, including `Authorized` or `Dispatching`; or, for a `Retired` revision, any nonterminal Run or EmbeddingJob snapshot still pins it for a future effect. The Candidate abandon preparation applies its stricter association/job rules atomically instead of bypassing this predicate. Revocation permanently denies future resolution, so a nonterminal Run or EmbeddingJob historical reference does not block a Revoked revision once every already-authorized/dispatching effect, lease, and provisional credential-key intent is terminal or reconciled. A shared external effect already adopted to `Unknown` also does not block after its lease is released: it cannot be replayed, and its immutable metadata reference survives. Completed/failed/cancelled/Unknown jobs and effects, including terminal `InconclusiveUnknown` EmbeddingJobs, terminal Runs, immutable qualifications, provider observations, Audit, and other metadata-only references never require ciphertext and therefore do not block.

After live-Candidate or Retired/Revoked preparation commits and releases all database locks, the supervisor performs the vault erase only for the exact bound MaterialKeyId outside every database transaction. The finalizer/reconciler starts a new database transaction, reacquires `ConnectionExecutionGuard -> exact CredentialActivationGuard`/slot -> exact preparation/revision/material rows, verifies the immutable preparation plus section-11.6 witnessed `MaterialKeyErased` receipt, appends `Destroyed`, deletes only that revision's ciphertext row, writes the Audit tombstone, and commits atomically. No database lock is held during the vault network call. A crash before or after key erasure cannot reopen resolution or accept a new reference; the live reconciler resumes finalization, and an idempotent replay returns the original state/receipt. The separate preparing/prepared credential-intent reconciler resumes reserve/vault/receipt/abort/bind/finalize without treating an external-vault key as rolled back. Raw SQL creation/mutation/deletion by server/worker roles and resurrection through the governed creator both fail; only these guarded transitions can create, prepare, bind, publish, or remove ciphertext while opaque metadata/commitments, lifecycle, references, and audit evidence remain. The UI presents every blocker, `credential_preparing`, `credential_abandon_finalizing`, or `erasure_finalizing` state by typed identity and route, never a generic conflict.

### 11.5 Model-provider transport boundary

Every remote OpenAI-compatible Connection uses HTTPS with Web PKI validation. The URL has no user information, query, or fragment; redirects, ambient proxies, insecure-certificate switches, credential forwarding, and caller-selected `Host` are disabled. On every new transport, all A/AAAA results and the connected peer are checked against the Connection's policy. Loopback, private, link-local, multicast, unspecified, and infrastructure-metadata destinations are refused for a remote profile. The sole v1 HTTP exception is the typed `LMStudioLocal` profile and its exact logical-to-Compose mapping; it still reports `RemoteProvider` when the effective peer is the host bridge.

Provider errors expose only a safe bounded status/code/type and provider correlation identifier; they never expose or persist a raw body excerpt, response-body fingerprint, unkeyed body digest, or exact body size. Image input may use only a bounded verified Artifact rendered as an inline data URL; the model adapter never fetches an arbitrary external image URL. Missing upstream usage is persisted as `unknown`, not zero, and a model without observed usage cannot satisfy a hard token/cost budget unless an independently enforceable local bound closes that requirement.

### 11.6 Monotonic backup and restore safety

The supported installation has a stable `InstallationId`, one immutable `FingerprintKeyId` plus `FingerprintKeyContinuityProof`, one active `InstallationActivationEpoch`, and a distinct `DatabaseGenerationId` for every source or restore target. Its `InstallationSafetyJournal` is an append-only, monotonically sequenced, hash-chained log on a dedicated Compose safety volume that is never part of a PostgreSQL backup. A separate host-supervisor `InstallationSafetyWitness`, outside every Compose volume, backup, journal, and key store, exposes only monotonic compare-and-advance over `(InstallationId, FingerprintKeyId/proof, acknowledged_sequence, chain_digest, activation_epoch, generation_lineage_state, WAL_checkpoints, backup_set_heads_and_restore_hold_lifecycle, TargetActivationPlanId/digest/progress, resume_or_target_initialization_state)`; lineage names the one active/frozen source, any prospective maintenance child and its fork LSN, and every sealed/abandoned generation. Per-attempt witness state can only advance through held/reason-bound-released backup, retryable/atomic-abandon-resume, or irreversible plan-bound target-initialization milestones; it cannot represent an `Abandoned` child without the same-CAS `SourceResumePrepared` payload, release a restore hold without its exact terminal receipt, or enter `TargetActivating` without the archived plan digest bound to that activation epoch. It has no rewind, import, restore, truncate, fingerprint-key replacement, or target-plan replacement operation. The Ed25519 private key and create-only installation fingerprint key are held in separately identified protected host-key records and are unavailable to database/runtime roles. A signed journal entry becomes an issuable receipt only after the entry is fsynced and the independent witness advances to that exact sequence/digest. PostgreSQL and every backup manifest pin the public key, FingerprintKeyId/proof, and witnessed checkpoint; the supervisor recomputes and verifies the proof before readiness and restore. A valid signed prefix is never proof of completeness: normal restore requires the current witness, and journal plus archived WAL must authenticate continuously through its acknowledged head/checkpoint. Missing, lower, contradictory, replaced, or unreachable witness or fingerprint-key state refuses normal readiness and activation.

The journal contains only typed identities, generation/epoch, causal IDs, revision/digest metadata, authorization correlation, PostgreSQL timeline/LSN and mutation-watermark checkpoints, and timestamps; it never contains credentials or retained content. The safety key does not rotate within one v1 `InstallationId`; key or witness replacement requires the refused/salvage new-installation path. The narrowly scoped supervisor may sequence entries, issue installation mutation permits and safety receipts, drive archive/freeze/restore epochs, and invoke the material-key vault, but cannot execute ordinary product work.

Every mutating product command, including ordinary Agent, Workflow, Settings, Artifact, Interaction, Run, Evaluation, and configuration writes, first obtains a shared `InstallationMutationPermit` for its exact generation before taking any PostgreSQL workspace, aggregate, credential, material, ingress, authorization, policy, or external-effect lock. Restricted runtime roles have no direct product-table DML bypass; database enforcement bumps one transactional `InstallationMutationWatermark` row exactly once in every successful mutating transaction and rolls the bump back on failure. The global order is `InstallationMutationPermit -> declared aggregate guards in their existing canonical order -> exact evidence/material rows`; code may never request a permit while holding a database lock. Each command in the closed safety subset follows its declared receipt ordering. The default is `PreparedSafetyFence -> witnessed receipt -> narrowly granted database transition -> commit marker`; irreversible material/archive-key erasures instead require their database-visible preparation blockers before their fences, as defined below. Backup creation uses the exclusive permit directly. Freeze/cutover first enter witnessed `Quiescing`, refusing every new command, acceptance, provider effect/intent, admission, or dispatch. A narrow `DrainMutationPermit` is a closed completion-only authority for identities durably accepted, reserved, prepared, or `Dispatching` before that Quiescing commit. For one exact pre-Quiescing `MaterialKeyCreationIntent` or `CredentialKeyCreationIntent`, an unbound intent in `Reserved`, `ProvisionalCreated`, or `ProvisionalReceipted` may either resume only its fixed provisional-create/receipt/prepare path when its already-authorized bounded input remains lawfully available and reconstructable, or take its existing guarded pre-prepared abort, witnessed unbound erase, and terminal `Abandoned` receipt path. That latter path fabricates no `ContentPrepared`-only abort marker; for a credential it also performs the exact intent/version-bound `Preparing -> Cancelled` association closure. Prepared work may bind its exact marker; only ordinary `ContentPrepared` or `CredentialPrepared` work may instead take its exact guarded prepared-abort path, while `ResultPrepared` may only bind/finalize. A Bound intent may only promote/finalize its fixed `Live`, `Candidate`, or result state and never enters `Abandoned`. If accepted input cannot lawfully be reconstructed after crash, the drain truthfully takes the permitted abort path rather than synthesizing bytes or waiting forever. It may likewise finish an already-`ResultPrepared` EmbeddingJob's exact bind/attachment-promotion/space-corpus activation/`Succeeded`; lawful pre-dispatch cancellation or `FailedDefinite` cleanup; and the existing exact terminal receipt/`Unknown`, erasure, or unpaired-safety reconciliation. Every drain write uses only the precommitted fixed identity, owner/cause/ordinal, nonce, binding, provider/model, output set, and receipt/marker. It cannot reserve or accept a new identity/output/work, create a provider effect or intent, dispatch bytes, widen authority, add an unreserved output, reuse/switch credential/provider/model, or start a successor. Freeze waits through every Reserved, vault-created-before-receipt, receipted, prepared, bound, promotion/abort, result, credential, and accepted-effect/job boundary until terminal reconciliation, then freezes, or records its exact durable blocker/failure while leaving its permitted reconciler able to finish; it never strands an operation solely because Quiescing began. After effects, erasures, reconciliations, leases, and drain permits finish, the full exclusive permit is acquired. Read-only operations need no permit but cannot unwrap erasure-prepared keys or execute external work.

For avoidance of doubt, `Abandoned` terminalization follows only a committed guarded pre-prepared or ordinary prepared-abort branch and its witnessed unbound-erase receipt. A Bound intent has no abandon transition and may only execute its fixed promotion/finalizer path; a ResultPrepared output always binds and finalizes.

The closed v1 safety-fence set covers externally replayable ingress acknowledgement; external-effect `Dispatching`; vault key erasure and tombstone/Destroyed finalization; managed-backup archive-key deletion; every credential activation/rotation with exact new `Active` and prior `Retired`; credential `Revoked`; capability/grant revocation, expiry override, or narrowing; active authorization/policy replacement; access-token/session revocation; webhook-key rotation/revocation; and Connection/Trigger disabling or authority reduction. A security-affecting transition not represented by this closed set is denied. Guarded operations reject missing, wrong-installation/generation/epoch/kind/identity, stale, or forged receipts. Material erasure intentionally uses the stricter order `database MaterialErasurePrepared blocker -> witnessed PreparedMaterialKeyErasure fence bound to that preparation -> vault erase -> witnessed MaterialKeyErased receipt -> database tombstone/Destroyed finalization`. Managed-backup deletion uses the parallel order `database ManagedBackupDeletionPrepared blocker -> witnessed PreparedArchiveKeyErasure -> archive-envelope erase -> witnessed ArchiveKeyErased -> artifact/index removal plus ManagedBackupDeleted`. The supervisor cannot issue either irreversible fence without reading its exact committed preparation, so an eligibility/lease/blocker failure never becomes an unpaired deletion command; no key is erased before the database blocker exists. Preparation alone makes database use refuse, while an unpaired key-erasure fence also makes the supervisor refuse unwrap/restore until the live reconciler finishes. Reconciliation compares journal/witness/vault with PostgreSQL before readiness and continuously after faults. Thus no crash window admits a reference, hydrates bytes, activates a Candidate, dispatches with an identity in either prepared phase, or starts a restore from a deletion-prepared backup.

A managed backup is an encrypted PostgreSQL base backup plus a continuous, hash-chained archive of every required WAL segment from the base LSN, including explicitly witnessed timeline branches created by restore promotion or source resume. All canonical product and `ContentMaterialBytes` state is held in logged PostgreSQL tables; v1 permits no unlogged or external mutable product-content store, so Agent/Workflow/Settings/Artifact/message/Run changes and encrypted content are WAL-covered. Backup creation takes the exclusive installation permit, drains shared holders, establishes the base snapshot, records timeline/LSN, mutation watermark, material-key index digest and witnessed journal head, then releases the barrier into persisted lifecycle `Streaming -> Sealing -> Sealed -> DeletionPrepared -> ArchiveKeyErased -> Deleted`. Each backup set owns a random archive key and independently encrypted base/WAL objects; v1 does not share a decryptable ciphertext object or archive-key envelope between sets, so deleting one set cannot damage another retained set.

Every base chunk and WAL/timeline-history append obtains a set-bound `BackupArchiveAppendPermit` while holding the backup-set guard, requires lifecycle `Streaming`, expected immutable archive head, and absence of deletion/seal preparation, and records a unique staged-object intent before writing. The archiver writes/fsyncs an authenticated object under a non-manifest staging identity, then re-takes the guard to compare-and-swap the index/head and append the witnessed `WalArchiveCheckpoint`; only that commit makes the object restorable. It releases the permit afterward. Crash reconciliation either completes the exact staged intent or removes the orphan staging object before readiness; it cannot create a second ordinal/head. No index, object, or checkpoint append is permitted in `Sealing`, `Sealed`, or any deletion phase.

Restore acquisition is legal only while a backup set is `Streaming`. Under the backup-set guard, selection compare-and-swaps the current Streaming head to add one non-expiring `ManagedBackupRestoreHold`; `Sealing`, `Sealed`, `DeletionPrepared`, `ArchiveKeyErased`, and `Deleted` return a typed non-restorable conflict and cannot receive a hold, including through raw SQL. If restore acquisition wins before sealing, the hold keeps the set Streaming; if `Streaming -> Sealing` wins, acquisition creates nothing. Worker absence or a lapsed operational lease never releases a hold.

A hold releases only through one immutable witness-bound reason: complete `Lactiveinit` plus `TargetInitializationComplete`; complete `Ltargetabandon` plus `Lsource_resume`; `RefusedTargetDestroyed`, after the exact refused target and every target-only material/key/authority are irreversibly destroyed or sealed non-executable and its final evidence is archived; or `SalvageInstallationCompleted`, after the destructive metadata-only salvage obligations finish and the new InstallationId/witness/journal/key vault/activation plus its first verified Streaming backup exist. A bare `Refused` or `Salvaged` label, worker timeout, or operator database edit never releases it. The guarded supervisor operation verifies the terminal receipt, appends exactly one reason-bound release record, and advances witness and database state idempotently across crashes. Successful activation or abandonment leaves the set Streaming on the surviving active generation. RefusedTargetDestroyed or SalvageInstallationCompleted instead proves zero append permits and, in the same backup-set guarded transaction that releases the hold, advances the unsafe old set to `Sealing`; it can never be selected in the release-to-seal interval and is retained only as a non-restorable sealed forensic set until its governed deletion.

Age/count/manual deletion can only persist a `DeletionRequested` while a restore hold, staged append, or archive permit exists; it cannot advance lifecycle. When deletion becomes eligible and the guard proves no hold, one transition `Streaming -> Sealing` refuses new append permits, drains/reconciles every existing permit and staged intent, records the exact final branch/head, and then commits `Sealed`. `Sealed` is deletion staging, not a retained restore source. Only a hold-free `Sealed` set can commit immutable `ManagedBackupDeletionPrepared`, which prevents every new append/verification/restore acquisition and makes the set unavailable. Only for that preparation may the supervisor witness `PreparedArchiveKeyErasure`, destroy the exact archive-key envelope, and return `ArchiveKeyErased`; finalization requires the receipt before removing the frozen manifest/base/WAL objects/indexes and appending `ManagedBackupDeleted`. A crash in any seal/deletion phase remains visibly `seal_pending` or `deletion_finalizing`, and the live reconciler resumes the same head/state idempotently. Automatic retention must establish another verified Streaming set before sealing the last one; an explicitly confirmed manual deletion may leave no managed backup and reports that truthfully. Per-material key erasure independently makes that material unrecoverable even inside otherwise retained base/WAL ciphertext.

Restore is the persisted state machine `RestoredOffline -> SourceCatchUp -> SourceQuiescing -> SourceFrozen -> OverlayApplied -> MaintenanceValidation -> TargetQuiescing -> CutoverFrozen -> TargetActivating -> Active`, with explicit `Refused`, `Abandoned`, and irreversible `Salvaged` outcomes. `TargetForkPrepared` and `TargetForkCommitted` are witnessed lineage substates inside the `SourceFrozen -> OverlayApplied` edge, not hidden alternate activation states. `TargetActivating` is the point-of-no-return whose single witness CAS binds the immutable TargetActivationPlan digest and new activation epoch while moving the sole lease to target: public product services remain disabled while crash-resumable target-only initialization finishes, source resume is no longer an outcome, and time-based qualification expiry cannot rewrite the pinned plan. Restore never overwrites or mounts the active database. The supervisor restores the selected Streaming base/WAL set into new empty volumes as a PostgreSQL recovery target with no application listener or target write capability, assigns the prospective DatabaseGenerationId, validates backup/fingerprint-key/material-key/witness continuity, and continuously replays authenticated source WAL while the source remains active. Because the target is still physical-recovery read-only, it cannot diverge while source changes are being captured.

Before target maintenance may begin, the supervisor witnesses `SourceQuiescing`, refuses all new source mutating ingress/scheduler/worker work, acceptance, provider effects/intents, admissions, and dispatch, and drains ordinary shared permits while WAL follow continues. Exact pre-existing `Dispatching` effects, accepted reservation/prepared material or credential intents, `ResultPrepared` EmbeddingJobs, lawful pre-dispatch cleanup, and already-prepared erasures/fences may receive only their section-11.6 completion-only drain operations; absence of worker presence never shortcuts that wait. The reconciler uses the same fixed identities and cannot emit new bytes, work, output, authority, or routing. Once all accepted effects/jobs, intent/result/credential reconciliations, erasures, fences, provider leases, and drain permits are terminal—or an exact persistent blocker/failure is durably reported with its lawful completion path still available—the supervisor acquires the exclusive source permit. It remains held while one source transaction records `SourceFrozen`, `Lfreeze_commit`, and the final mutation watermark; its commit marker is fsynced; PostgreSQL then performs a controlled clean shutdown; and the archiver durably covers every resulting segment through final shutdown-checkpoint/end-of-WAL `Lfreeze`. The supervisor seals the source data volume against writes/restart and only then witnesses `SourceFreezePoint = (source generation, timeline, Lfreeze_commit, Lfreeze, mutation watermark, journal head Hfreeze, admission/throttle digest)`. Restart reconciliation can only finish commit/archive/shutdown/seal and advance that same freeze, never reopen writes. The witness thereafter refuses every source mutation/drain permit, safety receipt, process start, volume write, credential unwrap, ingress acknowledgement, or dispatch; diagnostics come from the witnessed snapshot/recovery target, not a running source database. The target replays exactly through `Lfreeze` and proves identical watermark/schema/material-index/admission digests and complete WAL ancestry. The supervisor then witnesses `TargetForkPrepared` for the prospective child generation and parent `Lfreeze`, promotes PostgreSQL with every application listener and ordinary mutation permit still disabled, waits for the actual new timeline/history file, starts target WAL archiving, and uses the sole witness-bound bootstrap writer for the first post-promotion transaction: it records the new DatabaseGenerationId, parent generation/timeline/`Lfreeze`, actual target timeline, and inherited watermark. That transaction is flushed and archived through `Lfork`, after which the witness may advance to `TargetForkCommitted`; no overlay or maintenance mutation is permitted earlier. A crash in this handshake resumes or seals the same prepared child and never mints a second fork. Missing coverage refuses progression. Every cancellation after SourceFrozen—including before TargetForkPrepared and after an unpromoted TargetForkPrepared—uses the single phase-aware abandonment protocol below; no path may mark a restore/child `Abandoned` separately from `SourceResumePrepared`.

Only after witnessed `TargetForkCommitted`, one atomic idempotent `RestoreSafetyOverlay` reconciles every fence through `Hfreeze` against the WAL-restored database: it completes unpaired material preparations/erasures/tombstones; verifies credential Active/Retired rotation, Revoked and Destroyed state; installs ingress idempotency fences; applies every security reduction; and marks any ambiguous effect plus its causal Run/Step/Job `restore_reconciliation_required`. Ordinary post-backup mutations require no reconstruction from the journal because WAL already reproduced them through the witnessed source freeze point. The overlay quarantines every still-nonterminal Run, Step, QualificationJob, trigger delivery, sweep, remote invocation, and protocol binding and never auto-resumes it; closes restored Trigger enable epochs; records pending schedule/outbox observations as `restore_quarantined` without Run creation; and installs effective `KeepForever`. Every restored session, access token, capability grant, policy activation, webhook key, and cached authorization is invalid under a new `RestoreSecurityEpoch`; Connections and Triggers remain disabled until explicit target-epoch reissue/enable.

Only after `OverlayApplied` may the supervisor mint one target-bound `RestoreMaintenanceEpoch`. It exposes an authenticated loopback restore console and permits only database reconciliation, target-generation security reissue, monotonic reduction of inherited authority, creation/qualification of at most one non-current RestoreCandidate per permanent credential guard, and exact credential/model qualification through a dedicated maintenance executor. A later epoch reuses/requalifies that Candidate or explicitly cancels and finishes destroying it before another can be created. Public product/protocol listeners, schedulers, triggers, downloads, general workers, retention sweeps, remote-agent work, ordinary Runs, inherited-authority broadening, ordinary credential activation/rotation, and any pre-TargetActivating `Active`/`Retired` credential event remain off. New credentials/tokens/grants are target-generation-only. Revocation, policy/capability narrowing, or material erasure of an identity inherited from source must first append a witnessed `CrossGenerationSecurityReduction`/material-erasure fence, so it can never disappear on target abandonment. Before every maintenance provider probe, a supervisor `CrossGenerationMaintenanceBarrier` keyed by Connection and affected security identities proves the source process is stopped, its volume is sealed, its generation is witnessed frozen with zero provider leases, and its final WAL is fixed at `Lfreeze`; advances the target overlay through the current cross-generation witness head; and then remains held through target live authorization, policy/credential revalidation, admission, and `Dispatching` commit. The probe uses the WAL-copied PostgreSQL rolling-window/throttle state, fresh nonces/intents/effect IDs, target InstallationMutationPermit, witnessed `MaintenanceProviderDispatch`, and no-retry-after-Dispatching. There is one admission namespace and no stale source revocation can race target disclosure. An attempted source mutation/dispatch after freeze receives no permit and may append only supervisor-side `FrozenGenerationRefusal` control evidence with no database receipt; any source process start, data-volume/WAL advance, operation fence/mutation receipt, or credential unwrap after `Hfreeze` without the exact phase-appropriate witnessed `SourceResumePrepared` is a hard safety breach that refuses both normal target activation and source resume.

Final activation first witnesses `TargetQuiescing`, refuses new maintenance commands/probes, and allows only exact DrainMutationPermits until every target provider effect is definite/Unknown, every prepared erasure/fence is reconciled, and every lease drains. It then takes the exclusive target permit and every affected credential guard, proves zero-or-one nonterminal RestoreCandidate per slot and requires each selected one to be CutoverReady with currently unexpired evidence, commits `TargetFrozen` plus the complete immutable proposed TargetActivationPlan, flushes/archives both target state and plan through attempt-bound `Ltargetfinal`, appends/witnesses `CutoverFrozen`, and captures attempt-bound `Hfinal`. It verifies `(Hfreeze, Hfinal]` generation-aware: committed target entries match exact receipts, source control/refusal evidence is harmless but any source operation fence/receipt/WAL advance is a hard refusal, and target timeline/mutation watermark plus plan digest are archived exactly through `Ltargetfinal`; it also proves parent lineage at `Lfreeze`, source sealed, zero leases, closed dependencies, and network-free release invariants. A repairable target-only validation failure—including stale qualification or duplicate slot occupancy—appends/witnesses `CutoverRefused`, invalidates every old maintenance/target permit, and opens a new RestoreMaintenanceEpoch before the monotonic event-derived view again shows `MaintenanceValidation`; source remains sealed. A lineage, witness, or post-freeze-source safety breach instead enters `Refused` and cannot use normal activation or source-resume abandonment.

The separately confirmed `Abandon restore and resume source` is one phase-aware, externally idempotent protocol available only before `TargetActivating`. A recovery-only target before TargetForkPrepared is stopped/discarded. A TargetForkPrepared but unpromoted child must additionally prove recovery mode and absence of any child timeline, transaction, unwrap, admission, or effect. A promoted child repeats target quiesce/drain, cancels and completes guarded Candidate erasure for every target-only credential plus every target-only token/material/key, commits `TargetAbandonedSealed`, cleanly stops the target, flushes/archives the abandoned branch through `Ltargetabandon`, and witnesses its final mutation watermark and journal head. All phases compute `source_resume_not_before` from target admissions/throttle/effect terminals, with the empty promoted-target set defined as the SourceFreezePoint database timestamp, and collect the closed set of post-`Hfreeze` cross-generation reductions/erasures. Exactly one witness CAS then atomically records `(restore/prospective child = Abandoned, SourceResumePrepared = {bound, reductions, phase evidence})`; neither half can exist alone, and a crash before it leaves the prior retryable phase. That receipt permits the source to start only in supervisor-only mode with product roles, unwrap, admission, dispatch, and ordinary mutation still disabled. A narrow idempotent `SourceResumeSafetyOverlay` applies every inherited revocation, policy/capability narrowing, and material preparation/erasure fence under the source generation, flushes/archives the resulting source WAL through witnessed `Lsource_resume`, and refuses any target-only broadening or ordinary target product state. Only after that overlay is complete and source PostgreSQL `clock_timestamp()` is strictly beyond the bound may the narrowly granted transaction append `SourceUnfrozenAfterAbandon`; public permits return only after the witness confirms it. Thus no crash can strand an already-Abandoned child without its resume authority, target probes cannot be forgotten and followed by source over-admission, and abandonment cannot resurrect authority or managed material.

If validation passes, one witnessed compare-and-advance verifies the archived plan digest, enters irreversible `TargetActivating`, binds that exact TargetActivationPlan to the new InstallationActivationEpoch, moves the sole lease to target, and seals source permanently while every public listener/scheduler/general worker remains disabled. The target activation executor processes exactly the plan's optional candidate entry per slot—retiring its recorded inherited `Active` prior or preserving its witnessed `Revoked`/`Destroyed` prior—then completes only the plan's target security/readiness entries, recording idempotent progress after each step. It performs no network probe, TTL check, dependency rediscovery, alternative-candidate selection, or plan rebuild after the CAS. It flushes/archives through `Lactiveinit` and witnesses `TargetInitializationComplete`; a crash or later qualification expiry can only resume the same plan. Only that receipt advances to `Active` and releases public product permits. Subsequent ordinary Run acceptance still requires current unexpired qualifications. No interval has two writable generations, admission authorities, or an uncaptured source commit.

If the base/WAL chain, timeline/LSN or mutation watermark, journal, signing key, independent witness, `FingerprintKeyId`/key proof, material-key state, archive envelope, or InstallationId continuity is absent, discontinuous, corrupt, contradictory, or behind its required checkpoint, normal readiness and activation are refused rather than guessed. If the archive cannot be authenticated/decrypted, restore ends `Refused` with no import. Hard `Refused` remains ineligible for activation and source-resume abandonment, but an explicitly confirmed crash-resumable `Destroy refused target` finalizer may erase every target-only key/material/authority, stop and remove target volumes, archive the terminal attempt evidence, and witness `RefusedTargetDestroyed`; only that receipt may release its backup hold. For an authentic/decryptable base whose safety or WAL continuity is insufficient, the only alternative is explicitly confirmed destructive structural salvage: erase every available restored material and comparison key, remove all content/credential ciphertext, append tombstone/destruction evidence, invalidate ingress/security and idempotency authority, disable executable configuration, quarantine work, and create a new InstallationId/FingerprintKeyId/witness/journal/key vault/activation epoch before metadata-only APIs. Only after the new installation is active and owns its first verified Streaming backup may the supervisor witness `SalvageInstallationCompleted` and release the old hold. A crash before either terminal receipt resumes the same cleanup and never releases early. Settings requires backup ID plus typed confirmation and links catch-up/freeze/overlay/maintenance/refusal/target-destruction/abandon/salvage/key deletion/hold release/cutover to immutable Audit evidence.

## 12. Failure semantics and recovery

The user must be able to distinguish configuration errors, authentication/authorization denial, invalid input, dependency unavailability, execution failure, cancellation, human-input pause, unknown external outcome, and a truncated stream.

- LM Studio unavailable: readiness identifies the provider; a new dependent effect either waits visibly for pre-dispatch admission/dependency readiness within its configured queue bound or fails definitely before dispatch. A provider call is never automatically replayed after `Dispatching`. Existing unrelated pages continue to work.
- OpenAI-compatible Connection unavailable or unqualified: the exact Connection/Model revision and failed prerequisite are visible; no fallback provider receives the prompt implicitly.
- Model POST/Embeddings timeout, EOF, truncated stream, or crash before receipt/result-prepared commit: the shared external effect becomes deadline-gated and may be adopted as `Unknown` by one recovery winner; no automatic replay or success is inferred. Prepared request evidence without `Dispatching` never claims provider delivery. An EmbeddingJob crash after durable `EmbeddingJobResultPrepared` instead resumes provisional-key bind/corpus activation without another provider call and cannot report `Succeeded` first. After `Dispatching`, the exact request remains current `Complete`/reconstructable while retained even though an unresolved outcome is `Unknown`; lawful erasure later changes only current reconstruction to `Expired`, not the outcome. A pre-erasure current `Incomplete` blocks readiness and release qualification, disables inspection and dispatch, and is never displayed as retention; its historical check remains visible if the exact implementation later recovers current `Complete`. A QualificationJob or unresolved EmbeddingJob then reaches terminal `InconclusiveUnknown`, scheduled refresh stops, and only the acknowledged operator action may create an entirely new job/effect/request-evidence identity. For an ordinary Run, only the separately authorized duplicate-risk command may create the linked next Step attempt; for an EmbeddingJob, only the separately authorized duplicate-charge command may create its linked new job. Neither changes its predecessor `Unknown` outcome or runs automatically after `Dispatching`.
- Transition-rebuild `InconclusiveUnknown` is the bounded exception to the ordinary EmbeddingJob successor rule. While its exact version is current/nonstale, only the same-version command may create one fresh physical successor for the exact immutable `TransitionBatchId`/ordered recipe list/target tuple after predecessor-intent reconciliation. On a new version, a terminal latest no-direct-successor head is classified at recipe granularity: each old recipe/input has exact mapped current new recipe/input or immutable `NoLongerRequired`; only surviving mapped recipes form the dedicated ordered-subsequence carry batch and acknowledgement blocker. A nonterminal overlapping predecessor instead owns one target-bound dedicated immutable barrier batch containing only its preserved-order mapped overlap. Its append-only derived lifecycle is `AwaitingPredecessorTerminal -> ResolvedToCarry | ResolvedSatisfiedExisting | ResolvedDefinite | NoLongerRequired | Superseded`; exactly one current/open barrier exists for its predecessor physical-attempt/logical-batch lineage. Canonical guard ordering serializes stale-target supersession with terminal classification: supersession with overlap terminalizes only the obsolete batch/mapping as `Superseded`, records per-recipe exact mapping or `NoLongerRequired`, and links one fresh preserved-order current barrier; no surviving overlap instead closes the old barrier/batch `NoLongerRequired` with no successor. Superseded history is never dispatched or classified. The terminal classifier resolves only that latest barrier; `Dispatching` remains deadline-gated, ResultPrepared only finalizes, and it converts/links the exact batch to carry or produces exact `SatisfiedExisting`, definite release, or `NoLongerRequired` with no provider invocation or silent batch move. Candidate abandonment terminalizes only the current open dependent barrier/carry and only a current nonterminal Candidate-bound transition as `Failed(reason=candidate_abandoned)`, preserving terminal `Stale`/`Failed` history or recording `candidate_work_closed` when none exists, after underlying effect/lease/intent reconciliation; neither transition path resolves a current/default tuple, reuses an ambiguous result/vector, or retries automatically;
- Retrieval generation changed after a definite provider response: if the captured fence no longer revalidates under the shared generation guard, one transaction appends the definite provider receipt, immutable safe `RetrievalGenerationChanged` observation, and local `FailedDefinite` with no canonical result/vector/digest. The job UI distinguishes this local failure from the successful provider effect; crash before that receipt transaction remains the ordinary deadline-gated `Unknown`/`InconclusiveUnknown` path. Only the confirmed authorized one-successor `Retry retrieval on current generation` command can create a fresh current-tuple job/fence/effect/MRE after that exact reason; no stale generation/vector or automatic retry is used.
- Credential rotation or revocation: only a Bound/finalized Candidate obtains Connection plus every required Model qualification before the slot CAS; a `credential_preparing` association cannot resolve or qualify. Future Runs and EmbeddingJobs pin the activated revision, already accepted nonterminal owners may continue on the retired revision, and revocation blocks every subsequent pre-dispatch transaction. A revoke racing final dispatch either commits first and refuses/zeroizes the lease before `Dispatching`, or commits after the already ordered `Dispatching`; there is no check/send gap. A failed staged activation leaves the old revision and all its effective bindings current. Emergency revoke may deliberately make new resolution unavailable. Stale leases are refused before bytes leave the process, while completed evidence retains only the prior credential revision ID.
- Credential transition/rotation blocked: a `Preparing` pre-live abort first appends only the guard-ordered intent-bound association `Cancelled` event and `CredentialAbandonPrepared`; the existing non-publishable association remains an occupancy blocker until its witnessed unbound erase makes the intent terminal `Abandoned`. It cannot produce a Candidate, qualification, or `ErasurePrepared`. For every candidate-bound embedding qualification over a live old corpus, an incomplete/stale/expired `rotation_staged` exact-space transition refuses the whole rotation or RestoreCandidate activation plan; old active query service remains until the single guarded handoff, and emergency revoke may instead leave it unavailable without inventing a transition. A crash resumes the same association, transition, projection-recipe set, target generation, or archived plan entry and never mixes spaces.
- Credential destruction blocked: no material or lifecycle state changes; the response/UI names the exact preparing/pending association, CredentialKeyCreationIntent, QualificationJob/EmbeddingJob, effect, queue/admission lease, material-key intent, slot, or Retired-Run/EmbeddingJob dependency. A pre-live credential intent may only complete its fixed receipt/bind/finalizer or guarded CredentialAbandonPrepared removal plus witnessed unbound erase; it never exposes a Candidate. A failed first or staged-rotation bound Candidate uses only the activation-serialized abandon-and-destroy transition; its first transaction either atomically closes Pending as Cancelled plus commits ErasurePrepared, after which every use is permanently refused and the witnessed finalizer erases the key/removes ciphertext, or activation wins first and preparation changes nothing. A crash leaves visible `credential_preparing`, `credential_abandon_finalizing`, or `erasure_finalizing` state for the live reconciler; metadata/Audit remains and an idempotent replay returns the durable receipt, abort, preparation, or final receipt.
- Retention sweep failure or worker loss: committed source/vector tombstones, persisted generation revocations, and durable invalidation events remain valid; uncommitted deletions roll back. The job exposes its safe failure/checkpoint, stale workers fail the epoch revalidation, and a deadline-gated worker resumes without skipping or double deletion. A policy revision change cancels the old job between batches and cannot restore bytes or vector generations already deleted under the prior confirmed policy.
- Worker unavailable: accepted queued work remains durable and visible; readiness and Home show stalled leases without declaring absent workers dead before the configured deadline.
- Browser/SSE disconnect: Run continues and the client replays from its last durable ordinal while retained; a completed tombstoned prefix produces the exact pre-stream AG-UI `409`/`vestrace.cursor_expired` contract and the wrapper reads canonical truth without reconnect looping.
- Server restart: accepted protocol bindings and streams are reconstructed from PostgreSQL.
- Lost A2A response: invocation becomes `Unknown` and reconciliation starts; no blind redispatch occurs.
- Slow client: bounded buffering applies; reconnect resumes from a durable cursor.
- Invalid resume or stale approval: no effect executes; the protocol returns a specific error and audit retains the denial.
- Artifact verification failure: content remains quarantined and cannot reach a model, tool, or remote agent.
- Restore failure or unsafe rollback: the active database is never overwritten. Every cancellation after SourceFrozen, whether before fork, after an unpromoted TargetForkPrepared, or after maintenance, uses the same atomic `Abandoned + SourceResumePrepared` witness transition; before that CAS the prior phase remains retryable, and after it the source-resume overlay is authorized. Source resume first applies and archives every witnessed cross-generation security/material reduction while rejecting target-only broadening, so abandonment cannot resurrect authority or content. `TargetActivating` is explicitly irreversible and can only execute the already archived/pinned TargetActivationPlan; crash duration or qualification TTL cannot create a new failure mode after its CAS. Missing/corrupt base, WAL, generation lineage, journal, witness, signing key, FingerprintKeyId/proof, or material/comparison-key continuity refuses activation or permits only confirmed material-free salvage from an otherwise decryptable archive. RefusedTargetDestroyed and SalvageInstallationCompleted cleanup/release operations resume idempotently after crashes and never release a hold from a bare terminal label. Every overlay, maintenance, CutoverRefused, refusal, cleanup, abandonment, TargetActivating, and cutover transition remains evidenced, and no public restored worker, credential, content download, or protocol listener starts before `TargetInitializationComplete`.

## 13. Migration and compatibility

All schema changes use new forward-only migrations; existing migrations are never edited. New protocol and product tables receive RLS policies, grants, indexes, unique idempotency constraints, and raw-SQL enforcement tests in the same slice that introduces them.

Migrations create immutable `no_auth_binding_revisions` one-to-one with auth-`None` ConnectionRevisions and immutable `qualification_target_bindings` one-to-one with QualificationJobs. CHECK constraints, composite FKs, and one-of uniqueness enforce exactly one credential branch (exact CredentialRevision and slot/guard lineage) or no-auth branch (exact NoAuthBindingRevision), never both or neither; auth-required revisions cannot own a no-auth binding, and the no-auth branch cannot carry a slot, credential, guard, lease, material, or secret. Backfill deterministically creates no-auth bindings for provable auth-`None` legacy revisions; ambiguous legacy rows remain `needs configuration` and no credential identity is fabricated. The same target binding is FK-required by every ModelsList/chat/Embeddings probe effect, q1 ordinal-90 MRE, dispatch record, and Connection/Model qualification provenance. Raw SQL rejects invalid XOR combinations, sentinel slots, cross-binding, or altered historical target data.

Forward migrations create `connection_execution_guards` with exactly one permanent `(workspace, ConnectionId)` row per stable Connection. Connection creation and guard insertion are one transaction; deterministic backfill creates one row for every existing Connection before any executable ConnectionRevision, NoAuthBindingRevision, CredentialSlot, QualificationTargetBinding, qualification, snapshot, or provider-work row may exist. Deferred FKs and uniqueness require that guard for all such rows, readiness/startup refuses a missing or duplicate guard, and runtime roles cannot mutate, delete, reuse, or create a sentinel CredentialSlot through raw SQL.

The existing skeletal A2A interoperability table is treated as untrusted legacy shape. A migration copies only rows that pass the new invariants, records rejects for operator repair, and does not reinterpret opaque payloads as proved remote outcomes.

Existing agent/workflow/trigger/connection/model/evaluation/settings rows are migrated through explicit validators. A row that cannot become executable remains visible as `needs configuration` and cannot be published. Existing empty Runs are retained as historical records with truthful incomplete status; they are not deleted or silently given synthetic Steps. Legacy workflow-execution rows with a valid owning Run become read-only projections rebuilt from that Run's events. Rows with `run_id IS NULL`, caller-asserted outcomes, or irreconcilable step history remain visible in a separate legacy-history view as unverified incomplete records and can never drive Run state, release evidence, or new execution. Public write routes to that legacy store are removed at cutover.

The existing `providers`, `models`, and `connections` rows are not parallel execution authorities. Forward migrations create stable Connection/Model aggregates with their exactly-one permanent `ConnectionExecutionGuard` rows, append-only configuration revisions, `qualification_jobs` plus append-only job transitions, immutable `connection_qualification_revisions` and `model_qualification_revisions`, `discovered_models`, and capability-specific `workspace_model_defaults` that reference a stable ModelRevision plus required capabilities rather than an expiring qualification. `provider_call_details` and immutable `model_request_evidence` are one-to-one typed extensions of `external_effect_intents`; the latter has only `ModelsList`, `ChatCompletions`, and `Embeddings` request-shape variants.
