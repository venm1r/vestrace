# Vestrace State Engine Follow-up Documentation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Convert the approved State Engine reconciliation into independent, reviewable amendments and ADR/design packages without starting Rust implementation, migrations, runtime services or infrastructure work.

**Architecture:** Treat `Vestrace State Engine` only as an internal durable-state boundary spanning existing Horizons. Prepare one documentation package per independent concern, preserve current ownership boundaries, and require a separate written approval gate before any package receives a code implementation plan.

**Tech Stack:** Markdown, existing Vestrace v0.1 and Harness v0.2 specifications, Horizon H1–H11B plans, repository search with `rg`, Git diff validation and GitHub draft PR review.

## Global Constraints

- This plan is documentation-only.
- Do not create or modify Rust source files, Cargo manifests, SQL migrations, schemas generated by code, CI workflows, Docker configuration or runtime configuration.
- Do not create `H12 State Engine`, a second event store, a second execution runtime, a generic mutable `Task/Action/Attempt` hierarchy or a direct-SQL agent API.
- H1 remains the sole owner of `AgentRun`, `RunStep`, `RunEvent`, checkpoints, leases and logical replay.
- H2 remains the sole owner of final authorization, approvals, authorization tickets, budgets and quotas.
- H6 remains the sole owner of Artifact and ContextSnapshot bytes, provenance, mounts, export policy, retention, purge and memory consolidation.
- H8 remains the sole owner of secret material, secret references, connection credentials and credential leases.
- H10 telemetry and operational projections never become authoritative Run state.
- H11 public interfaces never expose arbitrary SQL or storage credentials.
- `Unknown` never grants permission to retry an external action.
- A hash, identifier, reference or mount handle never grants read permission.
- Hidden chain-of-thought and provider reasoning traces are never persisted or exported.
- Every independent concern gets its own design document and its own review gate.
- A code implementation plan may be written only after the corresponding design is explicitly approved.
- Each documentation branch starts from the current `main` and contains only the files belonging to that concern.

### Task 3: Define durable event schema compatibility

**Files:**
- Create: `docs/superpowers/specs/2026-07-31-vestrace-event-schema-compatibility-adr.md`
- Modify: `docs/superpowers/plans/2026-07-31-vestrace-h1-durable-run-core.md`
- Modify: `docs/superpowers/plans/2026-07-31-vestrace-h7-conversations-channels-triggers.md`
- Modify: the H11 public API plan that owns event schemas and public event contracts.

**Interfaces:**
- Consumes: H1 `RunEvent`, H7 public events, H11 generated schemas and existing immutable-journal rules.
- Produces: stable event kind rules, per-kind schema versions, generated schemas and pure read-time upcasters.

- [ ] **Step 1: Write the compatibility ADR**

The ADR must define this envelope:

```text
EventEnvelope
├── event_id
├── stable_event_kind
├── schema_version
├── aggregate_or_reference_ids
├── sequence_or_cursor
├── occurred_at?
├── recorded_at
├── payload
└── payload_hash
```

Required rules:

1. Each stable event kind starts at schema version `1`.
2. Existing event-kind semantics never change silently.
3. A breaking payload change creates a new schema version or a new event kind.
4. Generated JSON Schemas live in versioned repository paths.
5. Upcasters are pure read-time functions and never rewrite journal rows.
6. Unsupported future schemas fail closed with a stable compatibility error.
7. A model or extension cannot register arbitrary runtime event kinds.
8. Internal Rust compatibility and external serialized compatibility are tested separately.

- [ ] **Step 2: Amend H1, H7 and H11 ownership statements**

H1 owns logical Run event ordering and persistence. H7 owns interaction/public-event semantics. H11 owns external schema publication and transport compatibility. None may create a mutable runtime schema registry.

### Task 6: Design workspace envelope encryption

**Files:**
- Create: `docs/superpowers/specs/2026-07-31-vestrace-workspace-envelope-encryption-design.md`
- Reference: H6, H8 and H10 documents.

**Interfaces:**
- Consumes: H8 `SecretBackendPort`, H6 blob storage and purge lifecycle, H10 capture and audit requirements.
- Produces: workspace-scoped key hierarchy, rotation, erasure and backup/restore contracts for sensitive bytes.

- [ ] **Step 1: Define the key hierarchy**

```text
workspace KEK reference       -> H8 SecretBackendPort
per-object/per-generation DEK -> wrapped by workspace KEK
ciphertext                    -> H6 blob store or bounded encrypted payload store
searchable metadata           -> minimized classified PostgreSQL projection
```

Define key generation identifiers, algorithm-suite version, nonce requirements, authenticated metadata and rotation ownership without embedding secret bytes in PostgreSQL.

- [ ] **Step 2: Define encryption scope**

Encrypt:

- optional context-capture bytes;
- sensitive Artifact and representation blobs;
- sensitive diagnostic captures;
- bounded non-indexed side payloads;
- export content when export policy requires it.

Do not opaquely encrypt:

- identifiers, revisions and RLS ownership columns;
- lifecycle state;
- operation fingerprints and content-free audit facts;
- deterministic uniqueness/concurrency fields;
- searchable text/vector source without a separate redacted projection strategy.

- [ ] **Step 3: Define rotation and cryptographic erasure**

Rotation creates a new key generation and background rewrap or re-encryption work with resumable progress. Cryptographic erasure destroys the wrapped DEK or KEK generation and retains a content-free tombstone. Historical hashes must not change silently.

- [ ] **Step 4: Define backup and failure behavior**

Include missing key material, partially completed rotation, restore into a deployment without the old KEK, search projection cleanup after erasure and cross-workspace dedup disabled by default.

- [ ] **Step 5: Self-review and commit**


### Task 7: Design explicit cross-workspace memory sharing

**Files:**
- Create: `docs/superpowers/specs/2026-07-31-vestrace-cross-workspace-memory-sharing-design.md`
- Reference: v0.1 memory design, H2, H6, H8, H10 and H11 documents.

**Interfaces:**
- Consumes: v0.1 workspace-bound Memory/MemoryRevision, H2 authorization and H6 context assembly.
- Produces: explicit `MemoryShareGrant` and `MemoryMount` design without weakening RLS or redefining `global`.

- [ ] **Step 1: Preserve the existing v0.1 invariant**

The design must state that `global` continues to mean the entire current workspace. Cross-workspace visibility never arises from a scope value, matching UUID, content hash, user identity or physical deduplication.

- [ ] **Step 2: Define the sharing identities**

Use stable conceptual contracts:

```text
MemoryShareGrant
├── source_workspace_id
├── target_workspace_id
├── allowed_memory_revision_ids or approved query scope
├── maximum_classification
├── purpose
├── valid_from / valid_until
├── granted_by
├── policy_decision_id
└── revocation state

MemoryMount
├── target_workspace_id
├── share_grant_id
├── read_only = true
├── mounted_namespace
├── refresh policy
└── current source revision manifest
```

Write permission is out of scope for the first design. A target workspace may propose a local derived memory, but it cannot mutate the source memory.

- [ ] **Step 3: Define retrieval, provenance and revocation**

Mounted memory must preserve source workspace, Memory ID, exact revision, classification, source provenance and grant ID. Revocation prevents new retrieval immediately and defines policy for already captured ContextSnapshots and derived local candidates.

- [ ] **Step 4: Define privacy and existence-oracle protection**

A denied target cannot discover that a source memory, hash or share exists. Search, embeddings and counts must be filtered before ranking and aggregation. Audit records remain content-free.

- [ ] **Step 5: Add acceptance scenarios and commit**

Include read-only share, expiry, revocation during an active Run, source revision supersession, target-derived candidate, denied high-classification memory and source deletion/purge.

