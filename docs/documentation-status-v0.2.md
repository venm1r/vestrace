Running the database-backed suites against a real PostgreSQL then exposed six defects that an unset `DATABASE_URL` had been masking, all now fixed and recorded in the registry. The most serious: migration 0112 left `run_checkpoints.resume_cursor` NOT NULL with no default and unwritten, so no checkpoint could ever be inserted and checkpoint-based recovery could not work — corrected by forward migration `0131_drop_vestigial_run_checkpoint_columns.sql`. The Q11 recovery repository compared payload timestamps against their microsecond-precision indexed columns at nanosecond precision, so no record written with a real clock reading could be read back. `PgRunCommandCommitter` never wrote `finished_at`, `PgRunRepository` discarded it on read, and `PgRunRecoveryStore::replace_projection` wrote an incomplete projection. The run worker's randomly generated `WorkspaceId` was replaced by polling over an explicit top-level `workspaces` list shared with recovery.

`FaultInjectionEnvironment::ProviderSandbox` still has no driver, but both runtimes now refuse it instead of letting a deployment declare that isolation and execute in a host process. The full workspace suite is green against a live PostgreSQL 17 (674 passed, 0 failed). That proves the schema and repository paths agree; it does not qualify a deployment, and no live provider, container image, or environment has been qualified.

This adds the second custody adapter, `mounted-secret-store`, and the distinction that makes it not a rename is the whole point: with `local-file` the provider, key id, version, purpose, scope and algorithm all live in a `KeyReference` the **caller constructed**, so every check compares the caller's word against the caller's word, while here those five facts are declared by the store (`<root>/<key_id>/{scope,purpose,algorithm}`, `<version>/{state,private.pkcs8,public.bin}`) and read from it — the request is checked against a statement the caller cannot edit, so **the adapter can refuse the caller**, and review confirmed every substantive refusal compares a store-read value against a caller-supplied one.
