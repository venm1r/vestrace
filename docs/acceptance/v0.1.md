# v0.1 Acceptance Procedure

## Overview

This document describes the acceptance criteria and verification procedure for vestrace v0.1 — the cognitive runtime foundation.

## Automated Acceptance Tests

All acceptance tests live in `tests/v01_acceptance.rs` and run without external dependencies (no database, no network, no API keys).

### Run the full suite

```bash
cargo test -p vestrace-integration-tests --test v01_acceptance
```

### Test coverage

| Test | Scenario |
|------|----------|
| `v01_full_lifecycle_acceptance` | Complete cycle: workspace → models → agents/skills/workflows → events → memory extraction/activation → retrieval/context pack → Balanced routing → model/step execution → evaluation → outcome memory derivation → new-session retrieval → stale knowledge revision → old knowledge absence verification |
| `v01_security_foreign_workspace_denial` | Memory source from a foreign workspace event is detected as cross-workspace |
| `v01_security_restricted_remote_provider_rejection` | Remote model rejected when data sensitivity is Restricted and no transfer approval |
| `v01_security_self_elevation_denial` | Principal self-approving a permission change is detected (approver == requestor) |
| `v01_security_hard_purge_requires_approval` | Hard purge requires a valid ApprovalRecord with a different approver; memory soft-delete works after approval |
| `v01_degraded_embeddings_and_reranker_disabled` | FTS-only retrieval succeeds with `degraded: true` and warnings when embeddings and reranker are unavailable |
| `v01_degraded_model_unavailable_fallback_used` | When the selected model becomes unavailable, `next_fallback()` returns a valid alternative and `fallback_used` is set |
| `v01_audit_trail_records_security_events` | AuditEvent captures principal, action, resource_type, and payload for security-sensitive operations |
| `v01_capability_enforcement` | Capability checks correctly deny or allow principals based on their granted capabilities |

## Deterministic Provider Fixtures

Fixtures live in `tests/fixtures/openai-compatible/`:

- `chat_completion.json` — deterministic chat completion response from local fixture model
- `embeddings.json` — 80-dimensional embedding vector (no external API call)
- `evaluation.json` — evaluation response with quality_score, relevance, coherence

These fixtures are compiled into the test binary via `include_str!` and require no network access.

## Manual Acceptance Procedure (Docker Compose)

### Prerequisites

- Docker with Compose v2
- `curl` available on PATH
- Ports 8080 available on localhost

### Steps

1. **Start the stack:**

   ```bash
   docker compose up --build -d
   ```

2. **Wait for health:**

   ```bash
   curl -sf http://127.0.0.1:8080/health/ready
   ```

   Expected: `{"status":"ok"}` or similar healthy response.

3. **Verify metrics endpoint:**

   ```bash
   curl -sf http://127.0.0.1:8080/metrics
   ```

   Expected: Prometheus-format text containing `vestrace_http_requests_total`.

4. **Run doctor in container:**

   ```bash
   docker compose exec vestrace-server vestrace doctor
   ```

   Expected: all checks pass or only warnings (no errors).

5. **Verify no sensitive labels in metrics:**

   ```bash
   curl -s http://127.0.0.1:8080/metrics | grep -E "query=|memory_id=|content="
   ```

   Expected: no output (sensitive labels are not exposed).

6. **Verify graceful shutdown:**

   ```bash
   docker compose stop vestrace-server
   ```

   Expected: server logs "shutdown signal received, stopping server" and exits cleanly.

7. **Tear down:**

   ```bash
   docker compose down -v
   ```

## Compose Smoke Tests

Automated Docker Compose smoke tests live in `tests/compose_smoke.rs` and are marked `#[ignore]` (require Docker):

```bash
cargo test -p vestrace-integration-tests --test compose_smoke -- --ignored
```

| Test | Scenario |
|------|----------|
| `compose_smoke_health_ready` | Stack starts, `/health/ready` returns 200 within 60s |
| `compose_smoke_metrics_endpoint` | `/metrics` returns Prometheus format with vestrace metric names |
| `compose_smoke_doctor_in_container` | `vestrace doctor` passes inside the server container |
| `compose_smoke_no_sensitive_labels_in_metrics` | Metrics output contains no `query=`, `memory_id=`, or `content=` labels |
