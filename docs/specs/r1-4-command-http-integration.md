# R1.4 Command HTTP Integration

## Goal

Move `POST /v1/runs` from the legacy direct repository write path to the canonical event-sourced run command path introduced in R1.3, while adding persisted request idempotency for create-run commands.

## Scope

- `POST /v1/runs` constructs a `RunCommandEnvelope::Create` and executes it through `RunCommandExecutor`.
- `GET /v1/runs` and `GET /v1/runs/{id}` continue reading from the existing `agent_runs` projection.
- `Idempotency-Key` is optional. When present, it is scoped by workspace, principal, command kind, and key.
- A completed receipt stores a deterministic request fingerprint, run id, committed run version, and creation timestamp.
- Repeating the same request with the same key returns the original run and does not append another event.
- Reusing the same key with a different request fingerprint returns `409 Conflict`.
- Concurrent requests using the same key yield one authoritative command execution; the loser reads the completed receipt or receives a bounded conflict while the first transaction is unresolved.
- The direct `RunRepository::create` path remains available only for the legacy `RunService`; HTTP no longer invokes it.

## HTTP contract

### Request

`POST /v1/runs`

Headers:

- `x-workspace-id`: required
- `x-principal-id`: required
- `x-correlation-id`: optional UUIDv7, generated by middleware when absent
- `Idempotency-Key`: optional non-empty ASCII string, maximum 128 bytes

Body:

```json
{
  "title": "Research task"
}
```

### Responses

- `201 Created`: first successful command execution.
- `200 OK`: replay of an already completed idempotent request.
- `400 Bad Request`: malformed or oversized idempotency key.
- `409 Conflict`: key already belongs to a different request fingerprint or command execution lost optimistic concurrency.
- Existing application/storage failures retain the current structured error mapping.

## Persistence contract

Create `run_command_receipts` with:

- `workspace_id uuid`
- `principal_id uuid`
- `command_kind text`
- `idempotency_key text`
- `request_fingerprint text`
- `run_id uuid`
- `run_version bigint`
- `created_at timestamptz`

Primary key: `(workspace_id, principal_id, command_kind, idempotency_key)`.

The receipt must become visible atomically with the run events and projection. A receipt must never point to a run version that was not committed.

## Fingerprint

For R1.4 create-run, fingerprint the canonical JSON object containing only the normalized title used by the domain command. Use SHA-256 hex encoding. The fingerprint implementation belongs to application/infrastructure code, not the HTTP handler.

## Non-goals

- generic idempotency for every future command
- command status polling
- asynchronous command execution
- HTTP endpoints for run transitions
- projection rebuild/checkpoints
- outbox or jobs
- removal of the legacy `RunService`

## Acceptance criteria

1. HTTP create produces exactly one `run.created` event and one matching projection.
2. Same idempotency key and same payload returns the original run without a second event.
3. Same key and different payload returns `409` without writes.
4. Requests without an idempotency key remain valid and create independent runs.
5. Workspace and principal boundaries prevent receipt reuse across identities.
6. Existing list/get behavior and response schema remain unchanged.
7. Full Rust, PostgreSQL, console, and Compose acceptance matrices pass.
