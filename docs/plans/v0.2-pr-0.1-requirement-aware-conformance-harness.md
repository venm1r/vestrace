# PR-0.1 — Requirement-aware Conformance Harness Skeleton

**Status:** approved documentation plan  
**Architecture baseline:** `docs/architecture-v0.2`  
**Implementation baseline:** `main@729d456f70f4de93c97d05cce795c09025c62f24`  
**Implementation changes authorized by this document:** **none**  
**Primary requirements:** `QUAL-001`, foundation for `QUAL-002`, `QUAL-013`

## 1. Goal

Create a minimal requirement-aware test evidence layer before any v0.2 domain implementation begins.

The harness must establish this distinction permanently:

```text
unit/integration test result
        !=
conformance result
        !=
qualification result
```

PR-0.1 does not qualify any Vestrace profile.

## 2. Core value objects

### RequirementRef

```text
RequirementRef
├─ requirement_id
├─ family
└─ specification_version
```

Canonical format:

```text
<FAMILY>-<NNN>
```

Allowed families:

```text
ARC MEM TMP MUT RET LRN CAP IDW HLT EXT REC GOV QUAL
```

Invalid/unknown IDs must fail registration rather than silently becoming arbitrary labels.

### ConformanceCase

```text
ConformanceCase
├─ case_id
├─ title
├─ requirement_ids[]
├─ profile_labels[]
├─ evidence_kind
└─ deterministic
```

A case may cover more than one requirement, but every mapping must be explicit.

### ConformanceCaseResult

```text
ConformanceCaseResult
├─ case_id
├─ status
├─ started_at
├─ completed_at
├─ evidence[]
└─ failure?
```

Statuses:

```text
PASS
FAIL
SKIPPED
BLOCKED
INCONCLUSIVE
```

### QualificationStatus

Qualification status is a separate concept:

```text
NOT_EVALUATED
INCOMPLETE
QUALIFIED
DISQUALIFIED
```

PR-0.1 must not synthesize `QUALIFIED` merely from test PASS values.

## 3. Profile labels

Cases may be tagged with future profiles:

```text
CORE
MEMORY
COGNITION
AUTONOMY
FEDERATION
TRUSTED
```

In PR-0.1 these are classification labels only. They do not assert that a profile is implemented or qualified.

## 4. Evidence record

Minimum machine-readable evidence:

```text
case_id
requirement_ids[]
status
test_binary / suite
test_name
source_revision
started_at
completed_at / duration
failure summary?
```

Later qualification work may add environment digest, DB version, migration set, policy revision, schema hashes, fault profile and signatures. Those are explicitly out of scope here.

## 5. Existing test reuse

PR-0.1 should wrap existing strong behaviors rather than duplicate them.

Initial candidates:

```text
Run optimistic concurrency
→ TMP / MUT / ARC

Memory lifecycle/revisions
→ MEM / MUT

ContextPack hard token budget
→ RET

Workspace RLS isolation
→ CAP / IDW

Missing capability denial
→ CAP
```

The existing v0.1 acceptance suite is a scenario source, not itself a qualification profile.

## 6. Initial conformance case IDs

Recommended bootstrap set:

```text
CONF-CORE-001  Optimistic version conflict is rejected
CONF-MEM-001   Memory revision/history behavior remains stable
CONF-RET-001   ContextPack never exceeds hard token budget
CONF-IDW-001   Foreign workspace data is denied
CONF-CAP-001   Missing capability denies protected operation
```

Case IDs are stable test-contract identifiers and are distinct from requirement IDs.

## 7. Storage/output

PR-0.1 may emit JSON/JSONL or another deterministic machine-readable local artifact.

The format must include a schema/version field from the beginning.

No durable production DB tables are required.

No migration is expected.

## 8. CI semantics

A failed registered MUST-requirement case should fail its conformance test job.

However CI green must still not be rendered as:

```text
Vestrace is QUALIFIED
```

The qualification evaluator arrives later.

## 9. What PR-0.1 MUST NOT introduce

- `QualificationBundle` production model;
- attestation/certificate language;
- target profile PASS claims;
- new product migrations;
- new HTTP/MCP runtime APIs;
- changes to production execution semantics;
- a second test runner where metadata can wrap existing Rust/integration tests;
- arbitrary unvalidated requirement strings.

## 10. Requirement mapping

### QUAL-001

Tests, conformance and qualification must remain distinct concepts.

### QUAL-002

PR-0.1 establishes the mapping structure needed for every future MUST requirement to have a verification path.

### QUAL-013

PR-0.1 establishes per-requirement evidence/result structure that later becomes an input to QualificationBundle.

## 11. Documentation-only acceptance cases

```text
CONF-HARNESS-001
valid requirement ID registers

CONF-HARNESS-002
invalid family/format is rejected

CONF-HARNESS-003
one case maps to multiple requirement IDs

CONF-HARNESS-004
PASS test result does not produce QUALIFIED profile

CONF-HARNESS-005
SKIPPED/INCONCLUSIVE remain distinct results

CONF-HARNESS-006
machine-readable result contains source revision
```

## 12. Future implementation exit gate

```text
[ ] requirement IDs validated against canonical catalog
[ ] existing tests can attach stable conformance metadata
[ ] one case can map to multiple requirements
[ ] machine-readable result schema is versioned
[ ] PASS/FAIL/SKIPPED/BLOCKED/INCONCLUSIVE are distinct
[ ] test result and qualification result are separate types/flows
[ ] source revision is captured
[ ] at least five existing strong behaviors are registered
[ ] no migrations
[ ] no runtime semantic changes
[ ] no CORE/MEMORY/TRUSTED qualification claim
```

Until these conditions pass, PR-0.1 remains planning-only.
