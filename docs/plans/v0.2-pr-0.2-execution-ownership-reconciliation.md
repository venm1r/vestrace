# PR-0.2 — Execution Ownership Reconciliation

**Status:** approved documentation plan  
**Architecture baseline:** `docs/architecture-v0.2`  
**Implementation baseline:** `main@729d456f70f4de93c97d05cce795c09025c62f24`  
**Implementation changes authorized by this document:** **none** — documentation/planning only  
**Primary requirements:** `ARC-004`, `ARC-005`, `MUT-007`  
**Primary ADR:** `docs/adr/0002-single-execution-state-engine-boundary.md`

## 1. Goal

Remove the architectural ambiguity between the existing event-sourced `AgentRun` runtime and the existing mutable `WorkflowExecution / StepExecution` lifecycle before either model is extended further.

The target ownership rule is:

> **`AgentRun` is the single authoritative durable execution lifecycle. Workflow/step execution records are typed execution history and projections linked to Run/RunStep identities; they are not an independent command/state runtime.**

This PR specification deliberately does **not** introduce a new execution aggregate, generic Task/Action/Attempt hierarchy, second event store, second retry engine, or second scheduler.

---

# 2. Why this reconciliation is required

Current `main` contains two independently mutable lifecycle models.

## 2.1 Run runtime

`AgentRun` / `RunState` provides:

- stable `AgentRunId`;
- `RunStatus`;
- monotonic `RunVersion`;
- command decision logic;
- append-only Run events;
- reducer/replay;
- optimistic concurrency;
- `RunStepState`;
- waits/completion;
- checkpoints and recovery.

This is already the stronger durable execution kernel and matches ADR-0002.

## 2.2 Workflow execution history

Current `WorkflowExecution` independently contains:

```text
WorkflowExecution
├─ WorkflowExecutionId
├─ workflow_id / workflow_revision_id
├─ ExecutionStatus
├─ attempt
├─ started_at / completed_at
├─ correlation_id
└─ causation_id
```

It owns a mutable `transition_to(...)` lifecycle.

`StepExecution` independently contains:

```text
StepExecution
├─ StepExecutionId
├─ WorkflowExecutionId
├─ workflow node identity
├─ kind
├─ attempt
├─ ExecutionStatus
├─ artifact/model/tool refs
├─ error_message
└─ started_at / completed_at
```

It also owns `transition_to(...)`.

The application port exposes direct lifecycle mutations:

```text
start_workflow_execution
update_workflow_execution_status
record_step
update_step_status
```

HTTP currently exposes direct creation/completion of this lifecycle through `/workflow-executions`.

Without reconciliation this naturally evolves into a second execution runtime with its own statuses, retries, history and recovery semantics.

# 3. Canonical ownership decision

## 3.1 Authoritative owner

`AgentRun` MUST be the authoritative durable lifecycle owner for all Vestrace-controlled execution.

Canonical chain:

```text
AgentRun
├─ Run events / version / reducer
├─ ExecutionPlanRevision
├─ RunStep identity/lifecycle
└─ typed operation/history refs
   ├─ WorkflowExecutionRecord
   ├─ StepExecutionRecord
   ├─ ModelExecution
   ├─ ToolInvocation
   ├─ ExternalEffect (future)
   ├─ HumanRequest
   ├─ SubRun
   └─ VerificationAttempt
```

A workflow is a versioned cognitive **definition/plan asset**. Executing that workflow happens **inside a Run**.

## 3.2 WorkflowExecution after reconciliation

`WorkflowExecution` remains a useful typed record answering:

> Which workflow revision did this Run execute, under what correlation/attempt context, and what was the derived execution outcome?

It MUST NOT independently decide whether the system is `Running`, `Waiting`, `Succeeded`, `Failed`, or `Cancelled`.

Its lifecycle/status becomes one of:

1. a projection from authoritative Run/RunStep events; or
2. append-oriented typed history facts derived during Run execution.

It MUST NOT be a second command target after migration.

## 3.3 StepExecution after reconciliation

`StepExecution` remains useful for workflow-node-specific history:

- exact workflow node;
- step kind;
- attempt number;
- model/tool/artifact references;
- errors/output metadata;
- timestamps.

But authoritative step lifecycle belongs to `RunStep` / Run events.

`StepExecution.status` MAY remain persisted for compatibility/read performance, but if retained it is a **derived projection** and MUST NOT be independently mutable by external commands.

# 4. Identity mapping

Target links:

```text
WorkflowExecutionRecord
├─ workflow_execution_id          # legacy/public typed history identity
├─ agent_run_id                   # REQUIRED authoritative owner
├─ workflow_id
├─ workflow_revision_id
└─ ...history metadata

StepExecutionRecord
├─ step_execution_id              # typed history identity
├─ workflow_execution_id
├─ agent_run_id                   # denormalized optional/required by schema decision
├─ run_step_id                    # REQUIRED authoritative step identity
├─ workflow_node_id
└─ ...operation/history metadata
```

Recommended canonical relation:

```text
one AgentRun
    1 ── 0..N WorkflowExecutionRecord

one RunStep
    1 ── 0..N StepExecutionRecord
```

`0..N` is intentional because:

- one Run may execute no workflow at all;
- a Run may execute several workflow/subworkflow segments;
- one logical RunStep may produce multiple typed attempt/history records where future semantics require it.

No identity is collapsed merely to make tables look simpler.

# 5. Lifecycle mapping

Current status enums are not identical:

```text
RunStatus:
Created
Ready
Running
WaitingForInput
WaitingForApproval
Completed
Failed
Cancelled
Stalled

ExecutionStatus:
Queued
Running
Waiting
Succeeded
Failed
Cancelled
```

Therefore direct enum equivalence MUST NOT be introduced.

## 5.1 Projection mapping

A compatibility read projection MAY map:

```text
Run Created / Ready        → Queued
Run Running                → Running
Run WaitingForInput        → Waiting
Run WaitingForApproval     → Waiting
Run Completed              → Succeeded
Run Failed                 → Failed
Run Cancelled              → Cancelled
Run Stalled                → Failed or separate compatibility marker
```

But `Stalled → Failed` is lossy and MUST NOT be used as canonical semantics.

Preferred long-term representation is to expose Run status directly and treat legacy `ExecutionStatus` only as compatibility/read-model vocabulary.

## 5.2 Waiting semantics

`RunWait` remains authoritative because it differentiates:

- input;
- approval;
- job;
- event;
- timer.

Legacy generic `ExecutionStatus::Waiting` MUST NOT become the owner of waiting semantics.

## 5.3 Completion semantics

`RunCompletion` remains authoritative because it distinguishes:

- Completed;
- PartiallyCompleted;
- Failed with retryability metadata;
- Cancelled;
- Stalled.

`ExecutionOutcome` may preserve domain/workflow summaries, but MUST NOT override RunCompletion.

---

# 6. Attempt ownership

Current workflow/step history contains `attempt` fields.

These SHOULD remain typed history attributes, not a generic universal retry runtime.

Rules:

1. retry policy belongs to the typed operation / Run command semantics that owns retryability;
2. workflow node attempt numbers may be recorded by `StepExecutionRecord`;
3. a duplicate `(workflow_execution_id, node_id, attempt)` remains invalid for history integrity;
4. the existence of `attempt = N` MUST NOT authorize another attempt;
5. future ExternalEffect retry semantics MUST use the ExternalEffect adapter contract, not this generic attempt counter.

---

# 7. Persistence migration design

Existing migration `0017_external_execution_history.sql` MUST NOT be edited.

A future forward-only migration SHOULD add linkage rather than destructively replace existing history.

## 7.1 `workflow_executions`

Recommended additive fields:

```text
agent_run_id UUID NULL initially
ownership_version / record_semantics marker if needed
```

After backfill/new-write transition, new Vestrace-controlled workflow execution records MUST have an `agent_run_id`.

Whether the eventual DB constraint becomes `NOT NULL` depends on legacy rows that cannot be proven to belong to a Run.

Unknown historical ownership MUST remain unknown; do not fabricate Run IDs.

## 7.2 `step_executions`

Recommended additive fields:

```text
run_step_id UUID NULL initially
agent_run_id UUID NULL (optional denormalization)
```

For new writes produced from Run execution, `run_step_id` MUST be known.

## 7.3 Foreign keys

Where current schema permits safe references, future migration SHOULD add FKs to the authoritative run/step tables or identities used by the Run persistence model.

If a direct FK to event-sourced step identity is not structurally available, the implementation may use a durable typed UUID reference plus integrity checker until the projection schema can enforce the relation.

## 7.4 Legacy rows

Legacy history is preserved.

Classification:

```text
LINKED
  row can be deterministically connected to AgentRun/RunStep

UNLINKED_LEGACY
  relation cannot be proven
```

`UNLINKED_LEGACY` rows remain readable but cannot be treated as authoritative execution state.

No synthetic linkage is allowed from timestamp/title similarity alone.

---

# 8. Write-path transition

Migration should use a staged model.

## Stage A — introduce links

Add Run/RunStep references and repository support while current API remains compatible.

## Stage B — dual visibility, single authority

Run commands/events own lifecycle. Workflow/step records are produced from the Run execution path as history/projection records.

Direct status mutations are deprecated internally.

## Stage C — disable independent lifecycle writes

External/public commands can no longer:

- start an independent WorkflowExecution without a Run;
- complete/fail/cancel WorkflowExecution independently of Run;
- mutate StepExecution status independently of RunStep state.

## Stage D — legacy compatibility read surface

Old records/endpoints may remain readable or become compatibility wrappers over Run-owned operations.

No second command state machine remains.

# 9. HTTP compatibility strategy

Current endpoints:

```text
POST /workflow-executions
GET  /workflow-executions/{id}
POST /workflow-executions/{id}/steps
GET  /workflow-executions/{id}/steps
POST /workflow-executions/{id}/complete
POST /workflow-executions/{id}/outcomes
GET  /workflow-executions/{id}/outcomes
```

## 9.1 Read endpoints

Read endpoints MAY remain for compatibility if they clearly represent workflow execution history/read models.

## 9.2 Start endpoint

Future behavior MUST NOT create an independent lifecycle.

Allowed strategies, in preferred order:

1. translate `POST /workflow-executions` into a Run creation/start command and return both Run identity and compatibility workflow-execution identity;
2. deprecate the endpoint in favor of Run API if preserving it would create semantic ambiguity.

The endpoint MUST NOT bypass Run policy/version/recovery semantics.

## 9.3 Complete endpoint

`POST /workflow-executions/{id}/complete` MUST NOT directly set the authoritative lifecycle status.

Future compatibility behavior must resolve the owning Run and issue an allowed Run command, or be deprecated.

## 9.4 Step write endpoint

Direct external creation of arbitrary `StepExecution` history is unsafe as an authoritative path.

Future write semantics should be internal execution-history recording from Run/Workflow orchestration. Public read access may remain according to capability policy.

## 9.5 Outcomes

ExecutionOutcome may remain an append-oriented typed domain record if it is clearly evidence/history and cannot rewrite RunCompletion.

# 10. MCP / internal compatibility

Any MCP or internal surface that currently writes `WorkflowExecution`/`StepExecution` MUST eventually route through the same Run/application command boundary.

No surface receives an exemption because it is "internal".

Conformance later MUST test:

```text
HTTP
MCP
worker/internal command
replay/recovery
```

for bypass of the single execution owner.

---

# 11. Workflow definition ownership

`Workflow` / `WorkflowRevision` remain versioned cognitive assets.

They own **definition semantics**, such as:

- nodes;
- edges;
- workflow version;
- node kinds;
- declarative execution structure.

They do NOT own durable runtime lifecycle.

Target relation:

```text
WorkflowRevision
      ↓ selected by
ExecutionPlanRevision / Run
      ↓ executes through
RunStep
      ↓ records typed history
WorkflowExecutionRecord / StepExecutionRecord
```

This preserves workflow-specific observability without creating a workflow-specific runtime.

---

# 12. State synchronization rule

There MUST NOT be two independently writable status fields whose divergence requires reconciliation.

If compatibility status is persisted in `workflow_executions` / `step_executions`, then:

```text
Run event/state
    ↓ deterministic projection
compatibility execution status
```

Never:

```text
Run status ←→ WorkflowExecution status
```

with bidirectional mutation.

A mismatch between authoritative Run state and its execution-history projection is a future **derived-state integrity finding**, repairable downward by rebuild.

---

# 13. Recovery semantics

Only Run state participates in authoritative replay/recovery.

On recovery:

```text
Run events/checkpoint
→ reconstruct RunState
→ rebuild workflow/step history projection where derivable
```

Legacy history records that contain unique evidence not present in Run events remain historical evidence and are not deleted, but they do not control recovered Run state.

Future Incident/Revalidation MUST treat any non-derivable conflict as explicit evidence/problem rather than choosing the history table over the Run stream.

---

# 14. Cancellation semantics

Cancellation authority belongs to Run commands/policy.

A compatibility workflow endpoint MUST NOT set `ExecutionStatus::Cancelled` directly without causing/confirming the corresponding authoritative Run transition.

Typed provider/tool operations may have weaker cancellation guarantees; their own outcome remains typed history and does not change this ownership rule.

---

# 15. Concurrency semantics

Run `RunVersion` / expected-version checking remains the concurrency owner.

`WorkflowExecution` MUST NOT introduce a separate optimistic-concurrency version whose success could conflict with RunVersion.

History record uniqueness constraints remain useful for duplicate prevention but are not logical aggregate versioning.

---

# 16. Idempotency semantics

Existing request/command idempotency should anchor to the authoritative Run command.

A compatibility WorkflowExecution identity MAY be returned on repeat requests, but duplicate prevention at the history-record layer MUST NOT substitute for Run-command idempotency.

---

# 17. Security / capability boundary

Future operation vocabulary should make the authority distinction explicit.

Examples:

```text
execution.run.start
execution.run.cancel
execution.run.resume
execution.history.read
execution.history.record        # internal/system capability only where needed
```

A permission to read or append typed history does not grant authority to transition the Run.

Until CapabilityGrant v2 exists, PR-0.2 implementation should preserve existing policy/RLS behavior and avoid creating broader shortcuts.

---

# 18. Observability

WorkflowExecution and StepExecution remain valuable for:

- UI timeline;
- workflow-node inspection;
- audit/execution diagnostics;
- model/tool linkage;
- attempt history;
- execution outcome analysis.

This is why they are retained rather than deleted.

The correct architectural classification is:

> **durable typed history/read models with domain identity, not independent lifecycle aggregates.**

---

# 19. What PR-0.2 MUST NOT do

No implementation corresponding to this plan may:

- create a new generic `Task`, `Action`, or `Attempt` execution aggregate;
- create another event stream for WorkflowExecution lifecycle;
- add a second checkpoint/recovery system;
- make WorkflowExecution the parent of AgentRun;
- use timestamps to fabricate Run linkage for legacy rows;
- delete legacy workflow/step execution history;
- make legacy `ExecutionStatus` the canonical target status vocabulary;
- couple future ExternalEffect retry semantics to generic StepExecution attempt counters;
- change workflow definitions into mutable runtime state.

# 20. Requirement mapping

## `ARC-004`

Repair, recovery, governance, effects, workflows and other operations use the common execution boundary.

PR-0.2 contribution: establishes Run as that sole boundary for existing workflow execution.

## `ARC-005`

No second execution runtime/event store.

PR-0.2 contribution: demotes WorkflowExecution/StepExecution from independent lifecycle to typed history/projection.

## `MUT-007`

State Engine must not introduce generic/duplicating execution aggregates.

PR-0.2 contribution: preserves Run-first ownership and prevents workflow execution tables from becoming parallel aggregate roots.

Supporting future requirements:

- `TMP-006..010` — one concurrency/order owner;
- `REC-004..006` — one crash-recovery classification path;
- `EXT-*` — typed effect semantics under Run rather than generic attempt runtime;
- `QUAL-*` — single-owner negative/bypass conformance cases.

# 22. Compatibility risk assessment

## High-risk surfaces

1. `POST /workflow-executions` currently creates an independent execution.
2. `/complete` directly mutates WorkflowExecution status.
3. step-recording APIs allow status-bearing records without a RunStep owner.

These MUST be normalized before the API is considered stable target architecture.

## Medium-risk surfaces

- MCP/internal execution-history writes;
- acceptance fixtures that treat workflow execution as an independent lifecycle;
- UI assumptions that WorkflowExecution status is canonical.

## Low-risk/reusable pieces

- workflow revision identity;
- workflow node identity;
- model/tool/artifact references;
- attempt uniqueness as history integrity;
- RLS isolation;
- execution artifacts/outcomes as typed evidence/history.

# 23. Documentation-only acceptance cases

These cases define what later code/conformance work must prove.

## CONF-ARC-EXEC-001 — Single lifecycle owner

Given one workflow-driven autonomous operation, there is exactly one authoritative Run lifecycle.

No independent WorkflowExecution transition can make the operation terminal while Run remains non-terminal.

Maps: `ARC-004`, `ARC-005`.

## CONF-ARC-EXEC-002 — Workflow execution requires Run owner

Every new Vestrace-controlled WorkflowExecution history record has an `AgentRunId`.

Legacy unlinked records are explicitly classified as legacy/unknown rather than fabricated.

Maps: `ARC-005`.

## CONF-ARC-EXEC-003 — Step history requires RunStep owner

Every new workflow StepExecution produced by runtime maps to a RunStep identity.

Maps: `ARC-004`, `MUT-007`.

## CONF-ARC-EXEC-004 — Compatibility status is derived

Changing/rebuilding Run state deterministically yields the compatible workflow/step status; direct compatibility-row status mutation cannot override Run.

Maps: `ARC-001..005` supporting set.

## CONF-ARC-EXEC-005 — Recovery uses Run history

Deleting/rebuilding derived workflow execution status must not change the recovered Run result.

Maps: `ARC-002`, `ARC-004`, future `REC-*`.

## CONF-ARC-EXEC-006 — HTTP cannot bypass owner

Workflow compatibility endpoints either delegate to Run commands or reject/deprecate independent lifecycle mutation.

Maps: `ARC-004`, `ARC-005`.

## CONF-ARC-EXEC-007 — Workflow definition is immutable execution input

The Run references an exact WorkflowRevision used for execution; runtime progress does not mutate the WorkflowRevision.

Maps: `ARC-001`, cognition asset boundary.

## CONF-ARC-EXEC-008 — Attempt counter grants no retry authority

Increasing/recording an attempt number does not by itself authorize execution/retry.

Maps: `ARC-004`, future `EXT-*`.

# 24. PR-0.2 implementation exit gate

A future implementation PR-0.2 is complete only when all are true:

```text
[ ] AgentRun is documented and implemented as sole authoritative lifecycle owner
[ ] new WorkflowExecution records link to AgentRun
[ ] new StepExecution records link to RunStep
[ ] workflow/step compatibility statuses cannot override Run state
[ ] direct independent workflow lifecycle mutation is removed, delegated or explicitly deprecated
[ ] recovery/replay remains Run-owned
[ ] no second event/retry/checkpoint runtime is introduced
[ ] legacy history remains readable
[ ] no synthetic linkage is fabricated for legacy rows
[ ] RLS/workspace isolation is preserved
[ ] requirement-aware conformance cases cover ARC-004 / ARC-005 / MUT-007
[ ] migrations are forward-only
```

Until those gates are satisfied, PR-0.2 remains `PLANNED`, not implemented/conformant.

# 26. Final decision

The existing workflow execution subsystem is **retained but reclassified**.

```text
BEFORE

AgentRun lifecycle       WorkflowExecution lifecycle
       │                         │
       └──── two mutable owners ─┘

AFTER

AgentRun / RunStep
 authoritative lifecycle
          │
          ├── WorkflowExecutionRecord
          ├── StepExecutionRecord
          ├── ExecutionArtifact
          └── ExecutionOutcome
                typed history / projections
```

This is the canonical implementation direction for PR-0.2.
