# Vestrace v0.2 → v1.0 — Dependency / Parallelization Map

**Status:** approved documentation plan  
**Implementation changes authorized:** none

## 1. Default rule

The roadmap is dependency-first. Parallel work is allowed only when it cannot create competing authority models or incompatible migrations.

## 2. Critical serial spine

The following spine is intentionally serial:

```text
0.1 → 0.2 → C1 → C2 → C3 → C4 → C5 → C6 → C7 → C8
```

Reason: each step defines authority/provenance semantics required by the next.

After C8:

```text
L1 → L2 → L3
G1 → G2 → G3 → G4 → G5 → G6
H1 → H2 → H3 → H4 → H5
E1 → E2 → E3 → E4
T1 → T2 → T3 → T4 → T5 → T6 → T7 → T8
```

## 3. Safe parallel preparation

The following work may be prepared in parallel but not merged ahead of dependencies:

| Work | May prepare while | Merge dependency |
|---|---|---|
| C8 conformance fixtures | C5–C7 | C7 |
| L3 benchmark datasets | L1–L2 | L2 |
| G6 negative-test matrix | G2–G5 | G5 |
| H5 fault scenarios | H2–H4 | H4 |
| E4 adapter fault fixtures | E1–E3 | E3 |
| T8 TRUSTED suite manifests | T3–T7 | T7 |
| docs/current-implementation updates | any PR | same PR |

## 4. Forbidden parallelization

Do not develop competing versions in parallel for:

- Run ownership vs WorkflowExecution ownership;
- Claim/reconciliation semantics before Evidence v2;
- ContextPack truth assembly before exact-revision retrieval;
- cross-workspace sharing before capability/delegation foundations;
- auto-repair before HealthFinding/RepairPlan separation;
- external dispatch before adapter idempotency/reconciliation declaration;
- trust restoration before RevalidationRun;
- qualification claims before requirement evidence exists.

## 5. Migration collision rule

Two future PRs may not independently redefine the same canonical column/table ownership. If preparation overlaps:

1. earlier dependency owns the canonical schema decision;
2. later PR extends it additively;
3. historical migration files remain immutable;
4. data backfill never invents facts not derivable from source state.

## 6. Review batching

Review may batch PRs conceptually as:

```text
Batch A: 0.1–0.2
Batch B: C1–C4
Batch C: C5–C8
Batch D: L1–L3
Batch E: G1–G3
Batch F: G4–G6
Batch G: H1–H5
Batch H: E1–E4
Batch I: T1–T4
Batch J: T5–T8
```

Batching is for review coordination only; release gates remain per PR dependency order.
