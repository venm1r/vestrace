# Vestrace v0.2 → v1.0 — Migration Rollout & Compatibility Contract

**Status:** planning baseline  
**Implementation changes authorized:** none

## 1. Global rules

All future schema evolution is forward-only and additive by default.

Never:

- edit already-applied migrations;
- invent unknown historical facts during backfill;
- reinterpret legacy rows as stronger target semantics without proof;
- drop old read paths before compatibility evidence exists;
- claim rollback semantics that require destructive history rewrite.

## 2. Rollout phases

Every schema-bearing PR should use the smallest applicable sequence:

```text
EXPAND
→ BACKFILL
→ DUAL-READ / COMPATIBILITY READ
→ SWITCH AUTHORITATIVE WRITE/READ
→ VERIFY
→ DEPRECATE LEGACY PATH
→ CONTRACT (only in later dedicated migration)
```

Not every PR needs dual-write. Dual-write is allowed only where both representations can be kept semantically equivalent without hidden divergence.

## 3. Unknown-preserving backfill

Backfill rules:

- unknown `occurred_at` stays `NULL`;
- unknown actor stays explicit unknown/system-migration marker;
- unknown validity does not become synthetic `valid_from`;
- old grants do not become accepted mounts automatically;
- old diagnostics do not become historical HealthFindings unless exact evidence exists;
- old tool invocations do not become confirmed ExternalEffects unless dispatch/outcome evidence exists;
- old secrets/credentials are not copied into Memory or governance tables;
- old evaluation scores do not become authoritative learned conclusions automatically.

## 4. Compatibility classes

| Class | Meaning |
|---|---|
| `READ_COMPATIBLE` | New runtime can read legacy representation safely. |
| `WRITE_COMPATIBLE` | New writes can be consumed by old readers without semantic loss. |
| `DUAL_REPRESENTATION` | Both schemas coexist temporarily with explicit ownership. |
| `VERSION_GATED` | Old reader/runtime must reject unsupported new version. |
| `REBUILD_ONLY` | Derived state is rebuilt rather than migrated row-by-row. |
| `NO_AUTOMATIC_UPGRADE` | Legacy record cannot safely become target semantic object automatically. |

## 6. Contract/drop policy

Destructive schema cleanup is not part of the PR that first introduces replacement semantics unless all are true:

1. backfill/rebuild completed;
2. new path is authoritative;
3. compatibility tests pass;
4. no supported reader requires legacy schema;
5. recovery/restore fixtures cover the new representation;
6. removal has its own reviewable migration step.

## 7. Failure policy

If migration/backfill cannot prove a target semantic value, it must preserve uncertainty and create a verification/reconciliation obligation where required. Migration success must never be achieved by inventing domain truth.
