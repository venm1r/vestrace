# PR-H1 — Invariant Registry + HealthFinding

## Goal

Convert the current fixed diagnostics/rebuild foundation into a normative invariant system without replacing working checks.

## Target flow

```text
InvariantDefinition metadata
      +
typed checker
      ↓
HealthFinding
      ↓
HealthOccurrence
```

## InvariantDefinition

```text
invariant_id
domain
scope kind
description
default severity
checker kind
repair strategy
check modes
cost class
version
```

## HealthFinding

Stores invariant, deterministic fingerprint, scope, severity, impact, evidence, repairability and lifecycle.

Integrity lifecycle:

```text
OPEN
ACKNOWLEDGED
REPAIR_PLANNED
REPAIRING
VERIFYING
RESOLVED
REOPENED
```

Suppression/AcceptedRisk remain separate disposition overlays per ADR-0009.

## Migration

Current diagnostics become typed checker implementations where possible. Do not delete diagnostic behavior just to rebuild it under new names.

## Requirements

`HLT-001..005`, `HLT-014`, `HLT-017`.

## Acceptance

- stable invariant IDs/versioning;
- deterministic finding fingerprints;
- repeated detections become occurrences of same logical finding;
- UNKNOWN coverage does not become HEALTHY;
- health aggregation follows dependency scopes.

# PR-H2 — RepairPlan / RepairExecution / Verification

## Goal

Put every mutation-capable repair behind an immutable plan and explicit verification.

## Target flow

```text
HealthFinding
→ RepairPlan
→ precondition check
→ policy/capability
→ existing Run execution boundary
→ RepairExecution
→ VerificationRun
→ RESOLVED / REOPENED
```

## Reuse

Current direct projection rebuild logic may remain as a low-level deterministic operation, but top-level repair semantics must no longer bypass plan/authority/verification.

## RepairPlan

Includes input state, exact findings, operations, postconditions, verification checks, risk, reversibility, authority and expiry.

## Requirements

`HLT-006..013`, `HLT-020`.

## Acceptance

- stale plan cannot execute;
- deterministic repair only writes downward from authority hierarchy;
- checker cannot hide mutations;
- execution success alone does not resolve finding;
- verification failure reopens/leaves finding open;
- composite repairs are restartable/idempotent rather than pretending distributed ACID.

# PR-H3 — Recurrence / Flapping / Disposition / Repair Budgets

## Goal

Prevent repair loops and distinguish integrity truth from operational treatment.

## Target model

```text
HealthOccurrence
RecurrenceClass:
  ONE_OFF
  RECURRENT
  FLAPPING
  PERSISTENT

RepairBudget
  max_attempts_per_window
  cooldown
  max_cumulative_risk

FindingDisposition
  NONE
  SUPPRESSED
  ACCEPTED_RISK
  MAINTENANCE_WINDOW
```

## Requirements

`HLT-014..019`, ADR-0009.

## Acceptance

- repeated recurrence increments occurrence history;
- exhausted budget stops auto-repair;
- flapping creates/escalates `REPAIR_LOOP_DETECTED` behavior;
- AcceptedRisk does not resolve finding;
- expired suppression does not rewrite finding history.

# PR-H4 — Doctor / Repair CLI Contract v2

## Goal

Align operator semantics with the architecture contract while preserving useful diagnostics.

## Target semantic surface

```text
vestrace doctor
  read-only diagnostics

vestrace doctor --plan
  diagnostics + RepairPlan creation only

vestrace repair <plan>
  governed execution + verification
```

A specialized `rebuild` command may remain, but only as an explicit wrapper/delegation to the same plan/verification semantics for rebuildable derived state.

## Rules

- no hidden fix-all authority;
- dangerous repair requires capability/policy;
- output distinguishes finding, plan, execution and verification;
- operator override cannot mark raw integrity healthy without verification.

## Acceptance

- doctor read-only path provably causes no repair writes;
- plan mode causes no repair execution;
- repair checks stale state;
- CLI exit/output reflects verification, not merely SQL success.

# PR-H5 — Understand Conformance Gate

## Mandatory scenarios

```text
projection drift → deterministic repair → verify
stale plan → no mutation
repair execution succeeds / verification fails → finding open
recurring defect → FLAPPING / budget stop
suppressed open finding → raw integrity still degraded
local finding does not globally escalate without dependency relation
unknown check coverage → UNKNOWN, not HEALTHY
```

## Release gate

All applicable `HLT-*` MUST requirements pass with executable evidence.

Only after this gate may **v0.5 Understand** be claimed.
