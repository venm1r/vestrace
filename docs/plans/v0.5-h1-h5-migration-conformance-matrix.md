# v0.5 Understand — Migration / Conformance Matrix (H1–H5)

**Status:** documentation-only implementation contract

## H1 — Invariant Registry + HealthFinding

### Migration

Add `InvariantDefinition`, `HealthFinding`, `HealthOccurrence`, stable fingerprint metadata and aggregate health projections.

Backfill:

- existing diagnostics become invariant/check definitions only where semantics are deterministic;
- current diagnostic failures may seed findings with exact evidence/scope;
- absence of historical evidence is not backfilled as `HEALTHY`;
- `UNKNOWN` remains explicit when coverage/freshness is insufficient.

### Cases

| Case | Requirements | Expected result |
|---|---|---|
| CONF-HLT-001 Findings-first | HLT-001/002 | raw finding exists independently from health projection |
| CONF-HLT-002 Unknown health | HLT-003 | missing/stale check coverage never produces HEALTHY |
| CONF-HLT-003 Stable invariant id | HLT-005 | invariant ID/version deterministically identifies check contract |
| CONF-HLT-004 Fingerprint recurrence | HLT-014 | repeated same defect produces occurrences under same logical finding |
| CONF-HLT-005 Dependency propagation | HLT-017 | health propagates only across declared dependencies |

## H2 — RepairPlan / RepairExecution / Verification

### Schema

Add immutable RepairPlan, RepairExecution, verification runs/evidence and plan input-state/precondition references.

### Cases

| Case | Requirements | Expected result |
|---|---|---|
| CONF-HLT-006 Downward authority | HLT-006 | auto-repair rebuilds only from more authoritative source |
| CONF-HLT-007 Checker separation | HLT-007 | checker cannot directly perform hidden mutation |
| CONF-HLT-008 Immutable plan | HLT-008 | authorized plan material cannot mutate in place |
| CONF-HLT-009 Stale plan | HLT-009 | changed precondition returns STALE_PLAN with no mutation |
| CONF-HLT-010 Repair authorization | HLT-010 | risky repair requires capability/policy/approval as configured |
| CONF-HLT-011 Verification closure | HLT-011..013 | successful execution without verification does not resolve finding |

## H3 — Recurrence / Flapping / Disposition / Repair Budgets

### Schema

Add repair attempt budgets/cooldowns, recurrence projection and separate disposition objects.

Backfill:

- historical diagnostics may become occurrences only when fingerprint equivalence is deterministic;
- suppression/accepted-risk history remains disposition metadata, never synthetic resolution.

### Cases

| Case | Requirements | Expected result |
|---|---|---|
| CONF-HLT-012 Repair budget | HLT-015 | auto-repair stops after configured attempts/window |
| CONF-HLT-013 Flapping | HLT-016 | recurring repair loop transitions to flapping/escalation |
| CONF-HLT-014 Accepted risk | HLT-018/019 | accepted-risk finding remains open until verification proves repair |
| CONF-HLT-015 Disposition expiry | HLT-018/019 | expiry changes operational disposition, not raw integrity history |

## H4 — Doctor / Repair CLI Contract v2

### Compatibility

Existing `doctor` and direct `rebuild` behaviors become explicit surfaces:

```text
vestrace doctor        → read-only findings/check evidence
vestrace doctor --plan → plan only
vestrace repair <plan> → governed execution
```

Legacy direct rebuild may remain only as a compatibility/admin path until target RepairPlan semantics are available; it must be clearly labeled and cannot masquerade as verified repair.

### Cases

- default doctor performs no mutation;
- plan mode performs no repair;
- repair requires exact immutable plan;
- stale plan is rejected;
- post-repair verification is mandatory;
- CLI and internal API produce equivalent governed semantics.

## H5 — Understand Gate

Required golden scenarios:

1. missing search projection → finding → deterministic repair → verification;
2. stale RepairPlan;
3. failed verification after successful operations;
4. flapping repair loop;
5. accepted-risk unresolved finding;
6. partial scope health propagation;
7. unknown/stale health coverage;
8. doctor read-only guarantee.

Gate:

```text
required HLT MUST PASS
unverified RESOLVED transitions = 0
auto-repair upward authority violations = 0
unbounded repair loops = 0
required SKIPPED/INCONCLUSIVE = 0
```

## Global migration rules

1. Existing diagnostics are preserved; new findings layer on top.
2. Historical absence of failure is not proof of historical health.
3. Repair history is append-oriented.
4. `SUPPRESSED`/`ACCEPTED_RISK` are disposition overlays, not finding resolution states.
5. No repair schema introduces a second execution runtime.
