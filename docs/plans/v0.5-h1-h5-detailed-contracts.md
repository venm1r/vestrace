## PR-H1 — Invariant Registry + HealthFinding

### Requirements

`HLT-001..007`, `HLT-014`, `HLT-017`.

### Contract

```text
InvariantDefinition
├─ invariant_id
├─ domain
├─ scope_kind
├─ description
├─ default_severity
├─ checker_kind
├─ repair_strategy
├─ check_mode
├─ cost_class
├─ max_staleness?
└─ version

HealthFinding
├─ finding_id
├─ invariant_id/version
├─ fingerprint
├─ category
├─ severity
├─ impact
├─ origin_scope
├─ affected_scopes[]
├─ evidence_refs[]
├─ repairability
├─ lifecycle
└─ first/last_seen_at
```

Finding fingerprint must be deterministic; LLM-generated fingerprint is prohibited.

### Acceptance

- `UNKNOWN != HEALTHY`;
- checker emits evidence, never hidden mutation;
- same defect deduplicates to one finding identity with multiple occurrences;
- health aggregation follows declared dependency graph.

## PR-H2 — RepairPlan / RepairExecution / Verification

### Requirements

`HLT-006..013`, `HLT-020`, `ARC-003..004`.

### Contract

```text
HealthFinding
→ RepairPlan
→ policy/capability
→ existing Run runtime
→ RepairExecution
→ VerificationRun
→ RESOLVED/REOPENED
```

RepairPlan pins finding fingerprint, input state, preconditions, operations, postconditions, verification scope, risk, reversibility, capability and expiry.

### Rules

- deterministic repair only downward in authority hierarchy;
- stale plan -> `STALE_PLAN`, no mutation;
- execution success != finding resolution;
- only successful verification may resolve finding.

### Acceptance

- corrupt retrieval projection rebuild leaves canonical Memory unchanged;
- concurrent canonical change invalidates plan;
- verification failure keeps/reopens finding;
- composite repair is restartable/idempotent rather than fake distributed ACID.

## PR-H3 — Recurrence / Flapping / Disposition / Repair Budgets

### Requirements

`HLT-014..019` plus ADR-0009.

### Contract

```text
HealthOccurrence
├─ finding_id
├─ detected_at
├─ evidence
└─ repair/execution refs?
```

Recurrence classes: `ONE_OFF`, `RECURRENT`, `FLAPPING`, `PERSISTENT`.

Disposition is separate from integrity state:

```text
NONE
SUPPRESSED
ACCEPTED_RISK
MAINTENANCE_WINDOW
```

### Repair budget

```text
max_attempts_per_window
cooldown
max_cumulative_risk
```

### Acceptance

- repeated repair loop becomes FLAPPING;
- auto-repair stops after budget exhaustion;
- accepted risk leaves finding open until verified repair;
- suppression affects routing, not raw integrity truth.

## PR-H4 — Doctor / Repair CLI Contract v2

### Requirements

`HLT-007..013`, `CAP-010`, architecture operator contract.

### Semantic CLI

```text
vestrace doctor            # read-only findings/checks
vestrace doctor --plan     # create plans, no execution
vestrace repair <plan>     # governed execution
```

Existing direct rebuild behavior becomes a compatibility path only where it maps to an explicit deterministic RepairPlan.

### Acceptance

- `doctor` never mutates;
- `--plan` never mutates authoritative/derived target state;
- repair checks capability/policy/preconditions;
- output distinguishes finding, plan, execution and verification states.

## PR-H5 — Understand Conformance Gate

### Requirements

All applicable `HLT-*`, plus inherited CORE/MEMORY/GOVERN requirements.

### Mandatory scenarios

```text
derived projection corruption -> deterministic repair -> verify
stale RepairPlan -> no mutation
repair succeeded but verification failed -> finding open
recurrent defect -> flapping -> auto-repair suspended
accepted risk -> operational disposition only
health dependency propagation
checker failure -> UNKNOWN coverage, not HEALTHY
```

### Exit gate

`v0.5 Understand` is claimable only when repair safety and evidence-backed closure are executable hard gates.
