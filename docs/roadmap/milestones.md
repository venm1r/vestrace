# Milestones: entry, outcome, and exit

**Status:** Proposed milestone framework. No dates or new runtime acceptance are assigned.

## M0 — Baseline and execution order

Start from an explicitly pinned checkout and review available source/evidence. Separate code
from documentation, reread affected symbols, capture dirty/untracked state, and agree exact
writable/protected paths, prerequisites, and the program branch. Exit requires owner acceptance
of a concrete first scope, intact existing gates, and named reproducible checks. This editorial
package supplies preparation, not approval to implement code.

## M1 — Foundation

Follow the accepted P04/P05 predecessors. Reuse accepted publication work, close remaining
query/rebuild and worker-composition obligations, and verify setup, roles, freeze, restore,
and diagnostics. Real terminal outcomes must survive selected crashes without fabricated
SQL completion. Accept P04/G0 only through their own evidence. Read-only design may start earlier.

## M2 — Governed memory

Enter after MW-00 and lawful reads/basic security. Implement detail/history/browse, context
output, the shared atomic writer, and Console. Users must read exact revisions, correct them,
receive conflicts for races, and see persisted results after reload. Qualify context readiness
separately from successful detail reads.

## M3 — User sources

Enter after MW-02/03 and material/scheduling dependencies. Deliver bounded import, exact
preview/apply, three-way sync, Missing/cancellation, portability, and upgrade. Exit requires
one complete folder → memory → editorial change → updated folder → conflict resolution →
permitted export workflow through actual API/worker/browser. An importer without an LLM is
an intentional scope choice, not a missing milestone feature.

## M4 — Measured usefulness

Use the working P1 workflow and pilot observations to choose temporal semantics, conflicts,
inspection, or integration. Add derived summaries only when useful. Compare the same corpus,
model, permissions, and budget; demonstrate a concrete improvement without a safety regression.
Not every P2 initiative is required before a pilot or continuation of the frozen-v1 track.

## M5 — Full release contract

Follow P05 → P06 → P07 → P08/P09 → P10 → P11, with separately qualified MW extensions
only when included. Exit requires P12 on the exact environment, the accepted release policy,
upgrade/restore, and known limitations. Developer PASS, document checks, and stars do not
replace the gate.

## M6 — Demand-supported expansion

Enter when people return to the task and operating costs are measured. Select team, hosting,
SDK, format, or harness work explicitly. Define a separate scope, support owner, and threat/
operations model. A local single-workspace result does not establish cluster or federation support.

## Stop expansion when fundamentals regress

Access violations, unresolved data loss, unreproducible upgrades, and duplicate external
effects return priority to the affected P0 path. Poor onboarding returns priority to P1.
Lack of meaningful repeat use calls for validating the scenario, not automatically building P4.
